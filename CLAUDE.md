# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Gekko 2 is a modular crypto trading bot framework written in TypeScript and run with Bun. It covers candle import, backtesting, screening/alerting, paper trading and live trading through CCXT (Binance, Hyperliquid). There is one entry point, `src/gekko2.ts`; what it does is decided entirely by a config file.

## Commands

Bun is the package manager and the runtime. Scripts, git hooks and CI all go through `bun` and `bun.lock`; `package-lock.json` is not used by any of them.

```bash
bun install
bun run dev              # run the bot from source (src/gekko2.ts)
bun run build:exec       # compile a standalone binary to dist/gekko2
bun run type:check       # tsc --noEmit, covers src/, test/ and scripts/
bun run lint:check       # eslint ./src          (bun run lint autofixes)
bun run format:check     # prettier over src/    (bun run format writes)
bun run test             # unit tests: vitest over src/**/*.test.ts and scripts/**/*.test.ts
bun run test src/utils/collection/ringBuffer.test.ts                       # one file
bun run test src/utils/collection/ringBuffer.test.ts -t "argument itself"  # one test, by name
bun run test:coverage    # what pre-push and CI run; fails below 80% lines/functions/branches/statements
bun run test:e2e         # test/e2e on Bun's own test runner (--isolate, a fresh global per file: their module mocks leak otherwise); not run by CI or hooks
bun run bench            # vitest benchmarks (src/**/*.bench.ts)
```

`bun test` without `run` is Bun's test runner, not vitest. Only `test/e2e` is written for it.

### Running the bot

There are no CLI flags, only two environment variables:

- `GEKKO_CONFIG_FILE_PATH`: the config file to load (`.yml`, `.yaml`, `.json` or `.json5`). Its `watch.mode` (`importer`, `backtest` or `realtime`) selects what runs.
- `GEKKO_LOG_LEVEL`: winston level (`error`, `warn`, `info`, `http`, `verbose`, `debug`, `silly`; case-insensitive, `warning` means `warn`). It defaults to `error`, so set `info` or `debug` to see anything. An unknown value falls back to `error` and says so once.

Bun loads `.env` and then `.env.local` (gitignored, takes precedence) automatically, so a bare `bun run dev` runs whatever config those files point at. A variable set on the command line wins over both:

```bash
GEKKO_CONFIG_FILE_PATH=./config/backtest.yml GEKKO_LOG_LEVEL=info bun run dev
```

A backtest replays 1-minute candles from SQLite and aborts if any minute of `watch.daterange` is missing, so the range has to be imported first (importer mode, e.g. `config/importer.yml`, writing to the gitignored `db/`). The importer only stores closed minutes: a `daterange.end` at or after the minute in progress is clamped to the last closed minute, with a warning. Writers (importer, realtime) create the database directory; a backtest opens the database read-only and refuses a missing file or a pair without a table. An import overwrites the stored candles of its range with the candles it reads from the exchange, so re-importing a range repairs the synthetic candles a realtime run's gap filler wrote there; a made-up candle never replaces a stored candle that traded, and a realtime run only replaces a stored candle that is itself made up.

Exit codes: 0 when a run ends normally or is stopped by `ApplicationStopError`, 1 after any other failure, 130 on SIGINT and 143 on SIGTERM (the storage buffer is flushed and closed, the plugins are not finalised). A run that ends normally still exits 1 if a promise rejection went unhandled along the way.

## Git workflow

- Commit messages must follow Conventional Commits. commitlint enforces it in the `commit-msg` hook and on pull requests: subject not capitalised, header at most 125 characters.
- `pre-commit` runs `type:check` and lint-staged (eslint --fix, prettier); `pre-push` runs `test:coverage`.
- Work lands on `development`. `main` only moves for releases: every push to `main` runs semantic-release, which writes `CHANGELOG.md`, writes the version it releases into `package.json` and rebuilds `dist/gekko2` from it (the prepare step of the repository's own plugin, `scripts/release/version.cjs`, which fails the release before anything is tagged if the build writes no `dist/gekko2`), commits both files to `main` (`chore(release): <version> [skip ci]`) and publishes the GitHub release with `dist/gekko2` attached under the stable name `gekko2`. So never bump a version or edit the changelog by hand. The executable prints the `package.json` version it was built with (`Gekko version: vX.Y.Z` at info level): a release prints its own, a build of `development` the last one merged back from `main`.
- semantic-release uses its default Angular preset. A breaking change needs a `BREAKING CHANGE:` footer; `feat!:` on its own releases nothing.
- CI runs on pushes and pull requests to `main` and `development`: `format:check`, `lint:check`, `type:check`, `test:coverage`, `build:exec`.

## Code conventions

- `console.*` is a lint error. Log through `debug`, `info`, `warning` and `error` from `@services/logger`, each taking `(tag, message)`; `tag` is a closed union in `src/models/tag.types.ts`. `debug` returns before winston formats anything when its level is off, so a debug line on the hot path costs nothing; a line at another level logged on every candle goes behind `isLevelEnabled(level)`, as `StrategyManager.log` does. A line that quotes a failure writes `describeError(err)` (`src/errors/error.utils.ts`): a `GekkoError`'s `untaggedMessage`, since the line has a tag of its own, any other Error's message, a string as it is, anything else as `util.inspect` writes it. Never `String(err)` or `${err}`: they write an object as `[object Object]`, and throw for one without a prototype from the very catch meant to report it. `toError(value)` there makes an Error of any thrown value. A message that counts writes its noun with `pluralize(word, count)` (`src/utils/string/string.utils.ts`), the plural for 0 too, rather than `minute(s)`.
- Unused parameters must be prefixed with `_`, a lint error otherwise. Import cycles are lint errors (`import/no-cycle` reads the `.ts` modules), and only a type-only import (`import type …`) breaks one: an import written as a value import counts even when it brings only types. A value cycle can throw `Cannot access … before initialization` under Bun, depending on which of its modules loads first (`movingAverages.const.ts` says how one was avoided). No lint rule finds a dead export (`import/no-unused-modules` checks nothing without options, and crashes under ESLint 10 with `unusedExports`): look for one with TypeScript's find-references. The `.cjs` files (the release and commitlint configurations, `scripts/release/version.cjs`) are linted as CommonJS with Node's globals, though `lint:check` covers `src/` only.
- Prettier: 140 columns, single quotes, trailing commas, no parentheses around a lone arrow parameter.
- The path aliases (`@constants`, `@models`, `@errors`, `@utils`, `@services`, `@indicators`, `@strategies`, `@plugins`) are declared in `tsconfig.json` and copied by hand into `vitest.config.ts`. A new alias goes in both.
- Files are named `<name>.<role>.ts` (`.types`, `.schema`, `.const`, `.error`, `.utils`, `.strategy`, `.indicator`, `.stream`, `.mock`, `.bench`). Coverage skips `.schema`, `.mock`, `.types`, `.error`, `.const`, `.bench` and `index.ts` files, and everything under `src/strategies/custom/` and `src/strategies/debug/`. `src/utils` has no barrel files; import `@utils/<dir>/<file>`.
- `lodash-es` (never `lodash`), `date-fns` and zod v4 are used throughout. Timestamps are epoch milliseconds, and a duration in milliseconds is written with `ONE_SECOND` and `ONE_MINUTE` (`@constants/time.const`). The realtime e2e flows mock that module to `{ ONE_SECOND: 1, ONE_MINUTE: 50 }`, so a constant added to it is undefined there unless their mocks add it too, and a duration that must stay real under that clock keeps a literal or a date-fns conversion, with a comment saying why (`Bot.listen`'s polling interval, `MIN_ANNUALIZATION_HORIZON_MS`). A minute is floored with `startOfMinuteUTC` (`src/utils/date/date.utils.ts`) and moved with `± ONE_MINUTE`, the clocks set on every bucket included (`start + ONE_MINUTE` in the Trader, the StrategyManager, the simulator and the analyzers: date-fns' `addMinutes` built a Date each time), a second is floored with `Math.floor(t / ONE_SECOND) * ONE_SECOND`, and a duration shown to the user is written with `formatDurationUTC(start, end)` (same file), on the UTC calendar. date-fns' `startOf…`, its `add…` and `differenceIn…` of days, weeks, months and years, and `intervalToDuration` count in the host's local time: on a host with daylight saving time, `startOfMinute` read every instant of the hour repeated when it ends an hour early, so a live stream pushed nothing for that hour, a duration across a change came out an hour off, and `intervalToDuration(…, { in: tz('UTC') })` of `@date-fns/tz` still moved a date whose UTC time the host's zone skips at its spring change ("1 day -1 hours"): no code imports `@date-fns/tz`.
- There is no decimal library: `round` (`src/utils/math/round.utils.ts`) rounds a number exactly as it is written, and `addPrecise` and `multiplyPrecise` (`src/utils/math/math.utils.ts`) add and multiply two numbers as they are written (0.3 − 0.1 is 0.2, 100.01 × 0.0004 is 0.040004), exactly up to 15 significant digits and as `a + b` or `a × b` from 17, for the amounts, prices, costs and fees that must come out as decimals. At 16 digits `addPrecise` gives the double nearest to the sum, which `String` can write a unit of its last decimal off, so that the next call adds to that neighbour and a change below an ulp can be lost (an 8-decimal balance from 67.1 M to 90 M units), and `multiplyPrecise` the binary product rounded to the decimals of the two, which can land a unit off the exact product, farther than `a × b` (a cost of 100,000 to a million, from an 8-decimal amount at a 2-decimal price). A quotient, which neither works out exactly (a mean, a fee rate, a percentage), goes through `toSignificantDigits` there: the double rounded to the 15 significant digits it keeps, a tie away from zero (0.06999999999999999 is 0.07); a reported return or drawdown works its change out with `addPrecise` first. They read the number's decimal string, a cost a per-candle loop should not pay: the candle batcher sums volumes with a scaled integer instead, and the analyzers' valuation (`calculatePairEquity`, `calculatePortfolioTotalValue` in `src/utils/portfolio/portfolio.utils.ts`) pays it once per timeframe candle, a few µs for each asset held, because the analyzers compare equities exactly. The simulator books the cost of an order to 8 decimals, as Binance keeps its balances (`BOOKED_CURRENCY_UNIT`, 10^-`COST_DECIMALS`, `src/constants/order.const.ts`), while an equity values a holding at amount × price, up to 5e-9 apart: the analyzers take two equities less than that unit apart for one amount, a round trip that ends so close to its entry equity (or within a billionth of it) breaking even, and the PortfolioAnalyzer's drawdowns and returns ignoring such a gap.
- Indicator results and other computed numbers are guarded with `isFiniteNumber` (lodash's `isNumber` accepts NaN), and two values equal in exact arithmetic but computed apart, such as a flat market's close and its SMA, are compared with `compareWithTolerance` (relative 1e-9), both in `src/utils/math/math.utils.ts`. TMA, SMACrossover and EMARibbon compare so, and CCI, Stochastic (StochasticRSI through it) and Bollinger Bands (OBV through them) decide a flat window so. `isFinitePositive` there is the one check of a finite number above 0: an order's price, amount and cost, a market's bound or step (`toBound` in `src/utils/market/market.utils.ts` reads a limit or a step so). Steps and ticks are applied by `roundToStep` and `getPriceTick` (`src/utils/market/precision.utils.ts`), which the simulator, GridBot and the PositionTracker share: an amount truncated to its step, whatever the step, a price rounded half up to the tick at that price. A message that quotes a value beside a bound writes it with `formatEveryDecimal` (`src/utils/string/string.utils.ts`): every decimal `String` gives it, without an exponent, where `formatAmount` (for a person, thousands grouped) and `toPlainNumber` (for a CSV cell) round to 8 decimals. A percentage shown to the user is written with `formatPercent(value, rounding)` (same file), the rounding taken from `PERCENT_ROUNDING` (`src/plugins/analyzers/analyzer.const.ts`), one entry per figure, so that the CSV, the console tables and Telegram write a figure alike.
- `ORDER_SIDES` and `ORDER_TYPES` (`src/constants/order.const.ts`) are the one list of order sides and types: `OrderSide` and `OrderType` derive from them, and a new type does not compile until the Trader's `ORDER_FACTORY` has a class for it.
- `TIMEFRAME_TO_MINUTES` (`src/constants/timeframe.const.ts`) is the one list of timeframes: `TIMEFRAMES` (`src/services/configuration/configuration.const.ts`) and `CandleSize` (`src/services/core/batcher/candleBatcher/candleBatcher.types.ts`) derive from it. Its months and years are nominal (30 days a month), while those candles span whole UTC months: a timeframe in any unit but minutes, hours, days or weeks does not compile until `MONTHS_PER_CANDLE` (same file) gives its months, a divisor of 12, and any other size until it has a case in the exhaustive switch of `getCandleTimeOffset` (`src/utils/candle/candle.utils.ts`). `getCandleStart` and the batcher's `isTimeframeCandleClose` (`fastCandleBatcher.ts`: the offset of the next minute is 0) read that one calendar, so the warmup and backtest windows and the timeframe candles share their boundaries.
- `INPUT_SOURCES` (`src/indicators/indicator.const.ts`) is the one list of price sources: `InputSources`, `checkInputSource` and the strategies' `src` parameter (`inputSourceSchema`, `src/models/schema/inputSource.schema.ts`) derive from it, so a source added there is typed, checked and offered by RSI, TMA, SMACrossover and EMARibbon at once. A new strategy with a `src` takes `inputSourceSchema.default('close')`.

## Architecture

### Boot and pipeline

`src/gekko2.ts` calls `gekkoPipeline()` (`src/services/core/pipeline/pipeline.ts`), which threads the configured plugin list through a fixed sequence of steps: the backtest's check that the database holds every minute of `watch.daterange`, read each plugin class's static configuration, mode compatibility, per-plugin zod parse, dependency and duplicate-emitter checks, a warning when a plugin creates orders that no plugin executes (a TradingAdvisor without a Trader), `exchange.loadMarkets()`, instantiate, wire events, inject services, then launch the stream pipeline for the mode.

Two module-level singletons sit under everything:

- `config` (`src/services/configuration/configuration.ts`) reads the config file and validates it with zod at import time, and throws if `GEKKO_CONFIG_FILE_PATH` is unset. `configuration.schema.ts` is the source of truth for the config shape. Every section is a `z.strictObject` except the `strategy` block and the `plugins[]` entries, which the plugin's own strict schema parses, so an unknown key anywhere (a misspelt `sandbox`, say) refuses the file. A YAML file is loaded with js-yaml's core schema, so an unquoted timestamp stays text, like a quoted one, for the schema to check (merge keys `<<` and js-yaml's `!!timestamp`, `!!set`… tags are not supported). A `watch.daterange` bound is a day (`2024-01-01`, its midnight UTC) or a day and a time with `Z` or an offset (`2024-01-01T00:00:00Z`, `2024-01-01T02:00:00+02:00`), checked against the calendar: `2023-02-29`, `24:00` or a `+25:00` offset is refused rather than rolled over to another day. The range must end in the minute of its start or later, in every mode; both minutes are read, so equal bounds are one minute. Assets, the currency and symbols are written in upper case: Latin capitals, digits or the letters of a script without case, a symbol being two of them around one slash (`pairConfig.schema.ts`). A list read into a Map by a key (`simulationBalance` by `assetName`, `marketData` and `initialTicker` by `symbol`) refuses a repeated key (`refuseRepeatedKeys`, `exchange.schema.ts`), and every `simulationBalance` asset must be a watched asset or the currency. An invalid file is a one-line `GekkoError` naming the file and listing every issue with its path; an invalid plugin entry is reported the same way, with the plugin's name and index.
- `inject` (`src/services/injecter/injecter.ts`) lazily creates and memoises the `exchange()` and `storage()` instances that streams, orders and plugins share. `closeStorage()` closes the storage only if one was created.

`src/gekko2.ts` imports the configuration, the injecter and the pipeline dynamically inside the `try` of `main()`, so that a configuration error is reported like any other failure; a static import that loads `config` would throw before the handlers exist, so do not add one. It is also the only place that reports a fatal error and decides the exit code. Its `catch` and its process-level handlers share one formatter: a `GekkoError` is logged as its one-line message (stack at debug level), anything else with its name, message and stack, and causes are appended. A wrapper passes the failure it wraps as `{ cause }` (`GekkoError(tag, message, options?)` takes `ErrorOptions`, and keeps `tag` and `untaggedMessage` beside its tagged `message`), and the report appends each cause in full (`Caused by: <its stack>`), as for the SQLite open failure or a plugin dependency that fails to load. An `uncaughtException` is logged and exits 1 at once, without finalising the plugins; `Heart` failing to tick after the machine slept is no longer one: it emits `'error'`, the realtime stream destroys itself with it and the pipeline rejects, so the plugins are finalised. An `unhandledRejection` is logged and sets the exit code to 1 but does not stop the bot, because timer-driven tasks float promises that reject on a network blip.

### Candle streams

Data moves as 1-minute `CandleBucket`s (`Map<TradingPair, Candle>`, one candle for every watched pair) through Node object-mode streams assembled in `src/services/core/pipeline/pipeline.utils.ts`:

| Mode     | Chain                                                                                                                                                                                                     |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| realtime | warmup history, then live per-pair streams synchronised by timestamp → RejectFutureCandle → RejectDuplicateCandle → FillCandleGap (drops the leading buckets that miss a pair never seen) → PluginsStream |
| backtest | SQLite reader → PluginsStream                                                                                                                                                                             |
| importer | exchange OHLCV history → RejectFutureCandle → FillCandleGap → PluginsStream                                                                                                                               |

A history range (`HistoricalCandleStream`) is inclusive on both ends, so equal bounds mean one minute. The realtime pipeline reads the clock once: the warmup history runs from the start of the candle `warmup.candleCount` candles before the one in progress (`getCandleStart`, on calendar boundaries for `1M`, `3M`, `6M` and `1y`) to the minute before the one in progress, and the live streams start at the minute in progress, so the two ranges neither overlap nor leave a gap. `HistoricalCandleStream` pulls one page per `_read` with `tickrate` as the minimum interval between requests; an empty page after some data ends the history with a warning. A live stream ticks on each minute boundary plus `REALTIME_GRACE_PERIOD` (`src/constants/realtime.const.ts`), asks for every closed minute since the last one it pushed, oldest first (a failed fetch is retried on the next tick, never pushed as a made-up candle, and a late tick catches up instead of skipping a minute), ignores the minute in progress, and destroys itself with a `GekkoError` after `REALTIME_MAX_TICKS_WITHOUT_CANDLE` minutes without a candle, so a pair that stops delivering stops the bot instead of freezing it. `FillCandleGap` fills a missing minute with a flat candle marked `synthetic`, refuses a gap longer than `MAX_GAP_FILL_MINUTES`, and in realtime drops the leading buckets that lack a pair it has never seen a candle for (one warning per such pair at the first drop, one summary at the first minute pushed), so the plugins only ever get complete buckets; the importer lets such buckets through. `pipeline.utils.ts` makes the three pipelines reject with the error of the failed bucket rather than with an upstream one. In every mode the per-pair streams are merged by `synchronizeStreams` (`src/utils/stream/stream.utils.ts`), each bucket holding the pairs in the order of `watch.assets`: a pair's stream that ends lets the others go on, one that fails fails the pipeline with its error, and one that closes without ending, or delivers a candle whose start is not a finite number, fails it with a `GekkoError` naming the pair, rather than leave the pair out of the buckets (in realtime, filled with flat candles forever) or stall them.

Aggregation to `watch.timeframe` is not a stream stage. It happens inside the TradingAdvisor plugin (`CandleBucketBatcher`), which throws a `GekkoError` if a bucket misses a watched pair, mixes minutes or does not follow the previous bucket by one minute, and which skips the minutes before the first timeframe boundary (with a warning) rather than emitting a partial first candle.

For every bucket, `PluginsStream` (`src/services/core/stream/plugins.stream.ts`) does three things in order: the simulated exchange, if one is configured, consumes the bucket and fills orders; every plugin's `processOneMinuteBucket` runs concurrently; then the deferred events are flushed plugin by plugin, in config order, a plugin with nothing queued skipped (`hasDeferredEvents()`; in backtest the Trader counts its reports in flight as queued).

### Plugins (`src/plugins`)

A plugin extends `Plugin`, implements `processInit`, `processOneMinuteBucket` and `processFinalize`, and exposes a static `getStaticConfiguration()` returning `{ name, schema, modes, dependencies, inject, eventsHandlers, eventsEmitted }`. `tradingAdvisor/tradingAdvisor.ts` is a good reference.

- Registry: the exports of `plugins/index.ts`. `plugins[].name` in the config must equal the exported class name exactly; an unknown name is refused with the list of valid names. The entry is parsed by the plugin's zod `schema` (a `z.strictObject`: a misspelt or retired option is an error, not a silent default) and the result is the constructor argument.
- Wiring is by name: an emitted event `orderCompleted` is bound to the `onOrderCompleted` method of every plugin that has one. Handlers are discovered on the prototype, so they must be methods, not arrow-function properties. Event names live in `src/constants/event.const.ts`, payload types in `src/models/event.types.ts`.
- An event can have only one emitting plugin. `PortfolioAnalyzer` and `RoundTripAnalyzer` both emit `performanceReport`, so they cannot be configured together.
- `processFinalize(failure?)` receives the error that stops a run before its end (a crash, `MissingCandlesError`, the circuit breaker): the analyzers then set `interruption` on their `performanceReport`, and `PerformanceReporter` writes it in the `status` column of its CSV rows (`completed` otherwise). `Supervision`'s `candle_check` subscription also alerts on Telegram when no 1-minute bucket came for `candleStaleThreshold`.
- Delivery is deferred: plugins queue events with `addDeferredEmit(name, payload)` and handlers receive an array of payloads when the queue is flushed after the bucket, each handler its own copy, so that one writing to it changes nothing for the others. The payload is copied when queued, by `copyPayload` (`src/utils/event/event.utils.ts`), which copies plain data by hand and anything else with `structuredClone`, and refuses what `structuredClone` refuses, a function or a symbol (a `DataCloneError`). The payload of an event nobody listens to is queued uncopied: a listener added before its delivery would get a copy made then, which never happens in a run, the pipeline wiring every listener before the stream starts. A listener added during an emit or a delivery is called from the next one on. Nothing is flushed after `processFinalize`, so events sent from there use `emit` directly and carry a single payload, the same object for every listener, not a copy. The analyzers await that emit: a listener that fails is logged at error level (`A listener failed on the performance report: …`) and the run ends as it would have. The one exception is a strategy's error line: `tools.log('error', …)` fails the bucket, whose deferred events are then dropped, so the TradingAdvisor emits that `strategyInfo` at once, as an array of one.
- Config order matters. The flush is one pass over the plugins in config order, so an event queued on a plugin that was already flushed is delivered with the next bucket, one minute later. Keep `TradingAdvisor`, then `Trader`, then analyzers and reporters.
- Order reports are asynchronous (the order classes settle through callbacks or polls). In backtest the Trader waits for its pending reports before its queue is flushed and again in `processFinalize`, so a fill reaches the strategy and the analyzers in the bucket it happened in, the last one included. In realtime they float and arrive with a later bucket.
- Services named in `inject` (`exchange`, `storage`) are set after construction: use `getExchange()`/`getStorage()` from `processInit` onwards, not in the constructor.
- Modes: TradingAdvisor, Trader, PortfolioAnalyzer and RoundTripAnalyzer run in realtime and backtest; PerformanceReporter in backtest only; CandleWriter in realtime and importer; EventSubscriber and Supervision (both Telegram) in realtime only. Both take an optional `chatId` (`0` is refused); without it the bot warns at start-up, drops what was queued while Gekko was down, binds itself to the first chat that sends it a command from then on (logged at info with whose chat it is) and never rebinds, and anything sent before that is dropped. Each bot needs its own token (two pollers on one token get 409s).

The trading loop for one bucket: TradingAdvisor builds the timeframe candle and calls the strategy → `strategyCreateOrder` → Trader creates a `MARKET`, `LIMIT` or `STICKY` order (`src/services/core/order`) → `orderInitiated`, later one of `orderCompleted` / `orderCanceled` / `orderErrored`, plus `portfolioChange` → back into the strategy's order hooks and into the analyzers → `roundtripCompleted`, `performanceReport`. Strategies track their pending orders through those three terminal events, so every order has to end in one of them. Only the Trader emits them: with a TradingAdvisor and no Trader (a screener), no order ever ends, and a strategy that waits for its order to end before it advises again, as the built-in ones do, advises once per run. The pipeline warns about it at start-up (one `warn` line, hidden at the default `error` level) rather than refuse, since a strategy that never creates orders needs no Trader; a screener runs the Trader on `paper-binance`. `orderErrored` carries `filled` and `mayBeLive`, whether the order may still be live on the exchange, where Gekko follows it no more; `orderCanceled` carries the cumulative fill and what was left, both undefined when the exchange reported no fill (unknown, not 0).

`ApplicationStopError` is the graceful stop (the circuit breaker): plugins are finalised, the reason is logged at error level and the process exits with code 0, so that a restart-on-failure supervisor leaves it stopped. `ApplicationStopError(tag, message)` takes its thrower's tag, as every `GekkoError` does: the breaker's stop reads `[STRATEGY] Max consecutive order errors reached (5)`. Any other exception thrown by a plugin or a handler finalises the plugins and ends the process with exit code 1. `PluginsStream` destroys itself with the error it caught, which is how `main` tells the two apart, and it also finalises the plugins that were initialised when a stream upstream fails. When several plugins fail on the same bucket, an `ApplicationStopError` is the failure reported, otherwise the first in config order, and the others are logged after the close reason. SIGINT and SIGTERM flush and close the storage, then exit with 130 or 143 without running `processFinalize`.

### Strategies (`src/strategies`)

A strategy is a plain class, constructed without arguments, that implements any of the optional hooks of `Strategy<Params>` (`strategy.types.ts`, whose JSDoc gives the contract of every hook and tool). `StrategyManager` drives it. Model a new one on an existing strategy such as `dema/`, or on the Complete Example of `documentation/custom-strategies.md`, whose TypeScript examples type-check again.

- `init` runs once, on the first one-minute bucket, before any timeframe candle: in realtime the first minute of the warmup history, in a backtest the first minute of `watch.daterange`. Its `candle` holds that minute's candle of every watched pair, in the order of `watch.assets`. It is the only place `addIndicator(name, symbol, params)` is available: called once `init` has returned, it throws a `GekkoError`. It throws one too for an unknown indicator, an unwatched pair or a parameter the indicator refuses, so such a mistake stops the bot at start-up. Then on each timeframe candle: indicators update, `onEachTimeframeCandle`, then once warmup is over `log` and `onTimeframeCandleAfterWarmup`.
- `init` also gets `openOrders`, the orders open on each watched pair at start-up, which the TradingAdvisor's `processInit` reads with one `fetchOpenOrders` per pair (a failed read fails the start-up). The map is empty in backtest and paper trading, whose simulator starts empty, and the run does not follow those orders: the Trader follows only the orders of this run.
- Hooks get `candle` as a `Map` holding every watched pair, followed by one `{ results, symbol }` argument per indicator in `addIndicator` order. Results are typed `unknown`: `null` until the indicator has enough data, then complete on every candle (a number, or an object whose fields are all set), so one `=== null` check suffices. ROC and TRIX are the exception: `null` again on a candle whose base is 0. `watch.warmup.candleCount` counts timeframe candles and is unrelated to indicator periods, so always null-check.
- What a hook receives is the strategy's own copy (the candles, the indicator results, the portfolio, an order hook's event, a trailing stop's state, `openOrders`, `tools.strategyParams`, `tools.marketData`): writing to it changes nothing elsewhere.
- Realtime prefetches the warmup candles from the exchange. A backtest spends the first `candleCount` candles of its `daterange` on warmup, and the configuration refuses a backtest with a TradingAdvisor whose range holds no more whole timeframe candles than that.
- `tools.createOrder()` returns a UUID immediately; the outcome arrives later through `onOrderCompleted`, `onOrderCanceled` or `onOrderErrored`. The order is dated with the end of the minute being processed. Omitting `amount` means all-in. It throws a `GekkoError`, which stops the bot, before it draws an id or relays anything: during the warmup (so always from `init`), for a key `StrategyOrder` does not declare (`ORDER_KEYS` in `strategyManager.ts`, checked before the pair whatever its value: the Trader ignored it, so a misspelt `price` made a LIMIT at the last price and a `quantity` an all-in order), for a pair that is not watched (a key of `tools.marketData`), a `side` or `type` outside `ORDER_SIDES`/`ORDER_TYPES` (ccxt's lower-case `'buy'` and `'market'` among them), an `amount` or `price` given that is not a finite number above 0, or an invalid `trailing`.
- `trailing` applies to BUY orders only: a `percentage` in (0, 100), an optional `trigger` above 0, no other key. The stop is armed, from a copy `createOrder` took, when the BUY completes. A BUY that errors gets it for the fill the exchange reported, if any, with a warning either way, and a BUY canceled loses it, even after a partial fill. It trails each one-minute candle met as open, low, high, close, each price tested against the stop price before it raises the peak. `onTrailingStopActivated` fires when a high reaches `trigger` (at arming when there is none). When a price reaches the stop price, `StrategyManager` sends a MARKET SELL and hands its id to `onTrailingStopTriggered`: an order of the strategy's own from then on, to adopt as its pending SELL (`PositionTracker.adoptSell`). Both trailing hooks get `tools` last.
- A triggered stop sells until its SELL ends. Completed for all of the stop's amount, the stop is over. Completed for less (the Trader caps every SELL to the free balance and to the market's one-order maximum, and the exchange truncates its amount to the step), errored or canceled, it is active again for the rest, from the peak and the stop price it triggered at, with a warning, also when the SELL errored while it may still be live (`mayBeLive`). It is over instead, said at info level, when that rest is too little to sell at the market's minimums (`isSellable`), whatever else the account holds and even when that SELL may still be live. It is over too when the portfolio after that SELL shows too little of the asset free to sell, while no SELL the strategy created pends on the pair (at info level after a completed SELL, with a warning after an errored or canceled one): that is how a stop ends whose SELL went through after all, or whose BUY's fee was taken in the base asset (`Strategy.onTrailingStopTriggered` has the details). A SELL the strategy created holds the stops of its pair while it pends (they trail but do not trigger), cancels them all once it completes, and releases them when it is canceled or errors.
- The Trader caps every SELL to the free balance it last read less what the SELLs it placed since take from it, with a warning, and sizes an all-in SELL from that remainder, so that neither a live fee taken in the base asset nor two SELLs of one asset between two balance reads (two stops on one minute, a stop's and the strategy's) get a SELL refused. It sizes an all-in BUY the same way, from the currency it last read less what the BUYs it placed since may spend (each its cost at its price plus the 5 % fee buffer, an all-in BUY all it was sized from), with a warning, so that two all-in BUYs between two balance reads (two entry signals on one candle, two pairs of one currency), or a BUY then an all-in BUY, are not both sized from the whole currency: the second gets what is left, 0 once nothing is, which the market limits refuse. It also caps every SELL, the trailing stop's included, and every all-in BUY at the most the market takes in one order of its type (`amount.max`, narrowed for a MARKET order by `market.max`, Binance's MARKET_LOT_SIZE: see `getMarketOrderLimits`), with one warning naming the amount asked for and the maximum sent: the rest stays held, or unspent, for a later order, and the completed event carries the amount executed. A BUY with an amount is never capped: above the maximum, the exchange refuses it. An all-in order sized from nothing is warned of before the exchange refuses its amount of 0, with the cause: no balance read yet, none of the asset (or currency) free at the last synchronization, or, for a SELL, the SELLs placed since taking what was.
- `tools.log` prints a line if `GEKKO_LOG_LEVEL` lets it through. `info`, `warn` and `error` lines are also relayed as `strategyInfo` (the EventSubscriber's `strat_info`) whatever the level, `debug` lines never. `tools.log('error', …)` relays the line, then throws a `GekkoError`: it is not just a log call. An unknown level is logged and relayed at `info`, after one warning. A message that is not a string (an untyped strategy) is logged, relayed and thrown as `util.inspect` writes it, two levels deep, on one line but for an Error's stack.
- `end(interruption?)` runs once at the end of the run, also when an error stops it (not on SIGINT, SIGTERM or an uncaught exception): `interruption` is then that error's message.
- `maxConsecutiveErrors` consecutive `orderErrored` events (a TradingAdvisor option, default 5, `-1` disables, `0` is refused) raise `ApplicationStopError` (`[STRATEGY] Max consecutive order errors reached (5)`), once the strategy's `onOrderErrored` has run for the last one. Every errored order counts, GridBot's grid orders included; a completed or canceled one resets the count.
- The class is chosen by the TradingAdvisor plugin's `strategyName`: the exported class name in `strategies/index.ts`, or with `strategyPath` a named export of an external file. The top-level `strategy:` block holds its parameters; its `name` selects nothing but labels the run (backtest log, PerformanceReporter rows), so the schema requires it to equal `strategyName`. A strategy class may declare a static zod `schema` (`StrategyConstructor` in `strategy.types.ts`): `StrategyManager` parses the block with it, `name` removed, when the strategy is created, before any candle, refuses the run with a `GekkoError` listing every issue, and hands the strategy the schema's output (defaults applied, no `name`) as `tools.strategyParams`. Every built-in strategy and debug fixture declares one; without a schema the whole block, `name` included, is passed through unvalidated, so a misspelt parameter is silently `undefined`.
- A `strategyPath` file can import only types from Gekko (Bun drops type-only imports): the compiled executable resolves no `@…` alias in a file it loads at run time, `bun run dev` resolves them only inside the checkout, and the executable finds a package only through the `index.js` at its root (`zod` yes, `lodash-es` no). A strategy that needs Gekko modules, such as `PositionTracker`, lives in `src/strategies/custom/` (custom-strategies.md, "Where Your Strategy Lives").
- The built-in strategies are the seven signal strategies (CCI, DEMA, EMARibbon, MACD, RSI, SMACrossover, TMA) and GridBot. Each trades the first pair of `watch.assets` only: `init` takes it with `pickTradedPair(candle, tools)` (`src/strategies/positionTracker.ts`), which warns once when more pairs are watched.
- The seven signal strategies keep their position in a `PositionTracker`: they buy only when flat and sell only when long (`canBuy()`/`canSell()`), never while an order of their own is pending, place their orders through `position.buy`/`position.sell(createOrder, order)` and hand it the params of their three order hooks whole. A completed BUY makes the tracker long, and a completed SELL flat once it sold all it asked for; one that sold less (the Trader's caps), and every all-in or adopted SELL, is read from the portfolio after it, long when the asset left free is enough to sell, said at info level. An order of theirs that ends canceled or errored may have executed: the tracker then reads the position from the fill the cancelation reports, else from the free balance of the asset in the portfolio after it, long when that is enough to sell at the market's minimums, and logs a change at info. They start flat, so a holding present at start-up is sold only once a BUY of theirs has ended, completed, or refused or canceled while the account held enough to sell. Gekko 1 discarded a repeated same-side advice; Gekko 2 relays every advice, so a strategy without that tracking re-advises an all-in BUY on every candle of a trend until the refusals trip the breaker.
- What a strategy compares with the previous candle (EMARibbon's spread, SMACrossover's side of the SMA) is recorded in `onEachTimeframeCandle`, which runs on the warmup candles too, so the first candle after the warmup is compared with the last warmup candle.
- GridBot keeps a grid of LIMIT orders in memory instead of a position. Every level trades one quantity: the largest amount on the market's amount step that the free balances fund on each side, the need worked out in decimal. Each level re-arms through the three order events: a fill places the opposite order one step away, a refused or canceled order is placed again up to `retryOnError` times, and an order that may still be live is never placed again. It refuses to start while orders are open on its pair, and its lowest-buy and price-tick checks run when the grid starts and again around the price a rebalance ended at.
- `src/strategies/debug/` holds e2e fixtures, not built-in strategies: `DebugAdvice`, `DebugBacktest`, `DebugRealtime` and `DebugTrailingStop`. `strategies/index.ts` exports them and `config/realtime-screener.yml` and `realtime-supervision.yml` select `DebugAdvice`, but they order a fixed amount (1) on a fixed calendar of candles, counted from 0 after the warmup, and track no position: a SELL may be advised with nothing held, refused and counted towards the breaker. The e2e flows depend on their calendars, so change both together.
- A new built-in strategy is `strategies/<x>/<x>.strategy.ts`, `<x>.schema.ts` (its static `schema`), `<x>.types.ts` and `<x>.test.ts`, plus an export in `strategies/index.ts`. An all-in one keeps a `PositionTracker`.

`src/strategies/custom/` holds private, local-only strategies. The directory is gitignored except for a tracked placeholder `index.ts`, which the `preinstall` script marks `assume-unchanged` so local edits never show up in git. Never stage or commit anything from it. Tests in it run with a local `bun run test` but not in CI.

### Indicators (`src/indicators`)

An indicator extends `Indicator<Name>` (`indicator.ts`): it implements `onNewCandle`, which sets the inherited `result` that `getResult` returns, `null` until the output is complete, then complete on every candle, never a partial object or a placeholder (ROC and TRIX aside, `null` on a zero base). It declares its types by augmenting the global `IndicatorRegistry` interface in its `<x>.types.ts` with `{ input, output }`. The registry key, the class name and the export in `indicators/index.ts` must be identical, because the runtime lookup is `indicators[name]`.

- A constructor checks its parameters before it builds anything, with the helpers of `indicator.utils.ts` (`checkInteger`, `checkNumber`, `checkOneOf`, `checkInputSource`, `checkBelow`, `checkAtMost`), each throwing a `GekkoError` that names the indicator, the parameter and what it accepts. An indicator built on others checks its own parameters first, so that the message names the one the strategy passed. An indicator with a `src` reads its price through `getInputSource(src)` (`indicator.utils.ts`), the close by default.
- A moving average extends `MovingAverage<Name>` (`movingAverages/movingAverage.ts`): it checks its parameters, passes `src` to `super` and implements `update(value)`, which the inherited `onNewCandle` calls with the candle's price. An indicator built on another feeds it its own values through `update`, never a made-up candle.
- A moving-average kind that indicators take as a `maType` is added to `MOVING_AVERAGES` (`movingAverages/movingAverages.const.ts`) and nowhere else: `MOVING_AVERAGE_TYPES`, `MovingAverageTypes` and `MovingAverageClasses` derive from it, and its `satisfies` admits only a `MovingAverage` built from `{ period }`. No moving average may import that file, even through `indicator.const.ts`: the cycle would make the moving average loaded first throw "Cannot access … before initialization" under Bun, and leave it missing from the map under vitest.
- +DM, −DM, +DI, −DI and DX read one `DirectionalMovement` (`directionalMovement/directionalMovement.ts`), whose true range is `getTrueRange` (`volatility/trueRange/trueRange.utils.ts`), as TrueRange's is. These helpers, like `MovingAverage`, are not exported by `indicators/index.ts`, so they are not `addIndicator` names.
- `RingBuffer` (`@utils/collection/ringBuffer`), the window of ROC, Williams %R, CCI, Stochastic and Bollinger Bands, is read in place: `first` in constant time, `max`, `min`, `sum` and `reduce` in one pass (`sum` and `reduce` oldest first), and its constructor refuses a size that is not a whole number of at least 1 with a `GekkoError`. A callback that needs a value of its caller goes through `reduce`'s `argument`, made once, rather than a closure made on every candle.

### Exchanges, orders and storage

- `exchange.name` picks the implementation, through a zod discriminated union and a switch in the injecter: `binance` and `hyperliquid` use `CCXTExchange` (`sandbox: true` for testnets; the hyperliquid client is created with `builderFee: false`, otherwise ccxt signs a builder-fee approval at the first order and attaches a 1 bp fee to every one); `dummy-cex` is `DummyCentralizedExchange`, the backtest simulator; `paper-binance` trades simulated orders on live Binance data. A new CCXT exchange needs its schema, a union entry, an injecter case and a `LIMITS` entry in `src/services/exchange/exchange.const.ts`, and ccxt must list every feature of `BROKER_MANDATORY_FEATURES` there in its `has`, which `checkMandatoryFeatures` checks as `CCXTExchange` is built. `fetchOpenOrders` is one of them: `fetchOpenOrders(symbol)` lists the orders open on a pair, whoever placed them (ccxt's live, the simulator's book in backtest and paper trading). `fetchMyTrades` leaves out, with one warning, a ccxt trade without an amount and a price above 0 (`isExecutedTrade`): read as 0, an unknown price entered the mean price of its order.
- The schema ties the exchange to the mode: backtest takes `dummy-cex` only, importer takes `binance` or `hyperliquid`, realtime takes `binance`, `hyperliquid` or `paper-binance`.
- The simulator's clock is the close of the last candle. It keeps one order book per pair. Limit orders fill in full once a candle's low/high reaches their price, market orders fill at the last close, and there are no partial fills or slippage. Fees and order limits come from `exchange.marketData`, which must hold exactly one entry per watched pair. Its `precision` is given as a number of decimals (`8`) that the schema converts to a step (`1e-8`), because `MarketData.precision` holds steps everywhere else, as ccxt reports them; an optional `precision.priceSignificantDigits` (Hyperliquid's 5) is handed on as it is. Before it checks the limits, the simulator puts an order on the steps of the market as `CCXTExchange` sends it (`roundToMarketPrecision`, `dummyCentralizedExchange.utils.ts`, on `roundToStep` and `getPriceTick`): the amount truncated to the amount step, the price rounded half up to the tick at that price. An amount truncated to 0, or whose cost falls under `cost.min`, is refused, the cost worked out in decimal (`multiplyPrecise`) by `assertOrderWithinLimits`, as both exchanges check it, so that an order costing exactly `cost.min` passes. An amount or a price rounded to nothing is refused as the order asked for it, with the step (`Order 'amount' with value 0.0000099 rounds to 0 on the amount step 0.00001 of the market. …`). An order fills, and is reported, for the amount truncated. The simulator charges the fee in the currency, on top of a BUY and out of a SELL's proceeds, works out the currency of each order in decimal (amount × price × (1 ± fee), `multiplyPrecise`) and rounds it to 8 decimals (`COST_DECIMALS`), a half up, as Binance keeps its balances, and books every balance in decimal (`addPrecise`). Its refusal for want of funds names both figures with every decimal (`Insufficient asset balance (portfolio: 0.0000005, amount: 1)`). Its state sits behind an `AsyncMutex` (`src/utils/async/asyncMutex.ts`), FIFO and not reentrant: a free lock runs the section at once, in the caller's tick, and an exchange call made by an `onSettled` callback runs once the bucket is processed. `MarketData.market`, when present (Binance `MARKET_LOT_SIZE`), narrows the amount range of MARKET orders; `CCXTExchange` and the simulator refuse such an order before sending it.
- Order classes are event emitters. In backtest they settle through exchange callbacks; in realtime, paper trading included, they poll `fetchOrder` every `orderSynchInterval`. A creation is sent once and never replayed. One whose outcome is unknown ends the order in error with `mayBeLive` true, never as a refusal: lost on the network (`ExchangeNetworkError`), or `OrderOutcomeUnknown` when the exchange answered without anything to follow the order by, its state could not be read back, or ccxt threw an `OperationFailed` that is not a `NetworkError` (Binance -1000, -1006, a busy exchange). So does an order whose poll, cancelation or read-back fails for good while it is open. The reads of `CCXTExchange`, unlike its creations and cancelations, go through `retry`: after a ccxt NetworkError a read is sent again up to 3 more times, 1000, 1585 and 2000 ms apart (`getRetryDelay`, attempts numbered from 0 as the fetcher numbers its requests), each failure logged at debug level only, since the caller logs what it could not read at the level it deserves.
- Trader on a real, non-sandbox exchange is refused unless the config sets `'I understand that Gekko only automates MY OWN trading strategies': true`.
- Storage is `SQLiteStorage` on `bun:sqlite`, the only Bun-specific API in `src/`. It keeps one table of 1-minute candles per pair (`CANDLES_<ASSET>_<CURRENCY>`, upper-cased and always quoted in SQL, so tickers such as `1INCH` work), and `storage.database` is a path relative to the working directory. The `storage` section is required in backtest mode and whenever a `CandleWriter` plugin is configured, and ignored otherwise; `insertThreshold` is an integer number of minutes between 1 and 1440 (default 1 in realtime, 1000 otherwise) and `watch.batchSize` is bounded to 31 days of minutes. What replaces a stored minute depends on the mode and on the candle: an import replaces whatever is stored for the minutes the exchange returns, a minute without trades included, and its own made-up candle for a minute the exchange lacks only replaces a stored candle that is made up too (flat, volume 0); the other modes replace a stored candle only when it is made up, and only with a candle that traded, so a made-up candle never replaces one that traded.

## Testing

- Unit tests are colocated `*.test.ts` files. Vitest runs them under Node, not Bun, so anything importing `bun:sqlite` has to be mocked. There are no globals: import `describe`, `it`, `expect` and `vi` from `vitest`.
- Because `config` is built at import time, tests mock `@services/configuration/configuration` (`{ config }`), usually together with `@services/logger` and `@services/injecter/injecter`. Use `vi.hoisted` for values the mock factories refer to.
- `mockReset: true` and `restoreMocks: true` are set globally and both run before each test, ahead of the `beforeEach` hooks. `mockReset` resets every mock: an implementation passed as `vi.fn(impl)` survives, anything chained afterwards (`.mockReturnValue`, `.mockImplementation`), at module scope or inside a `vi.mock` factory, is wiped. `restoreMocks` puts the original back in place of every `vi.spyOn` spy and detaches the spy; it leaves `vi.fn()`, `vi.mock` factories and automocks alone. So set return values in `beforeEach`, create spies in `beforeEach` or in the test itself, never at module scope, in a `describe` body or in `beforeAll` (a detached spy passes `not.toHaveBeenCalled()` without testing anything), and do not call `vi.clearAllMocks()`.
- `src/gekko2.ts` runs `await main()` when it is imported, and `instanceof` checks break across `vi.resetModules()`. Its test resets the modules, imports the file dynamically in each test, and imports the error classes dynamically after the reset.
- A mock that gets called with `new` must be `vi.fn(function () { … })`; an arrow function throws.
- Time code that local time could change is tested with the zone forced: `useTimeZone('Europe/Paris')` (`src/utils/date/date.mock.ts`) in the describe block sets `process.env.TZ`, which Node reads again when assigned, so that the test also fails on a UTC machine (CI).
- `scripts/release/version.test.ts` runs `bun` once (the plugin's default build runner, on a stub `build:exec` script in a temporary directory), so `bun` must be on the PATH vitest runs with.
- Indicator tests push an ordered `it.each` table through one stateful instance. Rows depend on the ones before them, so a single row cannot be run alone. A row asserts its result with `expect(result).toEqual(approximately(expected, digits))` from `src/indicators/indicator.mock.ts`: a `null` cell matches null only, and an object or an array is compared field by field. `digits` is the largest count whose tolerance, 10^-digits / 2, spans 16 ulps of the largest magnitude the table works at, its values or the prices they come from: 12 from 16 to 256, 11 up to 2048, 10 up to 16384, 9 up to 262144 (13 is bit equality from 256 on). Never use `toBeCloseTo` on a result: it reads null as 0. The same file holds `illiquidCandles` (gaps, ties, candles without range or volume) and `resultsOf(indicator, candles)`.
- Strategy suites stand `OrderRecorder` (`src/strategies/positionTracker.mock.ts`) in for `tools.createOrder`: it records each order exactly as the strategy created it, an all-in order without `amount`, so assert orders with `toStrictEqual`. `playSteps` plays candles and order outcomes. Play the `null` an indicator returns until it is ready inside a trend, not only as a single candle, and build only results the indicator can produce (a ribbon's spread from its EMAs, a MACD `hist` equal to `macd − signal`): a free value can make a row pass that no run reaches.
- House rules, from `.agent/skills/unit-test-craftsman/SKILL.md`: tagged-template `it.each` tables for repetitive cases; one `expect` per `it`; cover every branch of the file under test (the enforced floor is 80% overall); finish with `bun run type:check` and `bun run test <file>`.
- `bun run bench` exits 0 even when a bench throws: vitest reports such a bench without samples ("NaNx faster"). Type bench fixtures as the engine hands them (no `as any`), and check that every bench of the summary has samples.
- `test/e2e` runs the whole pipeline for each mode on `bun:test`, with `mock.module` replacing CCXT, the config and winston, an in-memory SQLite database and a sped-up clock. The three realtime flows shorten `ONE_MINUTE` to 50 ms and mock date-fns' `addMinutes` and `differenceInMinutes` on it (`test/e2e/mocks/date-fns.mock.ts`); the streams and the pipeline floor their minutes with `startOfMinuteUTC`, and the per-bucket clocks add `ONE_MINUTE`, so they follow the same clock. The backtest flow keeps real minutes, which its seeded candles and the SQLite queries count. A realtime test never ends its pipeline by itself (nothing exits the process), so each realtime flow file calls `trackRealtimeRuns()` next to its mocks and `endRealtimeRun()` in `afterEach` (`test/e2e/helpers/realtimeRun.helper.ts`), which finalises the plugins and stops the order polls that would otherwise leak into the next test.

## Stale docs and example configs

`README.md` and `documentation/*.md` were written before the multi-asset refactor. The six guides, `quick-start.md`, `modes.md`, `plugins.md`, `built-in-strategies.md`, `custom-strategies.md` and `indicators.md`, have since been brought up to date: their YAML examples validate against the schemas and their TypeScript examples type-check. `README.md` was only patched where a fix touched it. Prettier does not format `documentation/` (`.prettierignore`), whose tables are aligned by hand, and `documentation/dev/` is gitignored: local notes and specs, never committed. When a doc and the code disagree, trust the zod schemas (`configuration.schema.ts`, `src/plugins/**/*.schema.ts`, `src/services/exchange/**/*.schema.ts`) and `strategy.types.ts`. The usual traps when copying from an older doc or config:

- `watch.asset` is now `watch.assets: [...]`, and `exchange.key` is `apiKey`.
- `simulationBalance` is a list of `{ assetName, balance }`, naming only the watched assets and the currency, spelt as `watch` spells them (`usdt` is refused).
- Assets, currency and symbols are upper case (`btc` is refused, not read as `BTC`), and `simulationBalance`, `marketData` and `initialTicker` list each asset or symbol once.
- A daterange bound written as a day alone is its midnight UTC: `end: 2024-12-31` reads only the first minute of December 31st. Write `2024-12-31T23:59:00Z` to end with that day (`2025-01-01` reads the first minute of the next one too). A date and a time need `Z` or an offset.
- Strategy parameters sit directly under `strategy:`, not under `params:`.
- The `PerformanceAnalyzer` plugin no longer exists; use `PortfolioAnalyzer` or `RoundTripAnalyzer`.
- `addIndicator` takes `(name, symbol, params)`, and `params` is required even when every parameter has a default: pass `{}` then, `undefined` for TrueRange.
- Every section but `strategy` refuses unknown keys, so a retired or misspelt one (`asset`, `fillGaps`, `tickRate`, `sandBox`) is an error, not a silent default. `tickrate` and `warmup.tickrate` are integers of at least 100 ms; `storage.insertThreshold` is an integer number of minutes between 1 and 1440.
- A dummy-cex example without `exchange.marketData` is incomplete: a backtest needs one entry per watched pair (`config/backtest.yml` and `documentation/modes.md` have complete blocks).

In `config/`, `backtest.yml`, `importer.yml` and `realtime-writer.yml` validate as they are. The other `realtime-*.yml` files validate once their credentials are filled in, `realtime-trader.yml` also once its disclaimer is set to `true`.
