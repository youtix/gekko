# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Gekko is a modular crypto trading bot framework written in TypeScript and run with Bun. It covers candle import, backtesting, screening/alerting, paper trading and live trading through CCXT (Binance, Hyperliquid). The bot has one entry point, `apps/gekko/src/gekko.ts`, and what it does is decided entirely by a config file; Fox, `apps/fox/src/fox.ts`, backtests the variants of a template configuration in parallel workers (see Fox).

The checkout is a monorepo of Bun workspaces (`"workspaces": ["packages/*", "apps/*"]` in the root `package.json`, which alone carries the version, beside the devDependencies of the tooling and of the root's own files: `js-yaml`, `lodash-es` and `zod`, which the documentation test imports) whose tasks Turborepo runs (`turbo.json`, see Commands): six packages and two apps in layers, each importing only the workspaces its row of the table lists, of lower layers though not every one of them (the core reads neither the indicators nor the strategies), which its `package.json` lists (`"@gekko/shared": "workspace:*"`) beside the external packages it imports (`scripts/tooling/dependencies.test.ts` holds the two lists to each other; `protobufjs`, which ccxt loads without declaring it, is listed by `packages/core` beside ccxt, and Bun hoists it to the root `node_modules`, where ccxt finds it). ESLint refuses an import of any other workspace, in a test as in a source, whatever directory it runs from (`DEPENDENCIES` in `eslint.config.js`: one `import/no-restricted-paths` zone per forbidden pair, between the workspaces `eslint.config.js` finds from the root `package.json`'s `workspaces`, as Bun does, anchored at the root by its `basePath`, its message naming both and sending here):

| Workspace             | Package             | Layer | Imports                                                             | Holds                                                                                                                                                                                                                                          |
| --------------------- | ------------------- | ----- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `packages/shared`     | `@gekko/shared`     | 1     | no workspace                                                        | the constants, the errors, the hand-written types (`models/`: candles, orders, events, `MarketData`, `Exchange`, `CandleSize`…), `global.d.ts`, the generic utilities (`utils/`) and the domain helpers (`helpers/`)                           |
| `packages/schemas`    | `@gekko/schemas`    | 2     | shared                                                              | every zod schema (the configuration, the exchanges, the plugins, the strategies, the Telegram bots) and the types inferred from them (`Configuration`, `Watch`, `ExchangeConfig`…)                                                             |
| `packages/indicators` | `@gekko/indicators` | 2     | shared                                                              | the indicators and their registry                                                                                                                                                                                                              |
| `packages/strategies` | `@gekko/strategies` | 3     | shared, schemas, indicators                                         | the strategies and their registry, `strategy.types.ts`, the PositionTracker and the PositionBook (`helpers/`), the private strategies (`custom/`) and the e2e fixtures (`debug/`)                                                              |
| `packages/core`       | `@gekko/core`       | 3     | shared, schemas                                                     | the configuration (`configuration/`), the run context and its services (`run/`), the logger, the pipeline with its streams and batchers, the orders, the exchanges, the storage, the Telegram bots, `Plugin` and its event emitter (`plugin/`) |
| `packages/plugins`    | `@gekko/plugins`    | 4     | the five packages                                                   | the eight plugins and their registry, the StrategyManager and the TrailingStopManager (`tradingAdvisor/`)                                                                                                                                      |

| `apps/fox`            | `@gekko/fox`        | 5     | shared, schemas, strategies, core, plugins                          | Fox, compiled to `dist/fox`, and its templates (`templates/`)                                                                                                                                                                                  |

Across workspaces a module is imported as `@gekko/<pkg>/<path>`, its path under the package's `src/` without `.ts` (`@gekko/shared/utils/math/math.utils`, `@gekko/core/exchange/ccxtExchange`; `@gekko/cli/…` and `@gekko/fox/…` name the apps' sources), and a module of the same package by a relative path, never by the package's own name (but a private strategy of `custom/`, which may import its package by name, see Strategies); a relative path never reaches into another workspace, but `logVersion`'s (`packages/shared/src/utils/process/process.utils.ts`), which reads the root `package.json`, the one version. No directory has a barrel file but the three registries, `@gekko/indicators/index`, `@gekko/strategies/index` and `@gekko/plugins/index`, which the code reads by name. The `paths` of `tsconfig.base.json` (`"@gekko/shared/*": ["./packages/shared/src/*"]`, one entry per workspace) are the one resolution: tsc reads them through each workspace's `tsconfig.json`, which extends the base, ESLint's resolver through the root `tsconfig.json`, wherever ESLint runs from, vitest through `vitest.shared.ts`, which builds its aliases from them, and Bun as tsc does. Each workspace's `package.json` exports its sources (`"exports": { "./*": "./src/*.ts" }`), which the links `bun install` makes in `node_modules/@gekko/` lead to as well: nothing is built, and no workspace has a version of its own.

## Commands

Bun is the package manager and the runtime. Scripts, git hooks and CI all go through `bun` and the root `bun.lock`, the one lockfile of the workspaces; there is no `package-lock.json`. Node (22.13 or later, not 23, as `engines` says) must be on the PATH too: vitest runs the unit tests under it (see Testing).

```bash
bun install
bun run dev              # run the bot from source (apps/gekko/src/gekko.ts) in the root directory
bun run dev:fox          # run Fox from source (apps/fox/src/fox.ts), its options after the script's name (see Fox)
bun run build:exec       # compile the standalone executables dist/gekko and dist/fox
bun run type:check       # tsc --noEmit of each workspace, after those it depends on, and of scripts/ and the root's vitest files
bun run lint:check       # eslint . (all but dist/, db/, documentation/dev/, .claude/, and coverage/ and .turbo/ at any depth; bun run lint autofixes)
bun run format:check     # prettier --check . (all but what .gitignore and .prettierignore list; bun run format writes)
bun run test             # unit tests: each workspace's vitest suite over its src/**/*.test.ts, and scripts/**/*.test.ts
bun run --filter @gekko/shared test src/helpers/collection/ringBuffer.test.ts                       # one file, of one workspace
bun run --filter @gekko/shared test src/helpers/collection/ringBuffer.test.ts -t "argument itself"  # one test, by name
bun run test:coverage    # what CI and the pre-push hook run; fails below 95% lines/functions/branches/statements in any workspace
bun run test:e2e         # apps/gekko/test/e2e on Bun's test runner, --isolate (a fresh global per file, or the module mocks leak)
bun run bench            # vitest benchmarks (src/**/*.bench.ts of shared, core and strategies)
```

The commands above run from the root. `type:check`, `test`, `test:coverage`, `test:e2e`, `bench` and `build:exec` are `turbo run <task>`: turbo runs the script of that name of every workspace that has one, in the workspace's directory. `type:check` runs side by side, each workspace's tsc after those of the workspaces it depends on (`"dependsOn": ["^type:check"]`), beside the root's `type:check:scripts` (`tsc -p tsconfig.scripts.json`: `scripts/`, the root's vitest files and `global.d.ts`). `test` and `test:coverage` run one workspace at a time (`--concurrency=1`), the root's `test:scripts` or `test:coverage:scripts` among them (vitest over `scripts/**/*.test.ts`, its coverage over `scripts/**/*.cjs`; the root's three tasks are declared `//#…` in `turbo.json`): side by side, the vitest processes (one per workspace and the root's), each with its pool of workers, overloaded the machine, and two tests of `apps/gekko/src/gekko.test.ts` ran past their 10 s timeout. `bench` runs one workspace at a time too, so that no benchmark measures another's load. `test:e2e` runs `apps/gekko`'s, the only one, and `build:exec` those of `apps/gekko` and `apps/fox`, which write `dist/gekko` and `dist/fox`. A run stops at the first task that fails (turbo's `--continue=never`): `bun run test:coverage --continue` runs the others. `lint`, `lint:check`, `format`, `format:check` and `commit:check` run once, at the root, with one configuration, and `dev` and `dev:fox` run the sources without turbo, which has no `dev` task.

Each workspace's `package.json` has `type:check` (tsc, incremental, its build info in the root's `node_modules/.cache/tsc/<name>.tsbuildinfo`), `test`, `test:coverage` and `test:watch`, `bench` and `bench:watch` in `shared`, `core` and `strategies`, `apps/gekko` also `build:exec` and `test:e2e`, and `apps/fox` `build:exec`. One workspace's runner takes a file or a test name: `bun run --filter @gekko/shared test <file> -t "<name>"` (Bun's own workspace filter, from the root) or `bun run test …` in the workspace's directory. At the root, `bun run test <file>` fails (turbo reads the file as a task: `Could not find task`), and `bun run test --filter=@gekko/shared` runs that workspace's suite alone, through turbo.

Turbo replays a task from its cache (`.turbo/`, gitignored, at the root and in every workspace) when nothing it reads has changed: the files of its workspace that git tracks or does not ignore, `tsconfig.base.json` and `vitest.shared.ts` (`globalDependencies`), the dependencies `bun.lock` resolves for it and for the root, the values of `GEKKO_LOG_LEVEL`, `GEKKO_CONFIG_FILE_PATH`, `TZ`, `CI` and `HUSKY` (`globalEnv`), and the files of the workspaces below it, through the tasks it depends on: `^type:check` for a type check, `transit` for the tests, a task no workspace has a script for, whose hash covers its workspace and every workspace it depends on (without it, a change of `@gekko/shared` replayed `@gekko/core`'s passing tests). The private strategies of `packages/strategies/src/custom/`, which git ignores, are inputs of the strategies' tasks and of the root's, so that a private strategy changed since the last run is checked again; the root's tasks read every file of the checkout, and its two test tasks the local copies of `config/` too (`config/*.local.*`, gitignored), which the documentation test checks. `bench` and `build:exec` are never cached, and `--force` runs a task whatever its cache. Turbo runs the tasks in its strict environment mode: they get the variables of `globalEnv` and those turbo always passes (`PATH`, `HOME`, `SHELL`, `TERM`, `TMP`, `TEMP`, `NODE_OPTIONS`, `GITHUB_ACTIONS`, …), not another variable of the shell, such as `TMPDIR` or `VITEST_MAX_WORKERS`. Neither the Bun nor the Node installed is an input, only the `engines` ranges of the root `package.json`: after upgrading either, run the tasks with `--force`, as the commit that moves Bun's pins must pass `test:e2e` on the new version. Only the shell's environment reaches turbo: `bun run` loads no `.env` file into the environment of the script it runs (under Bun 1.4.4 as under 1.3.14), so a `GEKKO_*` of `.env` or `.env.local` reaches no task and enters no hash. One exported in the shell or set on the command line (`GEKKO_LOG_LEVEL=debug bun run test:e2e`) reaches every task and is part of every hash, as is one that `bun --env-file=.env.local run <script>` loads. A Bun process that a script starts reads the two files itself, from its own working directory: the root's `dev` and `dev:fox`, run at the root, do; the tasks do not, a workspace's running in its directory, which holds none (`apps/gekko`'s `bun test`), and vitest under Node, which reads none. The tracked `.env` is an input of the root's tasks only as one of the checkout's files; `.env.local`, which git ignores, is an input of none.

`lint:check` and `format:check` both skip `.claude/`, where the Claude desktop app checks out its worktrees (`git worktree list`; `.git/info/exclude` hides them from git, which neither tool reads): a worktree is a copy of the checkout, whose guides `.prettierignore`'s `/documentation` does not reach, and whose own `eslint.config.js` ESLint 10 reads for the files under it, so that typescript-eslint, holding two candidate `tsconfigRootDir`s, refused every file of the lint, the root's too; the TypeScript programs read none of it, each workspace's covering its own directory, and tsc's `**` (the root `tsconfig.json`'s, which the pre-commit hook reads) entering no directory whose name starts with a dot.

`bun test` without `run` is Bun's test runner, not vitest. Only `apps/gekko/test/e2e` is written for it, and `bun run test` finds none of its files (each workspace's vitest reads its `src/**/*.test.ts`); CI runs `test:e2e` in its `build` job, after `test:coverage`, and no git hook does. Its realtime flows run real minutes under a fake clock of the harness's own (see Testing).

vitest pre-bundles date-fns and lodash-es for every suite, and ccxt for the suites that can load it (`depsOptimizerFor(dir)` in `vitest.shared.ts`, which every workspace's `vitest.config.ts` and the root's read: ccxt for a directory whose `package.json` lists it, or lists a workspace that can, at any depth, so for `@gekko/core`, the plugins, `apps/gekko` and `apps/fox`, not for shared, schemas, indicators, strategies nor the root's `scripts/`, where it cost each fresh cache an esbuild run of half a second and 39 MB; `scripts/tooling/vitestConfig.test.ts` checks the lists): each test file runs in a process of its own, which loaded them module by module, so a suite takes less than half the time. The bundles sit in the root's `node_modules/.vite/<key>/`, the key a hash of the root `bun.lock`'s content and of the directory whose suites run (`cacheDirFor`), one per workspace and one for the root's suites, so that a dependency bump starts new directories (Vite reads no `bun.lock`: in one directory, the suites would go on running against the bundle of the old version), and that neither two workspaces nor a copy of the repository whose `node_modules` is a link share one (Vite deletes the bundles it did not build to rebuild them, under a run that reads them). The directories of earlier lockfiles and of deleted copies stay behind, about 41 MB each where ccxt is bundled, 2 MB elsewhere: `rm -rf node_modules/.vite` reclaims them, and the next run rebuilds its own. ccxt must stay bundled where a suite loads it: left out, such a suite fails on `Cannot access 'bydfiRest' before initialization`.

### Running the bot

The bot takes no CLI flag, only two environment variables (Fox has options of its own, see Fox):

- `GEKKO_CONFIG_FILE_PATH`: the config file to load (`.yml`, `.yaml`, `.json` or `.json5`). Its `watch.mode` (`importer`, `backtest` or `realtime`) selects what runs.
- `GEKKO_LOG_LEVEL`: winston level (`error`, `warn`, `info`, `http`, `verbose`, `debug`, `silly`; case-insensitive, `warning` means `warn`). It defaults to `error`, so set `info` or `debug` to see anything. An unknown value falls back to `error` and says so once.

Bun loads `.env` and then `.env.local` (gitignored, takes precedence) automatically, from the working directory and not from a parent's, so a bare `bun run dev` at the root runs whatever config those files point at (the bot's own Bun process reads them, at the root where `dev` starts it: `bun run` hands a script neither file, see Commands). The compiled executable (`dist/gekko`) loads them the same way, from the directory it runs in, not from beside the binary. A variable set on the command line or exported in the shell wins over both files, so there is nothing to `source`:

```bash
GEKKO_CONFIG_FILE_PATH=./config/backtest.yml GEKKO_LOG_LEVEL=info bun run dev
```

Start it from the root: the root's `dev` runs `bun apps/gekko/src/gekko.ts` there, where `.env`, `config/` and `db/` are. `apps/gekko` has no `dev` script of its own, nor turbo a `dev` task: run in `apps/gekko`, the bot would find no `.env` and read a relative path (`GEKKO_CONFIG_FILE_PATH`, `storage.database`, a `strategyPath`) from there.

A backtest replays 1-minute candles from SQLite and aborts if any minute of `watch.daterange` is missing, so the range has to be imported first (importer mode, e.g. `config/importer.yml`, writing to the gitignored `db/`). The importer only stores closed minutes: a `daterange.end` at or after the minute in progress is clamped to the last closed minute, with a warning. It fills a gap of a pair of up to 7 days (`MAX_GAP_FILL_MINUTES`) with flat candles and refuses a longer one, naming the pair, before any of it is written; a pair whose history starts after the range does (listed on the exchange after `daterange.start`) or ends before it does, or whose last minutes of the range the exchange skips although it has later candles, keeps those minutes missing, with a warning, so that a backtest of them is refused rather than run on made-up candles. Writers (importer, realtime) create the database directory; a backtest opens the database read-only, refuses a missing file or a pair without a table (the connection it opened closed at once: it held the database until the garbage collector closed it), and writes nothing to it (SQLite's read-only connection to a database in WAL leaves an empty `-wal` and a 32 KB `-shm` beside it, which only a connection that writes removes, the next import as it closes). Every mode refuses, as the storage opens, a `storage.database` that is not an SQLite file or is a truncated copy: `Cannot open the database <path> (file is not a database).` (`database disk image is malformed` for a truncated copy). An import overwrites the stored candles of its range with the candles it reads from the exchange, so re-importing a range repairs the synthetic candles a realtime run's gap filler wrote there; a made-up candle never replaces a stored candle that traded, and a realtime run only replaces a stored candle that is itself made up.

Exit codes: 0 when a run ends normally or is stopped by `ApplicationStopError`, 1 after any other failure, 130 on SIGINT and 143 on SIGTERM (the storage buffer is flushed and closed, the plugins are not finalised). A run that ends normally still exits 1 if a promise rejection went unhandled along the way, if a plugin failed to finalise, or if the storage failed to close. A failed finalisation rejects the run with `[STREAM] <plugin> failed to finalize: <what it threw>` (several joined by `; `), caused by that failure (an `AggregateError` of them when several failed): an import whose last insert fails (another connection holding the write lock past the 5 s busy timeout, a full disk) so exits 1, naming the minutes it did not write. `main()` (`apps/gekko/src/gekko.ts`) closes the storage once more on its way out, through its run context's `services.closeStorage()` (none before the context exists: `GEKKO_CONFIG_FILE_PATH` unset, a file refused), after CandleWriter's own close (the first close when no CandleWriter was finalised: a backtest, a start-up that failed before CandleWriter was initialised); a failed close is logged at error level as `Could not close the storage: …`, as on SIGINT and SIGTERM and after an uncaught exception, and a run that had ended normally then exits 1 through `process.exitCode`, ending by itself. A run that failed or was stopped keeps its code, 0 for an `ApplicationStopError`, a failed finalisation logged at error level beside its own error.

## Git workflow

- Commit messages must follow Conventional Commits. commitlint enforces it in the `commit-msg` hook (`bun x commitlint --edit`), on pull requests (their own commits, `base.sha..head.sha`) and on pushes to `main` and `development` (`before..sha`; a new branch, or a forced push whose previous tip is not in the clone, is skipped with a notice): subject not capitalised, header at most 125 characters, body and footer lines of any length. `bun run commit:check --last` (or `--from <ref>`, or a message on stdin) checks messages by hand.
- `pre-commit` type-checks what is committed, not the working tree: git keeps a copy of the tree being committed in `node_modules/.cache/index-check`, with an index of its own, updated in place, which incremental tsc checks through the copy's root `tsconfig.json`, the whole checkout in one program, which resolves `@gekko/<package>/<path>` through the copy's `tsconfig.base.json` to the copy's own sources (its errors name the copy's paths). It does not run the workspaces' programs, which see less (each reads its own files, `global.d.ts` and what they import): `bun run type:check` does. Then it runs lint-staged (`eslint --fix` and `prettier --write` on the staged `.ts`, `.tsx`, `.js`, `.jsx`, `.cjs`, `.mjs`, `.cts` and `.mts` files, `prettier --write` on the `.json`, `.md`, `.yml` and `.yaml` ones). An untracked file, a private strategy of `packages/strategies/src/custom/` included, is not checked at commit time: `bun run type:check` checks it. A commit interrupted during the copy can leave `node_modules/.cache/index-check/.index.lock` behind, which refuses the next copy until it is deleted. `pre-push` runs `bun run test:coverage`, through turbo, a workspace whose inputs have not changed since its last passing run replayed from the cache, only for a push that creates or moves a branch, not for a tag, a notes ref or a deletion.
- Work lands on `development`, and pull requests target it (CONTRIBUTING.md has contributors fork and branch from `upstream/development`). `main` only moves for releases: a push to `main` runs the checks, then a `release` job of its own, with `HUSKY=0` so that no git hook runs at its commit and pushes, runs semantic-release, which writes `CHANGELOG.md` (listed in `.prettierignore`: it keeps the generator's text), writes the version it releases into the root `package.json` (no workspace has one) and rebuilds `dist/gekko` and `dist/fox` from it (the prepare step of the repository's own plugin, `scripts/release/version.cjs`, given `executables: ['dist/gekko', 'dist/fox']`: it removes the executables an earlier build left, runs `bun run --silent build:exec` once and, if the build leaves either missing, fails the release before anything is tagged, naming the missing ones), commits both files to `main` (`chore(release): <version> [skip ci]`) and publishes the GitHub release with `dist/gekko` and `dist/fox` attached under their stable names, `gekko` and `fox`, labelled `gekko executable (<platform>-<arch>)` and `fox executable (<platform>-<arch>)`. So never bump a version or edit the changelog by hand. The bot prints the root `package.json` version it was built with (`Gekko version: vX.Y.Z` at info level): a release prints its own, a build of `development` the last one merged back from `main`.
- semantic-release reads the commits with the `conventionalcommits` preset, the parser commitlint validates them with. `feat` releases a minor; `fix`, `perf` and a revert (a `revert:` or `Revert "…"` header with git's `This reverts commit <sha>.` line) a patch; the other types nothing on their own. A `!` after the type or the scope (`feat!:`, `fix(trader)!:`) and a `BREAKING CHANGE:` or `BREAKING-CHANGE:` footer each release a major; a header that starts with `BREAKING CHANGE:` is refused (no type). A `Co-Authored-By:` trailer after a breaking footer ends up in the note: mark the change with `!` and keep the trailer last, or end with a paragraph holding the trailer, then a one-line `BREAKING-CHANGE:` footer.
- CI runs on pushes and pull requests to `main` and `development`, in a job whose token can only read: the commit messages, `format:check`, `lint:check`, `type:check`, `test:coverage`, `test:e2e` and `build:exec`, `format:check` and `lint:check` reading the whole checkout (`packages/`, `apps/`, `scripts/` and the configuration files included), and `build:exec` building both executables, which the job then runs once (`dist/fox --help`, then each on `apps/fox/templates/dema.yml`, whose database the runner lacks, so that the storage refuses it, `Cannot open the database`, a line a module that fails to load in the executable, Fox's compiled worker included, never reaches), turbo's telemetry off for both jobs (`TURBO_TELEMETRY_DISABLED: 1` in the workflow's `env`). No turbo cache is kept from one CI run to the next: every run executes every task. The `build` job stops after 30 minutes and its `test:e2e` step after 10 (`timeout-minutes`): a test that awaits a promise that never settles fails after its timeout, which Bun counts in real time (30 s in the realtime flows, see Testing), but `await expect(promise).rejects` on such a promise blocks past every timeout, and GitHub's default bound is six hours, the release waiting behind it. On a push to `main`, the `release` job, which needs that one, runs `bun run release` with the write scopes, so a malformed commit pushed to `main` skips that push's release. Both jobs of `.github/workflows/ci.yml` pin Bun to 1.4.4 (`bun-version`), the version the root `package.json` declares as its `packageManager` (`bun@1.4.4`), since the e2e harness relies on that version's test runner (`mock.module`, `setSystemTime`, `--isolate`, see Testing), not on its fake timers, and the release compiles `dist/gekko` and `dist/fox` with it: an upgrade changes both pins and the `packageManager`, in a commit of its own that passes `test:e2e` on the new version.

## Code conventions

- `console.*` is a lint error. Log through `debug`, `info`, `warning` and `error` from `@gekko/core/logger/logger`, each taking `(tag, message)`; `tag` is a closed union in `packages/shared/src/models/tag.types.ts`. `debug` returns before winston formats anything when its level is off, so a debug line on the hot path costs nothing; an info line that would be logged on every candle goes behind `isLevelEnabled('info')` (no line of Gekko is one today), never a warning or an error, which the log buffer keeps for Supervision whatever `GEKKO_LOG_LEVEL`. The logger writes its lines to stdout, in order, through winston's Stream transport over a `LineWriter` (`packages/core/src/logger/lineWriter.ts`, its helpers in `logger.helper.ts`, its constants in `logger.const.ts`), so that a process exiting right after logging (a Fox worker once its outcome is posted, Fox and the bot on `process.exit()`) loses none of its lines to a pipe read slower than it writes, which `process.stdout`, queued by Bun, lost. Loading winston makes fd 1 non-blocking under Bun. A thread alone on stdout, the bot, writes what the pipe takes at once (`writeAvailable`) and queues the rest, in order, written at its next line and by a timer of its own, 1 ms later, then twice as late each time the pipe takes nothing, up to 100 ms (unref'd), its event loop running meanwhile: waiting for a reader that stalled (a pager left open, a log driver whose backend is down) held the Heart, the order polls, Telegram and the signal handlers, and failed a live run with `[CORE] Failed to tick in time` once the reader resumed more than 3 minutes later (Node writes to a pipe asynchronously on POSIX too). What is queued as the process exits is written by an `'exit'` listener, added while lines are queued, waiting for the reader as long as it takes (`writeAll`, 1 ms then twice as long up to 100 ms), and beyond `MAX_QUEUED_BYTES` queued (16 MiB) the thread waits for the reader to take them all, so that a backtest logging at debug level into a stalled pipe does not hold its whole log in memory. Fox's threads write each line whole under a lock they share, before the call that logs it returns, waiting for the reader meanwhile (see Fox). A write that fails otherwise (EPIPE once the reader is gone) is the stream's error, an uncaught exception the bot and Fox log and exit 1 on, as `process.stdout`'s EPIPE was. A line that quotes a failure writes `describeError(err)` (`packages/shared/src/errors/error.helper.ts`): a `GekkoError`'s `untaggedMessage`, since the line has a tag of its own; an `AggregateError`'s message followed by its errors, each so described (`; ` between them); any other Error's message; a string as it is; an object whose message `util.inspect` does not show (Bun's ResolveMessage and BuildMessage, which the import of a strategy file that cannot be found or parsed rejects with) as `<class>: <message>`, a BuildMessage followed by ` at <file>:<line>:<column>`; anything else as `util.inspect` writes it. Never `String(err)` or `${err}`: they write an object as `[object Object]`, and throw for one without a prototype from the very catch meant to report it. `toError(value)` there makes an Error of any thrown value. A refusal that names a value it refuses writes it with `showValue(value)` (`packages/shared/src/utils/object/object.utils.ts`): a string in double quotes (`"3"`, not the number 3), anything else as `util.inspect` writes it, two levels deep, on one line (`[ 14 ]`, `3n`, `[Object: null prototype] {}`); the RingBuffer's size refusal and the indicators' parameter checks do. A message that counts writes its noun with `pluralize(word, count)` (`packages/shared/src/utils/string/string.utils.ts`), the plural for 0 too, rather than `minute(s)`, and one that names several pairs, keys or options lists them with `listInWords(items)` (same file: `a and b`, `a, b and c`).
- Unused parameters must be prefixed with `_`, a lint error otherwise, a leading one too (`args: 'all'`); an unread catch binding is left out (`catch {`), since `catch (_err)` is reported. Import cycles are lint errors (`import/no-cycle` reads the `.ts` modules), and only a type-only import breaks one: `import type …`, or `import { type A, type B }` whose every name is a type; an import written as a value import counts even when it brings only types. A value cycle can throw `Cannot access … before initialization` under Bun, depending on which of its modules loads first (`movingAverages.const.ts` says how one was avoided). No lint rule finds a dead export (`import/no-unused-modules` checks nothing without options, and crashes under ESLint 10 with `unusedExports`): look for one with TypeScript's find-references. `lint:check` and `format:check` read the whole checkout, and lint-staged gives every `.cjs`, `.mjs`, `.cts` and `.mts` file ESLint and Prettier. The `.cjs` files (the release and commitlint configurations, `scripts/release/version.cjs`) are linted as CommonJS with Node's globals; the other `.js` files are ES modules, linted with Node's globals without CommonJS's (`globals.nodeBuiltin`), so a `require` or a `__dirname` there is `no-undef`. `version.cjs` is type-checked through its `// @ts-check` (`allowJs`, and its own entry in the `include` of the root `tsconfig.json` and of `tsconfig.scripts.json`: under the default include, its `version.d.cts` outranks it and tsc drops it).
- Prettier: 140 columns, single quotes, trailing commas, no parentheses around a lone arrow parameter. ESLint has no formatting rule: its stylistic rules, deprecated since 8.53, refused the double quotes Prettier writes around a text holding an apostrophe.

The root `tsconfig.json` includes `**/*.ts` and `scripts/release/version.cjs`, the whole checkout in one program, which the editor and the pre-commit hook read (a `**/*.cts` pattern would drop version.cjs again). The vitest configurations are typed (`defineConfig`): a misspelt option fails `type:check`.

No directory has a barrel file but the three registries: import `@gekko/shared/utils/<dir>/<file>`, `@gekko/shared/helpers/<dir>/<file>` and so on.
- Code splitting between `packages/shared/src/utils/`, the `helpers/` of `packages/shared` and `packages/strategies`, colocated files and class files follows strict rules:
  - `packages/shared/src/utils/` (`@gekko/shared/utils/*`) holds only generic, domain-agnostic utilities (`*.utils.ts`) with no dependency on Gekko's domain models (`@gekko/shared/models/*`), `GekkoError`, the logger or trading rules (`math.utils.ts`, `round.utils.ts`, `string.utils.ts`, `date.utils.ts`, `array.utils.ts`, `object.utils.ts`, `fetch.utils.ts`, `process.utils.ts`). The `.utils.ts` suffix is used exclusively inside `packages/shared/src/utils/`.
  - `packages/shared/src/helpers/` (`@gekko/shared/helpers/*`) holds the helpers (`*.helper.ts`) shared across several modules, of one package or of several, that work with Gekko's domain models or its trading rules or throw `GekkoError` (`candle.helper.ts`, `event.helper.ts`, `market.helper.ts`, `precision.helper.ts`, `portfolio.helper.ts`, `order/sizing.helper.ts`, `stream.helper.ts`), and, whatever their number of users, the helper classes `AsyncMutex` and `RingBuffer` and `finance/stats.helper.ts`, the figures of a performance report: `AsyncMutex` serves the simulator alone (generic, it imports nothing of Gekko's, but the modules of `packages/shared/src/utils/` are `*.utils.ts` files of functions), `stats.helper.ts` the analyzers. Shared imports no workspace (`import/no-restricted-paths` refuses it), so none of them logs, the logger being core's: a helper that a plugin and a module of a lower package share lives in the lowest package both import, as the sizing of an order (`packages/shared/src/helpers/order/sizing.helper.ts`), which the Trader and the PositionBook import. `packages/strategies/src/helpers/` (`@gekko/strategies/helpers/*`) holds what the strategies share: `strategy.helper.ts` (`indicatorsBySymbol`), the `PositionTracker`, which serves the book and the custom strategies, and the `PositionBook`. `SequentialEventEmitter`, which serves `Plugin` alone, sits beside it in `packages/core/src/plugin/`. Helper functions only used by a single module or directory stay colocated beside it and always use the `.helper.ts` suffix.
  - A file that declares a class (`<name>.ts`, `<name>.strategy.ts`, `<name>.indicator.ts`, `<name>.stream.ts`, `<name>.storage.ts`, `<name>.error.ts`) must contain only its imports and the class itself (apart from the internal `UTCDate` subclass in `date.utils.ts`), `configuration.ts` included, which exports the class alone. Never leave helper functions, types/interfaces or constants outside the class in that file: extract them into sibling `<domain>.helper.ts`, `<domain>.types.ts` and `<domain>.const.ts` files at the same directory level, reusing the directory's existing `.helper.ts`, `.types.ts` or `.const.ts` file whenever one already exists.
- `lodash-es` (never `lodash`), `date-fns` and zod v4 are used throughout. Timestamps are epoch milliseconds, and a duration in milliseconds is written with `ONE_SECOND` and `ONE_MINUTE` (`@gekko/shared/constants/time.const`). A minute is floored with `startOfMinuteUTC` (`packages/shared/src/utils/date/date.utils.ts`) and moved with `± ONE_MINUTE`, the clocks set on every bucket included (`start + ONE_MINUTE` in the Trader, the StrategyManager, the simulator and the analyzers: date-fns' `addMinutes` built a Date each time), a second is floored with `Math.floor(t / ONE_SECOND) * ONE_SECOND`, and a duration shown to the user is written with `formatDurationUTC(start, end)` (same file), on the UTC calendar. date-fns' `startOf…`, its `add…` and `differenceIn…` of days, weeks, months and years, and `intervalToDuration` count in the host's local time: on a host with daylight saving time, `startOfMinute` read every instant of the hour repeated when it ends an hour early, so a live stream pushed nothing for that hour, a duration across a change came out an hour off, and `intervalToDuration(…, { in: tz('UTC') })` of `@date-fns/tz` still moved a date whose UTC time the host's zone skips at its spring change ("1 day -1 hours"): no code imports `@date-fns/tz`.
- There is no decimal library: `round` (`packages/shared/src/utils/math/round.utils.ts`) rounds a number exactly as it is written, and `addPrecise` and `multiplyPrecise` (`packages/shared/src/utils/math/math.utils.ts`) add and multiply two numbers as they are written (0.3 − 0.1 is 0.2, 100.01 × 0.0004 is 0.040004), exactly up to 15 significant digits and as `a + b` or `a × b` from 17, for the amounts, prices, costs and fees that must come out as decimals. At 16 digits `addPrecise` gives the double nearest to the sum, which `String` can write a unit of its last decimal off, so that the next call adds to that neighbour and a change below an ulp can be lost (an 8-decimal balance from 67.1 M to 90 M units), and `multiplyPrecise` the binary product rounded to the decimals of the two, which can land a unit off the exact product, farther than `a × b` (a cost of 100,000 to a million, from an 8-decimal amount at a 2-decimal price). A quotient, which neither works out exactly (a mean, a fee rate, a percentage), goes through `toSignificantDigits` there: the double rounded to the 15 significant digits it keeps, a tie away from zero (0.06999999999999999 is 0.07), and a percentage of one figure in another through `toPercent(part, whole)` (`packages/shared/src/helpers/finance/stats.helper.ts`: the part moved two places in decimal, divided once, rounded so), the one way every percentage of the reports, a round trip's `profit` and the fee rate of a trade CCXTExchange reads are worked out; a reported return or drawdown works its change out with `addPrecise` first, and a figure made from a return is worked out from the equities and rounded once (`calculateAnnualizedReturnPct(currentEquity, startEquity, elapsedYears)`): from the 15-digit total return, a gain of 40 on 300,000 over a day annualized to 4.87999999999999 %, written 4.87 %. They read the number's decimal string, a cost a per-candle loop should not pay: the candle batcher sums volumes with a scaled integer instead, and the analyzers' valuation (`calculatePortfolioTotalValue` in `packages/shared/src/helpers/portfolio/portfolio.helper.ts`) pays it once per timeframe candle, a few µs for each asset held, because the analyzers compare equities exactly. The simulator books the cost of an order to 8 decimals, as Binance keeps its balances (`BOOKED_CURRENCY_UNIT`, 10^-`COST_DECIMALS`, `packages/shared/src/constants/order.const.ts`), while an equity values a holding at amount × price, up to 5e-9 apart: the PortfolioAnalyzer takes two equities less than that unit apart for one amount, its drawdowns and returns ignoring such a gap, and the RoundTripAnalyzer a round trip whose P&L, worked out from its fills, is less than that unit from 0 (or whose proceeds are within a billionth of its cost and fees) for a break-even.
- Indicator results and other computed numbers are guarded with `isFiniteNumber` (lodash's `isNumber` accepts NaN), and two values equal in exact arithmetic but computed apart, such as a flat market's close and its SMA, are compared with `compareWithTolerance` (relative 1e-9), both in `packages/shared/src/utils/math/math.utils.ts`. TMA, SMACrossover and EMARibbon compare so, CCI, Stochastic (StochasticRSI through it) and Bollinger Bands (OBV through them) decide a flat window so, and GridBot reads a level at its break-even so (`isLosingLevel`, its BUY cost against its SELL proceeds). `isFinitePositive` there is the one check of a finite number above 0: an order's price, amount and cost, a market's bound or step (`toBound` in `packages/shared/src/helpers/market/market.helper.ts` reads a limit or a step so). Steps and ticks are applied by `roundToStep` and `getPriceTick` (`packages/shared/src/helpers/market/precision.helper.ts`), which the simulator, GridBot and the PositionTracker share: an amount truncated to its step, whatever the step, a price rounded half up to the tick at that price. An amount is valued as the exchanges check it by `getSentCost(amount, price, marketData)` (`packages/shared/src/helpers/market/market.helper.ts`): truncated to the amount step, the amount sent, then multiplied by the price in decimal, its cost, the two figures that the Trader's minimum warnings (`warnOfMarketMinimums`), the PositionBook's skip (`getBuyRefusal`) and the PositionTracker's `isSellable` compare with `amount.min` and `cost.min`. A message that quotes a value beside a bound writes it with `formatEveryDecimal` (`packages/shared/src/utils/string/string.utils.ts`): every decimal `String` gives it, without an exponent, where `formatAmount` (for a person, thousands grouped) and `toPlainNumber` (for a CSV cell) round to 8 decimals. A percentage shown to the user is written with `formatPercent(value, rounding)` (same file), the rounding taken from `PERCENT_ROUNDING` (`packages/plugins/src/analyzers/analyzer.const.ts`), one entry per figure, so that the CSV, the console tables and Telegram write a figure alike.
- `ORDER_SIDES` and `ORDER_TYPES` (`packages/shared/src/constants/order.const.ts`) are the one list of order sides and types: `OrderSide` and `OrderType` derive from them, and a new type does not compile until the Trader's `ORDER_FACTORY` has a class for it.
- `TIMEFRAME_TO_MINUTES` (`packages/shared/src/constants/timeframe.const.ts`) is the one list of timeframes: `TIMEFRAMES` (`packages/schemas/src/configuration/configuration.const.ts`) and `CandleSize` (`packages/shared/src/models/candleSize.types.ts`) derive from it. Its months and years are nominal (30 days a month), while those candles span whole UTC months: a timeframe in any unit but minutes, hours, days or weeks does not compile until `MONTHS_PER_CANDLE` (in `timeframe.const.ts` too) gives its months, a divisor of 12, and any other size until it has a case in the exhaustive switch of `getCandleTimeOffset` (`packages/shared/src/helpers/candle/candle.helper.ts`). `getCandleStart` and the batcher's `isTimeframeCandleClose` (`packages/core/src/core/batcher/candleBatcher/candleBatcher.helper.ts`: the offset of the next minute is 0) read that one calendar, so the warmup and backtest windows and the timeframe candles share their boundaries.
- `INPUT_SOURCES` (`packages/shared/src/constants/inputSources.const.ts`, below both the indicators that read it and the schemas that offer it) is the one list of price sources: `InputSources`, `checkInputSource` and the strategies' `src` parameter (`inputSourceSchema`, `packages/schemas/src/configuration/inputSource.schema.ts`) derive from it, so a source added there is typed, checked and offered by RSI, TMA, SMACrossover and EMARibbon at once. A new strategy with a `src` takes `inputSourceSchema.default('close')`.

## Architecture

### Boot and pipeline

`apps/gekko/src/gekko.ts` builds the run context and calls `gekkoPipeline({ context, plugins })` (`packages/core/src/core/pipeline/pipeline.ts`), `plugins` the registry of `@gekko/plugins/index` (`PluginRegistry`, `Record<string, PluginClass>`, in `pipeline.types.ts`: the core imports no plugin, and an entry of `plugins[]` naming no class of the registry is refused with the list of its names, `[PIPELINE] No plugin is named "trader" (did you mean "Trader"?): the plugins are CandleWriter, …`, an `UnknownPluginError` of `pipeline.error.ts`, beside `PluginModeNotSupportedError` and `PluginsEmitSameEventError`, the three refusals of the plugin entries, whose texts Fox quotes), which threads the configured plugin list through a fixed sequence of steps: the backtest's check that the database holds every minute of `watch.daterange`, read each plugin class's static configuration, mode compatibility, per-plugin zod parse, dependency and duplicate-emitter checks, a warning when a plugin creates orders that no plugin executes (a TradingAdvisor without a Trader), `exchange.loadMarkets()`, instantiate, wire events, inject services, then launch the stream pipeline for the mode. Its `signal` option (`gekkoPipeline({ context, plugins, signal })`) is the one way to end a run from code, and the only end of a realtime run but a failure or the circuit breaker's stop: aborting the signal destroys every stream of the run, lets the bucket in progress finish, finalises the plugins with the `AbortError` as their failure (the analyzers report its message as their `interruption`: `The operation was aborted`, as Node writes it, without the final period Bun 1.3.14 added), then rejects the run with that `AbortError` (its `cause` is the reason of the abort), unless a bucket failed meanwhile, whose error stays the run's. `main()` passes no signal, so SIGINT and SIGTERM keep their behaviour; the e2e harness ends its realtime runs with one.

A run reads its configuration and its services from its `RunContext` (`packages/core/src/run/runContext.types.ts`: `{ configuration, services }`, a `ConfigurationReader`, the getters of `Configuration`, and a `ServiceProvider`): no module-level singleton holds a configuration or a service, and `GEKKO_CONFIG_FILE_PATH` is read by `main()` alone.

- `createRunContext(raw, source = 'object')` (`run/runContext.helper.ts`) builds it from a configuration as a file holds it, or as code builds it (Fox's variants, the e2e flows): `parseConfiguration(raw, source)` (`configuration/configuration.helper.ts`) parses `raw` with `configurationSchema` and refuses it with a `GekkoError` (`Invalid configuration <source>:` followed by every issue, see below; `source` is `file <path>`, `variant <n>` or `object`), then `new Configuration(validated)` (`configuration/configuration.ts`: `showLogo()`, `getPlugins()`, `getStrategy()`, `getWatch()`, `getStorage()`, `getExchange()`) and `new Services(configuration)` (`run/services.ts`). `Services` builds the exchange of the exchange section and the storage of the storage section the first time each is asked for (`exchange()`, `storage()`), both with the watch section, and shares them from then on; a section missing or unknown is refused with the `configuration` tag (`[CONFIGURATION] Missing or unknown storage.`), and `closeStorage()` closes the storage only if one was created.
- `gekkoPipeline({ context, plugins, signal })`, the context required, hands it down. Every step takes the options, and those that read the run read `options.context`: the date range check (`getWatch()`, `services.storage()`), the modes (`getWatch().mode`), the plugin entries (`getPlugins()`), `preloadMarkets` (`services.exchange()`), `createPlugins` (`new PluginClass(parameters, context)`), `injectServices` (`plugin.set<Name>(services.<name>())`) and `launchStream` (`streamPipelines[mode](plugins, context, signal)`, `pipeline.helper.ts`), which builds the streams of the mode and hands each what it reads, never the context: `RealtimeStream({ exchange, symbol, startMinute })`, `MultiAssetHistoricalStream({ exchange, pairs, daterange, tickrate })`, which hands each pair's `HistoricalCandleStream` the same, `MultiAssetBacktestStream({ pairs, daterange, batchSize, storage })`, which hands each pair's `BacktestStream` the same (the backtest pipeline logs the start of the run once, at info level, naming the pairs, the range and the strategy of the strategy block when there is one: `Launching backtest of BTC/USDT and ETH/USDT from … -> to … using DEMA strategy`), and `PluginsStream(plugins, watch, exchange)`.
- A plugin keeps the context as `this.context` and hands it, or what it reads of it, to what it builds. The Trader hands `this.context` to each order it builds, its last constructor argument (`new LimitOrder(symbol, id, side, amount, price, context)`; a MARKET or a STICKY order takes the price it was sized from, which it does not use, as `number | undefined`), and reads `exchangeSynchInterval` from `context.configuration.getExchange()`; an order reads, once, as it is built, the exchange of `context.services.exchange()`, the mode of `getWatch()` and the `orderSynchInterval` of `getExchange()`, and keeps no reference to the context. The TradingAdvisor builds its `StrategyManager(strategyBlock, warmupPeriod, maxConsecutiveErrors)` from `context.configuration.getStrategy()`, so the manager reads no configuration of its own.
- The exchanges take their exchange section and the watch section (`new DummyCentralizedExchange(exchangeConfig, watch)`): `CCXTExchange` keys the balances of its pairs, the simulator keeps a book and a balance per pair and starts its clock at the start of `daterange` (at the time it is built without one, as in paper trading), and the paper exchange hands the watch section on to both. `SQLiteStorage` takes the storage section and the watch section (`new SQLiteStorage(storageConfig, watch)`, `StorageConfig` in `storage/storage.types.ts`, `Storage(storageConfig, { mode })` its base): a table per pair, read-only in a backtest, its `insertThreshold` defaulting by mode. Each types its watch parameter with the part of `Watch` it reads (`Pick<Watch, 'pairs' | 'daterange'>`, `Pick<Watch, 'mode' | 'pairs'>`, …), which a whole watch satisfies. Two runs in one process, as the e2e flows make, share nothing.
- `loadConfigurationFile(path)` (`configuration.helper.ts`) reads a file, its extension choosing the parser (`.yml`, `.yaml`, `.json` or `.json5`), and refuses an unsupported extension, a file it cannot read (none at the path, a directory, one the process may not read: `[CONFIGURATION] Cannot read the configuration file ./config/nope.yml: ENOENT: no such file or directory, open './config/nope.yml'`, without a cause, which the fatal error report would print with its stack), a file that does not parse and an empty file, each with a `GekkoError('configuration', …)`.

`configurationSchema` (`@gekko/schemas/configuration/configuration.schema`) is the source of truth for the config shape. Every section is a `z.strictObject` except the `strategy` block and the `plugins[]` entries, which the plugin's own strict schema parses, so an unknown key anywhere (a misspelt `sandbox`, say) refuses the file. Its refinements still read the entries where a rule spans sections: the names of the plugins configured (a `CandleWriter` requires the storage section, a `Trader` the disclaimer on a real exchange), the TradingAdvisor's `strategyName`, which the `strategy` block's `name` must equal, and the `benchmarkAsset` of a PortfolioAnalyzer or a RoundTripAnalyzer, which must be one of `watch.assets` (see Plugins). A YAML file is loaded with js-yaml's core schema, so an unquoted timestamp stays text, like a quoted one, for the schema to check (merge keys `<<` and js-yaml's `!!timestamp`, `!!set`… tags are not supported). A `watch.daterange` bound is a day (`2024-01-01`, its midnight UTC) or a day and a time with `Z` or an offset (`2024-01-01T00:00:00Z`, `2024-01-01T02:00:00+02:00`), checked against the calendar: `2023-02-29`, `24:00` or a `+25:00` offset is refused rather than rolled over to another day. The range must end in the minute of its start or later, in every mode; both minutes are read, so equal bounds are one minute. Assets, the currency and symbols are written in upper case: Latin capitals, digits or the letters of a script without case, a symbol being two of them around one slash (`pairConfig.schema.ts`). A list read into a Map by a key (`simulationBalance` by `assetName`, `marketData` and `initialTicker` by `symbol`) refuses a repeated key (`refuseRepeatedKeys`, `exchange.schema.ts`), and every `simulationBalance` asset must be a watched asset or the currency. An invalid file is a `GekkoError` naming the file, followed by every issue with its path (`z.prettifyError`, one per line); an invalid plugin entry is reported the same way, with the plugin's name and index. A file that does not parse is refused in one line, naming its format and the file, with the parser's reason and the line and column of the fault (`[CONFIGURATION] Invalid YAML in configuration file ./config/live.yml: bad indentation of a mapping entry at line 9, column 18`), without quoting the file and without a cause: js-yaml's own message quotes the lines around the fault, credentials included, and the fatal error report prints a cause in full.

`main()` (`apps/gekko/src/gekko.ts`) reads `GEKKO_CONFIG_FILE_PATH` (a `GekkoError`, `[CONFIGURATION] Missing GEKKO_CONFIG_FILE_PATH environment variable`, when it is unset), builds the run's context from the file (``createRunContext(loadConfigurationFile(path), `file ${path}`)``) and runs `gekkoPipeline({ context, plugins })`, importing the configuration helpers, the pipeline and the plugin registry inside its `try`, so that a configuration error, or a module that fails to load (a strategy of `custom/` that imports a path that is gone), is reported like any other failure; a static import of the registry would throw before the handlers exist, so do not add one. It is also the only place of the bot that reports a fatal error and decides the exit code. Its `catch` and its process-level handlers share one formatter with Fox's, `logFailure(tag, failure, prefix?)` (`@gekko/core/logger/failure.helper`), called under the `gekko` tag: a `GekkoError` is logged as its one-line message at error level (its stack at debug level), anything else with its name, message and stack, and what caused it is appended in full, down to the root cause: the cause of each Error (`Caused by: <its stack>`) and each error an AggregateError holds (`Error 1 of 2: <its stack>`: the failures of the plugins that failed to finalize, which the run's failure carries as one AggregateError), each followed by its own causes, an Error already listed (a chain that loops, an aggregate that holds itself) not listed again. `describeFailure(failure)`, in the same file, is that error-level text without a prefix, which a Fox worker posts (see Fox). A wrapper passes the failure it wraps as `{ cause }` (`GekkoError(tag, message, options?)` takes `ErrorOptions`, and keeps `tag` and `untaggedMessage` beside its tagged `message`), as for the SQLite open failure or a plugin dependency that fails to load. An `uncaughtException` is logged and exits 1 at once, without finalising the plugins, once the storage is closed (a failure of that close is logged as `Could not close the storage: …`, and the process exits whatever the logger does); `Heart` failing to tick after the machine slept is no longer one: it emits `'error'`, the realtime stream destroys itself with it and the pipeline rejects, so the plugins are finalised. An `unhandledRejection` is logged and sets the exit code to 1 but does not stop the bot, because timer-driven tasks float promises that reject on a network blip.

### Candle streams

Data moves as 1-minute `CandleBucket`s (`Map<TradingPair, Candle>`, one candle for every watched pair) through Node object-mode streams assembled in `packages/core/src/core/pipeline/pipeline.helper.ts`:

| Mode     | Chain                                                                                                                                                                                                     |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| realtime | warmup history, then live per-pair streams synchronised by timestamp → RejectFutureCandle → RejectDuplicateCandle → FillCandleGap (drops the leading buckets that miss a pair never seen) → PluginsStream |
| backtest | SQLite reader → PluginsStream                                                                                                                                                                             |
| importer | exchange OHLCV history → RejectFutureCandle → FillCandleGap (leaves out a pair whose history has ended) → PluginsStream                                                                                   |

A history range (`HistoricalCandleStream`) is inclusive on both ends, so equal bounds mean one minute. The realtime pipeline reads the clock once: the warmup history runs from the start of the candle `warmup.candleCount` candles before the one in progress (`getCandleStart`, on calendar boundaries for `1M`, `3M`, `6M` and `1y`) to the minute before the one in progress, and the live streams start at the minute in progress, so the two ranges neither overlap nor leave a gap. `HistoricalCandleStream` pulls one page per `_read` with `tickrate` as the minimum interval between requests. An empty page after some data ends the history with a warning naming how many minutes of the range it leaves out, the last page warns likewise about the minutes the exchange skipped before the end of the range although it has later candles, and the first page warns once of the minutes before the first candle the exchange has from the start of the range on, naming them and that candle (a pair listed during the range; a first candle after the whole range gets that one warning, `starting the history of this pair after the range`, where the end-of-range warning spoke of an early end); those minutes stay missing too, the gap filler filling a pair only from its last candle, and the warning comes in realtime as well, for a warmup history that starts late, beside FillCandleGap's drop warnings; a gap longer than `MAX_GAP_FILL_MINUTES` between two candles of the range fails the stream at once, so that an import never stores a week of flat candles before the refusal. A live stream ticks on each minute boundary plus `REALTIME_GRACE_PERIOD` (`packages/shared/src/constants/realtime.const.ts`), asks for every closed minute since the last one it pushed, oldest first (a failed fetch is retried on the next tick, never pushed as a made-up candle, and a late tick catches up instead of skipping a minute), ignores the minute in progress, and destroys itself with a `GekkoError` after `REALTIME_MAX_TICKS_WITHOUT_CANDLE` minutes without a candle, so a pair that stops delivering stops the bot instead of freezing it; until then the buckets wait for it, so that no pair's minutes reach the plugins between that pair's last candle and the stop. `FillCandleGap` fills a missing minute with a flat candle marked `synthetic`, but never a pair more than `MAX_GAP_FILL_MINUTES` (7 days) after its last candle, missing alone or with every pair: the bucket that would is refused with a `GekkoError` naming the gap (and the pair, but for a gap of every pair longer than that) before anything of it is pushed, and the writes still queued are ignored. In the importer it leaves out a pair whose stream has ended (`hasEndedBefore`, which `MultiAssetStream` answers from `synchronizeStreams`' `onPairEnd` by comparing the start of the pair's last candle with the bucket's minute), so a pair whose history ends early keeps its remaining minutes missing; in realtime it fills such a pair until its live stream takes over. A partial gap still open when the stream ends is summed up in a warning. In realtime it also drops the leading buckets that lack a pair it has never seen a candle for (one warning per such pair at the first drop, one summary at the first minute pushed), so the plugins only ever get complete buckets; the importer lets such buckets through. `pipeline.helper.ts` makes the three pipelines reject with the error of the failed bucket rather than with an upstream one. In every mode the per-pair streams are merged by `synchronizeStreams` (`packages/shared/src/helpers/stream/stream.helper.ts`), each bucket holding the pairs in the order of `watch.assets`: a pair's stream that ends lets the others go on and is reported to `onPairEnd` with the start of its last candle, one that fails fails the pipeline with its error, and one that closes without ending, or delivers a candle whose start is not a finite number, fails it with a `GekkoError` naming the pair (its position among the streams when it closes before its first candle), rather than leave the pair out of the buckets (in realtime, filled with flat candles forever) or stall them.

Aggregation to `watch.timeframe` is not a stream stage. It happens inside the TradingAdvisor plugin (`CandleBucketBatcher`), which throws a `GekkoError` if a bucket misses a watched pair, mixes minutes or does not follow the previous bucket by one minute, and which skips the minutes before the first timeframe boundary (with one warning for the bucket, whatever the number of pairs) rather than emitting a partial first candle; the per-pair `FastCandleBatcher` skips them without a word (Supervision batches an exchange's minutes with one).

For every bucket, `PluginsStream` (`packages/core/src/core/stream/plugins.stream.ts`) does three things in order: the simulated exchange, if one is configured, consumes the bucket and fills orders; every plugin's `processOneMinuteBucket` runs concurrently; then the deferred events are flushed plugin by plugin, in config order, a plugin with nothing queued skipped (`hasDeferredEvents()`; in backtest the Trader counts its reports in flight as queued). In realtime, from the second bucket on, the same pass also runs between the first two: once the simulated exchange (paper-binance) has consumed the bucket, what the plugins queued since the previous flush is delivered before their `processOneMinuteBucket`, such as the end of an order whose report floated between two buckets (`deliversQueuedFirst`, the mode of the `watch` section the pipeline builds the stream with). Not in a backtest, whose Trader awaits its reports before its flush: there, a delivery before the hooks would bring the fills the simulator settles as it consumes a bucket before that bucket's candle, and, before the simulator, an order hook's orders (GridBot's grid) would trade on the bucket a candle early. Nor before the first bucket, whose prices the analyzers need to value the Trader's start-up read.

### Plugins (`packages/plugins`)

A plugin extends `Plugin` (`@gekko/core/plugin/plugin`), implements `processInit`, `processOneMinuteBucket` and `processFinalize`, and exposes a static `getStaticConfiguration()` returning `{ name, schema, modes, dependencies, inject, eventsHandlers, eventsEmitted }`. Its constructor takes `(parameters, context)`, the output of its schema and the run's `RunContext`, and calls `super(name, context)`: the base reads the watch section (timeframe, warmup, mode, pairs, assets, currency) and the strategy block from `context.configuration` and keeps the context as `this.context`, for what the plugin builds. No plugin imports the configuration or the services. `packages/plugins/src/tradingAdvisor/tradingAdvisor.ts` is a good reference.

- Registry: the exports of `packages/plugins/src/index.ts`, which the bot and Fox hand to `gekkoPipeline` as its `plugins`. `plugins[].name` in the config must equal the exported class name exactly; an unknown name is refused with the list of valid names. The entry is parsed by the plugin's zod `schema` (`packages/schemas/src/plugins/<name>.schema.ts`, `analyzer.schema.ts` for both analyzers, a `z.strictObject`: a misspelt or retired option is an error, not a silent default) and the result is the constructor's first argument.
- Wiring is by name: an emitted event `orderCompleted` is bound to the `onOrderCompleted` method of every plugin that has one. Handlers are discovered on the prototype, so they must be methods, not arrow-function properties. Event names live in `packages/shared/src/constants/event.const.ts`, payload types in `packages/shared/src/models/event.types.ts`.
- An event can have only one emitting plugin. `PortfolioAnalyzer` and `RoundTripAnalyzer` both emit `performanceReport`, so they cannot be configured together. Both value the whole portfolio (`calculatePortfolioTotalValue`: the currency plus every watched asset at its close). Both analyzers take `benchmarkAsset`, the asset whose closes give the report's market return and its start and end prices: left out, BTC when it is watched, else the first asset of `watch.assets`; an asset that is not watched is refused by `configurationSchema`, at `plugins[i].benchmarkAsset` (`benchmarkAsset must be one of the watched assets (BTC and ETH), got "SOL"`), so that the loader refuses the file and Fox the variant before any run (one not written as an asset, `btc`, is left to the analyzer schema, the rule standing down while a section has an issue), and again as the plugin is built, for a context the schema did not check, a suite's literal one (`pickBenchmarkAsset`, `packages/plugins/src/analyzers/analyzer.helper.ts`: `[PORTFOLIO ANALYZER] benchmarkAsset must be one of the watched assets (BTC and ETH), got "SOL"`), and the PerformanceReporter writes it in the `benchmark asset` column of both reports' rows. Both reports carry it (`Report.benchmarkAsset`, `''` in an empty report). The RoundTripAnalyzer keeps one `RoundTripTracker` (`roundTripAnalyzer/roundTripTracker.ts`) per watched pair, which the order events reach by `order.symbol` and the candles by their pair, and reports on every pair at once: the whole portfolio's balances, the win rate and the returns of every pair's round trips, the exposure as the union of their intervals, the ids in the order they close across pairs, and a `pairs` breakdown (`PairTradingSummary`), printed as a second console table on several pairs, and its report table names the benchmark (`benchmark` row). A round trip's `pnl` is `proceeds − cost − fees` of its own fills, in decimal, and its `profit` that in % of `entryEquity`, the whole portfolio's value before its opening BUY, NaN when the Trader had read no portfolio by then: the round trip then counts in the win rate, not in the returns. A round trip holds a position, what its BUYs bought less what their fees took of the asset (`feeTakenInAsset`) less what its SELLs sold (`OpenRoundTrip.position`), and a SELL counts for no more than it: what an all-in SELL sells of an asset held before the round trip, or a SELL of the gross amount a BUY reported (a trailing stop's) sells of the other coins, counts in no round trip, its share of the proceeds and of the fee left out with it (a debug line); counted whole, the sale of that holding was the round trip's profit, at no cost. The part of a BUY fee the exchange takes in the asset bought (Binance without BNB, or the trades after its BNB ran out partway through a BUY) is left out of `fees`, the position holding that much less: `feeTakenInAsset` on `orderCompleted` gives its `amount`, which the position loses, and its `value`, its part of the fee, which `fees` leaves out (`RoundTripTracker.countBuyFee`, a debug line; 0 counted when the value is the whole fee within `compareWithTolerance`, a rebate leaving the fee whole); counted in both, it understated the P&L. A fee taken in a third asset (BNB) counts 0, as the Trader reports it, whether the whole fee of an order or the part some of its trades paid so: no rate converts it, and the analyzers value no asset that is not watched, BNB kept for the fees among them, so that a round trip's P&L agrees with the portfolio they value (1 BTC bought at 100, its first trade paying 0.0001 BNB and its second 0.0005 BTC, then sold at 100 for a fee of 0.09995, makes -0.14995, where the account made -0.18745 with the BNB at 375). The tracker ends a round trip once what is left of its position, but no more than the account holds of the asset after the order as the balance its event carries shows, is dust (`DUST_TOLERANCE`, 1 % of the amount its BUYs bought). It reads that balance only while no other SELL of the pair is pending, initiated (`orderInitiated`, which the analyzer listens to) and not yet heard to end, and from a read the Trader does not say it made before the order's end (`exchange.portfolioReadAfterOrder` not false, `RoundTripTracker.heldAfter`; compared, the date of the fill, on the exchange's clock, and that of the read, on the host's, took fresh reads for stale ones under a host's clock behind the exchange's), the round trip ending on its own amounts otherwise: two SELLs of one candle share the read after both, which ended the round trip with the first one's proceeds alone. What that balance shows gone of the position beyond that dust, sold by a fill no event reported (an order ended in error whose creation's outcome was unknown, a sale made outside Gekko), counts as sold at the last close of the pair, without a fee, with a warning naming the pair and the amount (`reconcileWithBalance`), and a BUY that finds the position so gone ends that round trip before it opens the next, rather than merge the two. An order ended in error after a fill counts for the part it filled, as a canceled one does (`registerErrored`). The report's win rate adds up the wins of the pairs' breakdowns (`summarize`), the one place a win (a P&L above 0) is decided.
- `processFinalize(failure?)` receives the error that stops a run before its end (a crash, `MissingCandlesError`, the circuit breaker, an aborted `signal`): the analyzers then set `interruption` on their `performanceReport`, `PerformanceReporter` writes it in the `status` column of its CSV rows (`interrupted: <message>`, `completed` otherwise), and with `enableConsoleTable` the analyzers print it on a line above their table, at any log level (`Run interrupted, the report below covers a partial period. Reason: <message>`). A `processFinalize` that throws fails a run that ended normally (exit 1, see Exit codes); after a failed run it is logged at error level, naming the plugin. The PerformanceReporter's fails the run when a row was not written (`unwrittenReports`: the file not locked within `LOCK_WAIT_MS`, its first line not the header, a write that failed, each logged at error level as it happens), with a `GekkoError` naming each row and its cause (`The TRADING REPORT row was not written: <file> could not be locked (see the error logged above)`), checked once the rows are written: the reports come from the analyzers' `processFinalize`, which `finalizePlugins` starts with every plugin's in one synchronous pass in config order, each analyzer emitting before it awaits anything, so a reporter listed after its analyzer has its report by then, and one listed before it, or the second of two reporters, a microtask later (the emit awaits each listener), all before the next macrotask, after which (`await setImmediate()`, `node:timers/promises`) `processFinalize` awaits the writes of the rows (`rowWrites`, through `Promise.allSettled`), each having waited for the lock of the file as long as it took. `onPerformanceReport` returns the write of its row, which the analyzer's emit awaits, and which rejects only for a report its columns cannot write, which the analyzer logs, as the analyzers catch what a listener throws (below). `Supervision`'s `candle_check` subscription also alerts on Telegram when no 1-minute bucket came for `candleStaleThreshold`. The PerformanceReporter takes an optional `label` (`performanceReporterSchema`, a non-empty string), written after the strategy block's values in the `id` column, in parentheses (`generateRowId`: `DEMA-12-100--150 (--exchange.marketData.0.marketData.fee.maker 0.01)`), the columns the same either way: it tells apart the runs of one strategy block, and Fox sets it to each variant's values.
- Delivery is deferred: plugins queue events with `addDeferredEmit(name, payload)` and handlers receive an array of payloads when the queue is flushed after the bucket (in realtime, what was queued between two buckets also before the next one's hooks), each handler its own copy, so that one writing to it changes nothing for the others. The payload is copied when queued, by `copyPayload` (`packages/shared/src/helpers/event/event.helper.ts`), which copies plain data by hand and anything else with `structuredClone`, and refuses what `structuredClone` refuses, a function or a symbol (a `DataCloneError`). The payload of an event nobody listens to is queued uncopied: a listener added before its delivery would get a copy made then, which never happens in a run, the pipeline wiring every listener before the stream starts. A listener added during an emit or a delivery is called from the next one on. Nothing is flushed after `processFinalize`, so events sent from there use `emit` directly and carry a single payload, the same object for every listener, not a copy. The analyzers await that emit, both through `emitPerformanceReport` (`packages/plugins/src/analyzers/analyzer.helper.ts`): a listener that fails is logged at error level (`A listener failed on the performance report: …`) and the run ends as it would have. The one exception is a strategy's error line: `tools.log('error', …)` fails the bucket, whose deferred events are then dropped, so the TradingAdvisor emits that `strategyInfo` at once, as an array of one.
- Config order matters. Each delivery is one pass over the plugins in config order, so an event queued on a plugin whose turn is over waits for the next pass: in a backtest the flush of the next bucket, one minute later; in realtime the flush after the hooks when it was queued in the delivery before them (an order an order hook places on the end of an order that floated), else the delivery before the hooks of the next bucket, one minute later. Keep `TradingAdvisor`, then `Trader`, then analyzers and reporters. Only the plugins that emit in answer to another's events need that order (the Trader after the TradingAdvisor, the analyzers after the Trader): with the Trader first, a backtest's fills reach the strategy a bucket late and the last minute's fill never reaches the analyzers. Those that emit nothing (PerformanceReporter, EventSubscriber, Supervision, CandleWriter) can go anywhere.
- Order reports are asynchronous (the order classes settle through callbacks or polls). In backtest the Trader waits for its pending reports before its queue is flushed and again in `processFinalize`, so a fill reaches the strategy and the analyzers in the bucket it happened in, the last one included. In realtime they float: a report queues the end of its order between two buckets, and PluginsStream delivers it as the next bucket arrives, before the plugins process it. In paper trading a MARKET order's end comes as the next bucket arrives, and a LIMIT order's fill is read by its next poll (every `orderSynchInterval`, 20 s by default), its end heard as the bucket after that poll arrives. So the strategy, its position book and the analyzers know of every order the exchange ended before a bucket when they process it, as in a backtest. The exception is a report still waiting for the exchange as the bucket arrives (its summary's trades, or its synchronization's balance or tickers): it is heard after the hooks or with the next bucket, while the Trader may already size from the balance it read. The order hooks run before the candle hooks: a line an order hook logs is dated with the close of the candle the strategy processed last, the one before, and the orders it places go out after the hooks, with those of the bucket. The EventSubscriber's `Current price` of an errored or canceled order is that close too. The RoundTripAnalyzer reads a round trip's adverse excursion by the fill dates, from the one-minute candles that close after its BUY fills and by the time its SELL fills (`countCandle`, `roundTripAnalyzer.helper.ts`): a report that floats changes none, up to `LATE_FILL_CANDLES` (an hour) late. It prices the part a canceled order, or one ended in error, filled at the `fillPrice` the Trader relays, else at a LIMIT order's own price, else at the last close of its pair (`priceUncompletedFill`, `roundTripAnalyzer.helper.ts`): the `price` of a MARKET or STICKY order is only the one the strategy sized it from.
- Services named in `inject` (`exchange`, `storage`) are set after construction: use `getExchange()`/`getStorage()` from `processInit` onwards, not in the constructor. The base creates no service as it is built, and both throw `PluginMissingServiceError` until the pipeline has set them: `injectServices` calls `set<Name>(context.services.<name>())` for each name of the plugin's static `inject`, after `createPlugins` and `wirePlugins`.
- Modes: TradingAdvisor, Trader, PortfolioAnalyzer and RoundTripAnalyzer run in realtime and backtest; PerformanceReporter in backtest only; CandleWriter in realtime and importer; EventSubscriber and Supervision (both Telegram) in realtime only. Both take an optional `chatId` (`0` is refused); without it the bot warns at start-up, drops what was queued while Gekko was down, binds itself to the first chat that sends it a command from then on (logged at info with whose chat it is) and never rebinds, and anything sent before that is dropped. Each bot needs its own token (two pollers on one token get 409s). Both start subscribed to nothing and keep their subscriptions in memory: nothing is sent (for Supervision, no check runs) until the chat sends `/subscribe_all` or a `/sub_…`, and again after every restart. With `chatId` set, the commands the chat sent while Gekko was down (Telegram keeps them 24 hours) are handled at the first poll. The EventSubscriber answers `/portfolio` at once, subscribed or not, from the events alone (`inject: []`, no exchange call): the balances of the last read of the Trader's portfolio the events brought, with their age: the `exchange.portfolio` of any order event (`orderInitiated` included), whatever its balances, dated with its `exchange.portfolioReadAt` (`Balances read by the Trader at <read> (<age> ago)`; an event without one carries no read, the empty portfolio the Trader starts with), or a `portfolioChange`, which says nothing of its read, dated with its reception (`Balances read by the Trader, received at <reception> (<age> ago)`). The last one received is the newest read, the Trader queuing its events in the order of its reads: no read time is compared, which would hold every newer read out after a clock set back. `No balance received from the Trader yet …` without a Trader or before its first read arrives; each pair's last 1-minute close; the total value in the currency.

The trading loop for one bucket: TradingAdvisor builds the timeframe candle and calls the strategy → `strategyCreateOrder` → Trader creates a `MARKET`, `LIMIT` or `STICKY` order (`packages/core/src/core/order`) → `orderInitiated`, later one of `orderCompleted` / `orderCanceled` / `orderErrored`, plus `portfolioChange` → back into the strategy's order hooks and into the analyzers → `roundtripCompleted`, `performanceReport`. Strategies track their pending orders through those three terminal events, so every order has to end in one of them. Only the Trader emits them: with a TradingAdvisor and no Trader (a screener), no order ever ends, and a strategy that waits for its order to end before it advises again, as the built-in ones do, advises once per run on each pair. The pipeline warns about it at start-up (one `warn` line, hidden at the default `error` level) rather than refuse, since a strategy that never creates orders needs no Trader; a screener runs the Trader on `paper-binance`. `orderErrored` carries `filled`, `mayBeLive`, whether the order may still be live on the exchange, where Gekko follows it no more, and `fillPrice`, as `orderCanceled` carries it, never for a refusal (`reportErrored`); `orderCanceled` carries the cumulative fill and what was left of Gekko's own amount (not of the amount the exchange took, truncated to its step), both undefined when the exchange reported no fill (unknown, not 0), and `fillPrice`, the mean price of the fills reported for a LIMIT or STICKY order, left out without a priced fill and for a MARKET order, whose reported price can be the bound of its slippage. `orderCompleted` carries the fill as the Trader summarizes it (`amount`, `price`, `effectivePrice`, `fee` in currency, `feePercent`), `feeAsset` and `feeTakenInAsset`. Its fee is the fees of its trades added up, each in currency: the summary's rate is the mean of the trades' rates weighted by their costs (`getFeePercent`, `packages/core/src/core/order/order.helper.ts`), a fee taken in a third asset without a rate (BNB) at 0 with its trade weighing all the same, a trade that says nothing of its fee left out, so that the cost times that rate (`computeOrderPricing`) is their sum; weighted by the amounts of the rated trades alone, a BUY whose BNB ran out partway was charged the rate of its asset-paid trades on the whole amount. `feeAsset` is the asset the exchange took the fee in: the one every trade of the order that names its fee currency names (`createOrderSummary`; undefined when they name none or several, as the trades of a BUY whose BNB ran out partway, and for an estimated summary; `mapCcxtTradeToTrade` names a fee taken in the base or the quote of the market, Hyperliquid's fee tokens included (`UBTC`, `USDT0`), after the asset or the currency of the symbol configured, the names `fetchBalance` keys the portfolio by (`UBTC` on a pair written `UBTC/USDC`, which ccxt lists as `BTC/USDC`; `BTC` on one written `BTC/USDC`), and any other currency as the exchange names it; the simulator names the currency, which it takes every fee in), which the Trader's summary line (`Fee taken in: BTC,`), the Telegram `order_complete` message (`Fee: 0.1 USDT (taken in BTC)`) and DebugOrderScript's completed line name when it is not the currency. `feeTakenInAsset` (`FeeTakenInAsset`, `packages/shared/src/models/event.types.ts`) is what the fees took of the asset of the pair: its `amount`, the fee costs of the trades that name the asset as their fee currency (else their rate of the trade's amount), and its `value`, each at the price of its trade, its part of `fee`; undefined when no trade took its fee in the asset, and for an estimated summary. When the trades name several fee currencies, the asset among them, the Trader's summary line and the `order_complete` message name it instead (`Fee taken in: 0.0005 BTC and another currency,`, `Fee: 0.05 USDT (taken in 0.0005 BTC and another currency)`); DebugOrderScript's line does not. The `exchange` part of every order event carries `portfolioReadAt`, when the Trader read the balances of its `portfolio` (`Date.now()` once the exchange answered, the wall clock in a backtest too), undefined for the empty portfolio it starts with, and the end of an order `portfolioReadAfterOrder`, whether the Trader sent that read after the end and after the ends of the orders it relayed before (`getExchangeEvent`: `portfolioReadNumber`, the number of the synchronization that read the portfolio, above `relayedEndCount`, the greatest of the counts of synchronizations noted at those ends, since a completion waits for its summary before its read and can be relayed after the end of an order that ended after it): false when the read after the end failed and the event carries an earlier one, which may still count what the order reserved as used or miss what it filled (an order the Trader could not place, never sent, carries false too), undefined before any read, left out of `orderInitiated`. GridBot and the RoundTripAnalyzer read it rather than a time: a read sent between two ends, or a periodic one sent before an end and answered after it, is dated after what they waited on, and a clock set back dates a fresh read before it. `portfolioChange` stays a bare Portfolio, queued as the Trader reads it. `strategyCancelOrder` carries an `AdviceCancelOrder` (`packages/shared/src/models/advice.types.ts`): the `id`, and the `symbol` when the StrategyManager knows the order (created in this run by `createOrder`, the trailing stops' SELLs included, whose end it has not heard of yet, among the 10 000 most recent of those: `MAX_PENDING_ORDERS` in `strategyManager.const.ts`, beyond which the oldest is forgotten with the stop it asked for, a bound only orders that do not end reach, as without a Trader; forgotten before the order hook runs), left out otherwise; a `RoundTrip` names its `symbol`, the pair whose fills make it up, and carries their `cost`, `proceeds` and `fees`.

`ApplicationStopError` is the graceful stop (the circuit breaker): plugins are finalised, the reason is logged at error level and the process exits with code 0, so that a restart-on-failure supervisor leaves it stopped. `ApplicationStopError(tag, message)` takes its thrower's tag, as every `GekkoError` does: the breaker's stop reads `[STRATEGY] Max consecutive order errors reached (5)`. Any other exception thrown by a plugin or a handler finalises the plugins and ends the process with exit code 1. `PluginsStream` destroys itself with the error it caught, which is how `main` tells the two apart, and it also finalises the plugins that were initialised when a stream upstream fails. When several plugins fail on the same bucket, an `ApplicationStopError` is the failure reported, otherwise the first in config order, and the others are logged after the close reason. SIGINT and SIGTERM flush and close the storage, then exit with 130 or 143 without running `processFinalize`.

### Strategies (`packages/strategies`)

A strategy is a plain class, constructed without arguments, that implements any of the optional hooks of `Strategy<Params>` (`strategy.types.ts`, whose JSDoc gives the contract of every hook and tool). `StrategyManager` drives it, with the `TrailingStopManager` beside it in `packages/plugins/src/tradingAdvisor/`: both log through the core's logger, which the strategies package, beside the core in layer 3, may not import, and the TradingAdvisor builds the manager from the strategy block (see Boot and pipeline). A strategy imports `@gekko/shared`, `@gekko/schemas`, `@gekko/indicators` and its own package, never `@gekko/core` or `@gekko/plugins`, and logs through `tools.log`. Model a new one on an existing strategy such as `dema/`, or on the Complete Example of `documentation/custom-strategies.md`, whose TypeScript examples type-check again.

- `init` runs once, on the first one-minute bucket, before any timeframe candle: in realtime the first minute of the warmup history, in a backtest the first minute of `watch.daterange`. Its `candle` holds that minute's candle of every watched pair, in the order of `watch.assets`. It is the only place `addIndicator(name, symbol, params)` is available: called once `init` has returned, it throws a `GekkoError`. It throws one too for an unknown indicator, an unwatched pair, a parameter the indicator refuses (a required one left out included) or a third argument that is not a plain object (left out or null, an untyped strategy's parameters are `{}`, the defaults), so such a mistake stops the bot at start-up. Then on each timeframe candle: indicators update, `onEachTimeframeCandle`, then once warmup is over `log` and `onTimeframeCandleAfterWarmup`.
- `init` also gets `openOrders`, the orders open on each watched pair at start-up, which the TradingAdvisor's `processInit` reads with one `fetchOpenOrders` per pair (a failed read fails the start-up). The map is empty in backtest and paper trading, whose simulator starts empty, and the run does not follow those orders: the Trader follows only the orders of this run.
- Hooks get `candle` as a `Map` holding every watched pair, followed by one `{ results, symbol }` argument per indicator in `addIndicator` order. Results are typed `unknown`: `null` until the indicator has enough data, then complete on every candle (a number, or an object whose fields are all set), so one `=== null` check suffices. ROC and TRIX are the exception: `null` again on a candle whose base is 0. `watch.warmup.candleCount` counts timeframe candles and is unrelated to indicator periods, so always null-check.
- What a hook receives is the strategy's own copy (the candles, the indicator results, the portfolio, an order hook's event, a trailing stop's state, `openOrders`, `tools.strategyParams`, `tools.marketData`): writing to it changes nothing elsewhere.
- Realtime prefetches the warmup candles from the exchange. A backtest spends the first `candleCount` candles of its `daterange` on warmup, and the configuration refuses a backtest with a TradingAdvisor whose range holds no more whole timeframe candles than that.
- `tools.createOrder()` returns a UUID immediately; the outcome arrives later through `onOrderCompleted`, `onOrderCanceled` or `onOrderErrored`. The order is dated with the end of the minute being processed. It is sized by at most one of `amount`, in the asset, `cost`, in the currency (a BUY may spend it, the 5 % fee buffer included, sized as an all-in BUY of that currency, `getAllInBuyAmount(cost, price)`; a SELL sells `cost / price`, no buffer) and `allocation`, a percentage in (0, 100] of a balance as of the Trader's last synchronization, not of what the orders placed since leave: for a BUY, of the currency read (`FreeBalanceLeft.read`) plus what the Trader's own BUYs that read shows open hold of it (`heldByOpenBuys`, taken at each read: a BUY placed before that synchronization started and whose completion was not heard by then counts its amount at the price it was created with, its filled part included, one the strategy canceled before the read its filled part alone), then sized as a `cost`; for a SELL, of the asset read free, what an open SELL holds being that SELL's to sell. Omitting all three means all-in, which a BUY of `allocation: 100` is to the digit in its amount (with BUYs open at the read, its share is above what is left, and it is capped there with a warning). The order events carry `cost` and `allocation` as asked, beside the `amount` sized. It throws a `GekkoError`, which stops the bot, before it draws an id or relays anything: during the warmup (so always from `init`), for a key `StrategyOrder` does not declare (`ORDER_KEYS` in `strategyManager.const.ts`, checked before the pair whatever its value: the Trader ignored it, so a misspelt `price` made a LIMIT at the last price and a `quantity` an all-in order), for a pair that is not watched (a key of `tools.marketData`), a `side` or `type` outside `ORDER_SIDES`/`ORDER_TYPES` (ccxt's lower-case `'buy'` and `'market'` among them), an `amount`, `cost` or `price` given that is not a finite number above 0, an `allocation` given that is not one at most 100, more than one of `amount`, `cost` and `allocation` (`null` and `undefined` count as left out), or an invalid `trailing`.
- `trailing` applies to BUY orders only: a `percentage` in (0, 100), an optional `trigger` above 0, no other key. The stop is armed, from a copy `createOrder` took, when the BUY completes. A BUY that errors gets it for the fill the exchange reported, if any, with a warning either way, and a BUY canceled loses it, even after a partial fill. It trails each one-minute candle met as open, low, high, close, each price tested against the stop price before it raises the peak. `onTrailingStopActivated` fires when a high reaches `trigger` (at arming when there is none). When a price reaches the stop price, `StrategyManager` sends a MARKET SELL and hands its id to `onTrailingStopTriggered`: an order of the strategy's own from then on, to adopt as its pending SELL (`PositionTracker.adoptSell(orderId)`, or `PositionBook.adoptSell(orderId, state.symbol)` for the tracker of the stop's pair). Both trailing hooks get `tools` last.
- A triggered stop sells until its SELL ends. Completed for all of the stop's amount, the stop is over. Completed for less (the Trader caps every SELL to the free balance and to the market's one-order maximum, and the exchange truncates its amount to the step), errored or canceled, it is active again for the rest, from the peak and the stop price it triggered at, with a warning, also when the SELL errored while it may still be live (`mayBeLive`). It is over instead, said at info level, when that rest is too little to sell at the market's minimums (`isSellable`), whatever else the account holds and even when that SELL may still be live. It is over too when the portfolio after that SELL shows too little of the asset free to sell, while no SELL the strategy created pends on the pair (at info level after a completed SELL, with a warning after an errored or canceled one): that is how a stop ends whose SELL went through after all, or whose BUY's fee was taken in the base asset (`Strategy.onTrailingStopTriggered` has the details). A SELL the strategy created holds the stops of its pair while it pends (they trail but do not trigger), cancels them all once it completes, and releases them when it is canceled or errors.
- The Trader caps every SELL to the free balance it last read less what the SELLs it placed since take from it, with a warning, and sizes an all-in SELL from that remainder, so that neither a live fee taken in the base asset nor two SELLs of one asset between two balance reads (two stops on one minute, a stop's and the strategy's) get a SELL refused; once the SELLs placed since take the whole of the asset read, a SELL of an `amount`, a `cost` or an `allocation` is sent as asked, not capped to 0, with a warning naming that cause (`[<id>] SELL MARKET order of 1.5 BTC (50 % of 3 BTC): 1.5 BTC sent as asked, which the market refuses unless some of the asset is free by then (3 BTC free at the last synchronization, less 3 BTC for the SELLs placed since)`): it goes through should one of those SELLs be refused or canceled first; an all-in SELL is sent for 0 with its cause line, and nothing is warned of while no balance was read; a SELL by `cost` (`cost / price`, `toSignificantDigits`) or `allocation` (that share of the asset read) is an amount asked for, capped so, its warnings naming the key. It sizes an all-in BUY the same way, from the currency it last read less what the BUYs it placed since may spend (each its cost at its price plus the 5 % fee buffer, a BUY without an amount the budget it was sized from once capped at what is left, or what the market maximum costs at its price plus the buffer when that caps it; an order the strategy cancels after a partial fill (as its polls reported it) still takes what its fill took until the next read, the amount filled for a SELL, what that amount may spend at the order's price for a BUY (`getBuyBudget`), never more than it took when placed), with a warning, so that two all-in BUYs between two balance reads (two entry signals on one candle, two pairs of one currency), or a BUY then an all-in BUY, are not both sized from the whole currency: the second gets what is left, 0 once nothing is, which the market limits refuse. A BUY by `cost` or `allocation` is sized from a budget, its cost or its share of the currency read plus what the Trader's own BUYs open at that read hold, reserved or spent on their fills (so two BUYs of 50 % on one candle both go through in full, and so do two a synchronization apart while the first still rests), capped at what is left with one warning naming the key, the figure asked for and the currency left, with the all-in warning's breakdown (read, less what the BUYs placed since take) when there are some; when the market maximum caps it too, the one line is the maximum's, which keeps `above the free balance, sized from <free>` and drops the breakdown. It also caps every SELL, the trailing stop's included, and every BUY without an amount (all-in, `cost`, `allocation`) at the most the market takes in one order of its type (`amount.max`, narrowed for a MARKET order by `market.max`, Binance's MARKET_LOT_SIZE: see `getMarketOrderLimits`), with one warning naming the amount asked for and the maximum sent: the rest stays held, or unspent, for a later order, and the completed event carries the amount executed. A BUY with an amount is never capped: above the maximum, the exchange refuses it. Nor is an amount that is not a finite number, which only a price so small that the currency buys an infinite amount gives (5e-324, which createOrder lets through): it is sent as it is, for the exchange to refuse, whether the order is a SELL, an all-in BUY or a BUY by `cost` or `allocation` (`capBuyAtMaximum`, one cap for both BUY paths). An all-in order, a BUY by `cost` or `allocation` whose budget comes to nothing, or a SELL by `allocation` of no asset is warned of before the exchange refuses its amount of 0, with the cause: no balance read yet, none of the asset (or currency) free at the last synchronization, or the orders of its side placed since taking what was (an all-in BUY says that last one with its breakdown instead). An order by `cost` or `allocation`, or an all-in BUY, that the market refuses for one of its minimums is warned of before it is sent (`warnOfMarketMinimums`, through `getSentCost`): its amount truncated to the market's amount step as both exchanges send it, against `amount.min` (narrowed for a MARKET order by `getMarketOrderLimits`), then its cost at its price in decimal (95 % of a BUY's budget at most, not the budget) against `cost.min` (`toBound`), the amount first as the exchanges check them, one line at most; the exchange then refuses it, an `orderErrored` counting towards the breaker. The amount line ends `which the market refuses` (`[<id>] BUY MARKET order of 6 USDT: 0.00057 BTC at 10000 sent, below the minimum amount of 0.001 BTC of a MARKET order on BTC/USDT, which the market refuses`). The cost line ends `which the market refuses at that price`, the price it names: the Trader values the cost at the price of the order (the last close or the last synchronization's bid for a MARKET or STICKY order), while CCXTExchange checks a market order at its ticker's ask or bid and a limit order on its tick, so that in realtime the two can lie on either side of the minimum (a BUY of 5.3 USDT at a close of 62499 is sent as 0.00008 BTC, 4.99992 USDT, which passes at an ask of 62501); the simulator checks a market order at the close. When the step cuts the amount, either line says so after `… sent` (`, truncated to 0.00008 BTC on the amount step 0.00001 of the market`) and names the amount sent or its cost, the one the refusal names. The check skips an order sized to 0, which its cause warning covers, one the step cuts to 0, whose refusal names the step, an `amount` order, whose refusal names the amount the strategy chose, and an all-in SELL, which sells the asset free. An all-in BUY gets the same warnings, its line opening with `All-in BUY … sized from <currency left>` (`[<id>] All-in BUY MARKET order sized from 5 USDT: 0.0475 BTC at 100 sent, a cost of 4.75 USDT once 5 % is kept back for the fee, below the minimum cost of 10 USDT on BTC/USDT, which the market refuses at that price`), as a BUY of `allocation: 100` of the same amount does: it is the BUY of the signal strategies on one pair, and of the last pair to buy on several. Every figure of the Trader's lines is written with `formatEveryDecimal`: its sizing lines, and those of an order's summary, estimated summary, cancelation, refusal after a fill, partial fill and invalid price (an optional one through `formatFigure`, `packages/plugins/src/trader/trader.helper.ts`, which keeps `Fee percent: undefined,` for a fee rate no trade gave). Each sizing by `cost` or `allocation` is logged at debug level (the key, its base, the budget, the amount, the price). A share is of the balance as of the last synchronization (every `exchangeSynchInterval` in realtime, every timeframe in backtest, 10 minutes at least, and after each order's end), as all-in is.
- `tools.log` prints a line if `GEKKO_LOG_LEVEL` lets it through. `info`, `warn` and `error` lines are also relayed as `strategyInfo` (the EventSubscriber's `strat_info`) whatever the level, `debug` lines never. `tools.log('error', …)` relays the line, then throws a `GekkoError`: it is not just a log call. An unknown level is logged and relayed at `info`, after one warning. A message that is not a string (an untyped strategy) is logged, relayed and thrown as `util.inspect` writes it, two levels deep, on one line but for an Error's stack.
- `end(interruption?)` runs once at the end of the run, also when an error stops it (not on SIGINT, SIGTERM or an uncaught exception): `interruption` is then that error's message.
- `maxConsecutiveErrors` consecutive `orderErrored` events (a TradingAdvisor option, default 5, `-1` disables, `0` is refused) raise `ApplicationStopError` (`[STRATEGY] Max consecutive order errors reached (5)`), once the strategy's `onOrderErrored` has run for the last one. Every errored order counts, whatever its pair, GridBot's grid orders included; a completed or canceled one, of any pair, resets the count. A BUY the position book skips (on several pairs only) is never sent, so it counts for nothing.
- The class is chosen by the TradingAdvisor plugin's `strategyName`: the exported class name in the registry (`packages/strategies/src/index.ts`), or with `strategyPath` a named export of an external file. A file that cannot be imported (no file at the path, a package or a Gekko module it cannot resolve, a syntax error) stops the run with `[TRADING ADVISOR] Cannot import the strategy file <path>: <Bun's reason>`, an export it lacks with `Cannot find external <name> strategy in <path>`. The top-level `strategy:` block holds its parameters; its `name` selects nothing but labels the run (backtest log, PerformanceReporter rows), so the schema requires it to equal `strategyName`. A strategy class may declare a static zod `schema` (`StrategyConstructor` in `strategy.types.ts`; a built-in one imports its schema from `packages/schemas/src/strategies/`): `StrategyManager` parses the block with it, `name` removed, when the strategy is created, before any candle, refuses the run with a `GekkoError` listing every issue, and hands the strategy the schema's output (defaults applied, no `name`) as `tools.strategyParams`. Every built-in strategy and debug fixture declares one; without a schema the whole block, `name` included, is passed through unvalidated, so a misspelt parameter is silently `undefined`.
- A `strategyPath` file can import only types from Gekko (`@gekko/strategies/strategy.types`, `@gekko/strategies/trailingStopManager.types`, `@gekko/shared/models/…`: Bun drops type-only imports): the compiled executable resolves no `@gekko/…` path in a file it loads at run time, wherever the file, `bun run dev` resolves them only for a file inside the checkout, and the executable finds a package only through the `index.js` at its root (`zod` yes, `lodash-es` no). A strategy that needs Gekko modules, such as `PositionTracker` or `PositionBook`, lives in `packages/strategies/src/custom/` (custom-strategies.md, "Where Your Strategy Lives"). `apps/gekko/test/e2e/realtime/live-streams/warmupOrder.strategy.ts` and `apps/gekko/test/e2e/backtest/orderSteps.strategy.ts` (`OrderSteps`: orders of several pairs on candles of their own, or sized several ways on one candle, `steps: [{ candle, symbol, side, type, price?, amount?, cost?, allocation? }]`, all-in without any of the three) are `strategyPath` files of that kind, Gekko's types and zod only, which their flows load.
- The built-in strategies are the seven signal strategies (CCI, DEMA, EMARibbon, MACD, RSI, SMACrossover, TMA) and GridBot. The seven trade every pair of `watch.assets` (they traded the first alone, and warned of the others) through a `PositionBook` (`packages/strategies/src/helpers/positionBook/positionBook.ts`, a `private readonly book` field): `init` calls `book.track(params)`, then makes the same `addIndicator` calls on each pair of `book.pairs`, pair by pair in that order; every hook that reads candles or indicators loops over `book.pairs`, reading the pair's candle where it reads one (skipped when missing) and its results from `indicatorsBySymbol(indicators)` (`packages/strategies/src/helpers/strategy.helper.ts`: the hooks' indicator arguments grouped by pair, each pair's in `addIndicator` order); a strategy's signal state is kept per pair (a `Map<TradingPair, …>`, reset at `init`); and every line it logs about a pair starts with `[<pair>] `, the rest as it was (`[BTC/USDT] SMA crossed DOWN price (9950.00000 < 10000.00000) => BUY`), but for the position lines of its tracker, which start with the order's id (`[<id>] BUY order canceled: 0.9 BTC filled, enough to sell: the strategy is long`), as built-in-strategies.md says. GridBot alone trades the first pair: `init` takes it with `pickTradedPair(candle, tools)` (`packages/strategies/src/helpers/positionTracker/positionTracker.helper.ts`), which warns once when more pairs are watched, as a custom single-pair strategy can.
- The book keeps one `PositionTracker` per pair, and the seven trade through it: they buy only when flat and sell only when long on a pair (`book.canBuy(pair)`/`book.canSell(pair)`, false for a pair it does not track), never while an order of their own is pending on that pair, place their orders through `book.buy`/`book.sell({ type, symbol: pair }, params)`, the hook's params whole, and hand it the params of their three order hooks whole, which it dispatches to the tracker of `order.symbol`. A BUY takes an equal share of the free currency among the tracked pairs not long, a pair whose BUY is pending counted, since two BUYs of one candle are sized from one balance read: its `allocation` is `round(100 / n, SHARE_DECIMALS, 'down')`, 6 decimals, so the shares of a candle never sum above 100 %, and with n = 1 (a single pair, the last entrant) the BUY goes all-in, today's order, without `allocation`; a SELL stays all-in. The Trader sizes that `allocation` from the currency read plus what its own BUYs open at that read hold of it, reserved or spent on their fills (see the Trader's sizing above), so that a share does not depend on whether a synchronization fell between two BUYs, a STICKY BUY resting across one. On several pairs only (`this.pairs.length > 1`), a BUY the market would refuse is skipped, nothing sent or pending (`buy` returns undefined): one whose estimated cost, its budget (`getAllocatedShare` of the currency in `params.portfolio`: its `free`, plus what the Trader adds back for its own BUYs open at its read, as the book estimates it: the book records with each BUY it places, on several pairs and from a portfolio that lists the currency, what the Trader holds for it, its budget × `BUY_COST_SHARE`, the Trader's amount at its creation price to 15 significant digits, with the read of the currency it was sized from, forgets it at the BUY's outcome, and adds that of each BUY still pending that was sized from another read, one before the hook's, whose `free` or `used` differs (`getHeldByOpenBuys`; `isSameRead` in `positionBook.helper.ts`), not that of a BUY sized from the hook's read, placed after it, which the Trader leaves out too; all of the `free` for the last entrant's all-in BUY, which the Trader sizes from what is left) × 0.95 (`BUY_COST_SHARE`, 1 − `DEFAULT_FEE_BUFFER`, both in `packages/shared/src/constants/order.const.ts`), is below `toBound(cost.min)` of its market, or whose amount as the Trader would send it, `getAllInBuyAmount(budget, price)` at `order.price ?? candle.get(symbol).close` truncated to the market's amount step (`getSentCost`, `packages/shared/src/helpers/market/market.helper.ts`; the limits of a MARKET order narrowed by `getMarketOrderLimits`), is below `amount.min` or costs less than `cost.min`, worked out by `getBuyRefusal` (`packages/strategies/src/helpers/positionBook/positionBook.helper.ts`; the book's params carry the hook's `candle` for that price). The first skip of a pair is a warning (`[BTC/USDT] BUY skipped: 33.333333 % of the 25 USDT free, 7.9166665875 USDT once 5 % is kept back for the fee, is below the minimum cost of 10 USDT of the market: watch fewer pairs or fund the account; the next skips of this pair are logged at debug level until a BUY of it is placed`; for the amount sent, `…, 5.7 USDT once 5 % is kept back for the fee, 0.00005 BTC at 97654.32 once truncated to the amount step 0.00001 of the market, a cost of 4.882716 USDT, is below the minimum cost of 5 USDT of the market: …`, or `…, 0.00057 BTC at 10000 once truncated to the amount step 0.00001 of the market, is below the minimum amount of 0.001 BTC of the market: …`; while a part is held, the share names it as the Trader's sizing lines do (`[ETH/USDT] BUY skipped: 50 % of 30 USDT: 15.75 USDT free at the last synchronization, plus 14.25 USDT held by the BUYs open then, 14.25 USDT once 5 % is kept back for the fee, is below the minimum cost of 15 USDT of the market: …`), the line otherwise as it was; the part named is the Trader's figure whatever the exchange holds for that BUY, its `used` less once the BUY has partly filled or the exchange truncated its amount to the step, more by the maker fee the simulator holds with it, by a STICKY BUY's tick and moves above its creation price, or by orders Gekko did not place, figures the book went by until it skipped BUYs the Trader sized above the minimum and sent BUYs the Trader sized under it; it still differs from the Trader's where the Trader caps a budget, at what its BUYs placed since its read leave or at the market maximum, for a BUY the strategy canceled before the read, of which the Trader counts the fill, and when the hook's portfolio is not the Trader's last read, one `portfolioUpdates` held back), and its next skips are that line without its suffix, at debug, until a BUY of that pair is placed (no skip without a minimum cost or amount on the market, nor when the portfolio does not list the currency, and no check of the amount sent without a price above 0; every skip line writes the free currency with `formatEveryDecimal`). A BUY skipped while the portfolio shows enough of the pair's asset free to sell at the close makes the tracker long instead (`PositionTracker.adoptHolding(held, close, type, marketData)`, on `isSellable`, only while the tracker is flat with nothing pending), said at info in place of the warning, so that a holding present at start-up is sold at the next SELL signal (`[BTC/USDT] BUY skipped: 50 % of the 8 USDT free, 3.8 USDT once 5 % is kept back for the fee, is below the minimum cost of 5 USDT of the market, but 0.002 BTC is free in the portfolio, enough to sell: the strategy is long`). Otherwise the strategies treat a skip as a refused BUY without the refusal: DEMA, MACD, RSI and CCI wait for the next trend and SMACrossover for the next crossover, while TMA and EMARibbon ask again on each candle of their signal, the book logging its skip at debug. A skip leaves the book's line as its only trace: DEMA, SMACrossover and TMA log their advice line (`[BTC/USDT] Executing long advice due to detected uptrend: …`, `[BTC/USDT] SMA crossed DOWN price (…) => BUY`, at info, relayed as `strategyInfo`) only once `book.buy` has returned an id, the BUY placed, so the TradingAdvisor queues that BUY's `strategyCreateOrder` before the `strategyInfo` of its line (on Telegram, its `strat_create` notification comes before its `strat_info` line); CCI, MACD, RSI and EMARibbon log no line that says the BUY was placed. A book of one pair never skips: its all-in BUY is sent and refused as before, which is how the tracker learns of a holding present at start-up and how an unfunded account trips `maxConsecutiveErrors`. With several pairs, `track` logs one info line naming them and the rule (`Trading BTC/USDT and ETH/USDT: each BUY takes an equal share of the free currency among the pairs not invested, each SELL sells all of its asset`). A completed BUY makes the tracker long, and a completed SELL flat once it sold all it asked for; one that sold less (the Trader's caps), and every all-in or adopted SELL, is read from the portfolio after it, long when the asset left free is enough to sell, said at info level. An order of theirs that ends canceled or errored may have executed: the tracker then reads the position from what a canceled BUY filled, and otherwise from the free balance of the asset in the portfolio after the order, a SELL canceled after a fill included, since its fill tells what is left of the order, not of the holding (a SELL by `cost` or `allocation`, or capped at the market maximum, sells part of it), though never below what that SELL left unsold, which the cancelation released (a portfolio that shows less, or does not list the asset, was read before it); a SELL of an `amount` sent for all of it reads its fill alone, that amount being the position, as when it completes (`coversAmountAsked`, `positionTracker.helper.ts`). It is long when that is enough to sell at the market's minimums, and logs a change at info. They start flat on every pair, so a holding present at start-up is sold only once a BUY of theirs on its pair has ended, completed, or refused or canceled while the account held enough to sell, or has been skipped, on several pairs, while the portfolio showed enough of the asset free to sell. The original Gekko discarded a repeated same-side advice; Gekko relays every advice, so a strategy without that tracking re-advises an all-in BUY on every candle of a trend until the refusals trip the breaker.
- What a strategy compares with the previous candle (EMARibbon's spread, SMACrossover's side of the SMA, each kept per pair) is recorded in `onEachTimeframeCandle`, which runs on the warmup candles too, so the first candle after the warmup is compared with the last warmup candle.
- GridBot keeps a grid of LIMIT orders in memory instead of a position. Every level trades one quantity: the largest amount on the market's amount step that the free balances fund on each side, the need worked out in decimal. Each level re-arms through the three order events: a fill places the opposite order one step away, a refused or canceled order is placed again up to `retryOnError` times, and an order that may still be live is never placed again. It refuses to start while orders are open on its pair, and its lowest-buy and price-tick checks run when the grid starts or is reset and again around the price a rebalance ended at, and `buildGrid` warns of a spacing under the round-trip fee (`checkRoundTripFee`) on the levels it builds, around the price it builds them at, whatever path builds the grid: one warning per grid built, once its rebalance has filled when it has one (around the price a BUY rebalance chasing a breakout ended at, the top level of an atr grid on its minimum step lost money without a word). With `spacingType: 'atr'`, its one indicator, the ATR of `atrPeriod` timeframe candles, is read on every candle, the warmup included (`this.atr`), and `resolveSpacing` (`gridBot.helper.ts`) turns `spacingValue` × that ATR into a `fixed` `GridSpacing` when the grid starts and at each reset: rounded to the tick at the center price and raised, with a warning, to `getMinimumStep`, the smallest step at which the highest level, the one that earns the least at a fixed step, breaks even on the maker fee, one tick at least (one tick too where no step breaks even, from 501 sell levels at 0.1 % or at a maker fee of 1 or more, the warning saying so: `…, instead; GridBot reads no clock for it: compared with the start of the reset, a read sent between two cancels, or a periodic one sent before the reset and answered after it, was dated after that start while it still counted what the last canceled order held, and a clock set back dated a fresh read before it.
- `packages/strategies/src/debug/` holds e2e fixtures, not built-in strategies: `DebugAdvice`, `DebugBacktest`, `DebugOrderScript`, `DebugPositionBook`, `DebugRealtime` and `DebugTrailingStop`, their schemas in `packages/schemas/src/strategies/debug/`. The e2e flows depend on their calendars and their lines, so change both together.
- A new built-in strategy is `packages/strategies/src/<x>/<x>.strategy.ts`, `<x>.types.ts` and `<x>.test.ts`, its static `schema` in `packages/schemas/src/strategies/<x>.schema.ts`, tested beside it in `<x>.schema.test.ts` (the strategy's own test checks only that the class declares that schema), plus an export in `packages/strategies/src/index.ts`. An all-in one trades every watched pair through a `PositionBook`.

`packages/strategies/src/custom/` holds private, local-only strategies. The directory is gitignored except for a tracked placeholder `index.ts` (`export {};`), which the `preinstall` script marks skip-worktree (`git update-index --skip-worktree … 2>/dev/null || true`, which does nothing outside a git checkout), so that local edits never show up in git and survive `git stash`, `reset --hard`, `checkout -- .`, `restore .` and lint-staged's revert, which overwrote them when the bit was assume-unchanged. A `git pull` that changes the placeholder is refused and keeps the copy: set the exports aside, run `git update-index --no-skip-worktree packages/strategies/src/custom/index.ts` and `git checkout -- packages/strategies/src/custom/index.ts`, pull, write the exports into the new placeholder, then `bun install` marks it again. Never stage or commit anything from it. `bun run type:check` and `bun run lint:check` check its files, but not the pre-commit hook, which checks the committed tree, where the placeholder exports nothing, nor `format:check` (Prettier skips what `.gitignore` lists); its tests run with a local `bun run test` but not in CI. A strategy kept there imports what the strategies package may (`@gekko/shared`, `@gekko/schemas`, `@gekko/indicators`, and its own package for the PositionTracker and the PositionBook), and `lint:check` refuses its imports of `@gekko/core` and `@gekko/plugins`. The examples of custom-strategies.md import the strategies package by its name (`@gekko/strategies/helpers/positionTracker/positionTracker`), which resolves from `custom/` as from anywhere in the checkout, where the package's own code imports it by a relative path: the docs test compiles the examples outside the package, where a relative path leads nowhere. A class kept there takes a name of its own: two exports of one name leave neither in the registry's namespace (TS2308).

### Indicators (`packages/indicators`)

An indicator extends `Indicator<Name>` (`indicator.ts`): it implements `onNewCandle`, which sets the inherited `result` that `getResult` returns, `null` until the output is complete, then complete on every candle, never a partial object or a placeholder (ROC and TRIX aside, `null` on a zero base). It declares its types by augmenting the global `IndicatorRegistry` interface in its `<x>.types.ts` with `{ input, output }`, a file `indicator.types.ts` imports (`import type {} from './<dir>/<x>.types'`, the line a new indicator adds, which `scripts/tooling/typeCheck.test.ts` checks). The registry key, the class name and the export in the registry (`packages/indicators/src/index.ts`) must be identical, because the runtime lookup is `indicators[name]`.

- A constructor checks its parameters before it builds anything, with the helpers of `indicator.helper.ts` (`checkInteger`, `checkNumber`, `checkOneOf`, `checkInputSource`, `checkBelow`, `checkAtMost`), each throwing a `GekkoError` that names the indicator, the parameter and what it accepts. An indicator built on others checks its own parameters first, so that the message names the one the strategy passed. An indicator with a `src` reads its price through `getInputSource(src)` (`indicator.helper.ts`), the close by default.
- A moving average extends `MovingAverage<Name>` (`movingAverages/movingAverage.ts`): it checks its parameters, passes `src` to `super` and implements `update(value)`, which the inherited `onNewCandle` calls with the candle's price. An indicator built on another feeds it its own values through `update`, never a made-up candle.
- A moving-average kind that indicators take as a `maType` is added to `MOVING_AVERAGES` (`movingAverages/movingAverages.const.ts`) and nowhere else: `MOVING_AVERAGE_TYPES`, `MovingAverageTypes` and `MovingAverageClasses` derive from it, and its `satisfies` admits only a `MovingAverage` built from `{ period }`. No moving average may import that file, even through a module it imports, such as `indicator.helper.ts` (`indicator.types.ts` names the map in a type-only import, which closes no cycle): the cycle would make the moving average loaded first throw "Cannot access … before initialization" under Bun, and leave it missing from the map under vitest.
- +DM, −DM, +DI, −DI and DX read one `DirectionalMovement` (`directionalMovement/directionalMovement.ts`), whose true range is `getTrueRange` (`volatility/trueRange/trueRange.helper.ts`), as TrueRange's is. These helpers, like `MovingAverage`, are not exported by the registry, so they are not `addIndicator` names.
- `RingBuffer` (`@gekko/shared/helpers/collection/ringBuffer`), the window of ROC, Williams %R, CCI, Stochastic and Bollinger Bands, is read in place: `first` in constant time, `max`, `min`, `sum` and `reduce` in one pass (`sum` and `reduce` oldest first), and its constructor refuses a size that is not a whole number of at least 1 with a `GekkoError` (`[CORE] RingBuffer size must be a whole number, at least 1, got 0`). A callback that needs a value of its caller goes through `reduce`'s `argument`, made once, rather than a closure made on every candle.

### Exchanges, orders and storage

- `exchange.name` picks the implementation, through a zod discriminated union (`packages/schemas/src/exchange/exchange.schema.ts`) and a switch in `Services.exchange()` (`packages/core/src/run/services.ts`): `binance` and `hyperliquid` use `CCXTExchange` (`sandbox: true` for testnets; the hyperliquid client is created with `builderFee: false`, otherwise ccxt signs a builder-fee approval at the first order and attaches a 1 bp fee to every one); `dummy-cex` is `DummyCentralizedExchange`, the backtest simulator; `paper-binance` trades simulated orders on live Binance data. A new CCXT exchange needs its schema (`packages/schemas/src/exchange/<name>.schema.ts`), a union entry, a case in `Services.exchange()` and a `LIMITS` entry in `packages/core/src/exchange/exchange.const.ts`, and ccxt must list every feature of `BROKER_MANDATORY_FEATURES` there in its `has`, which `checkMandatoryFeatures` checks as `CCXTExchange` is built. `fetchOpenOrders` is one of them: `fetchOpenOrders(symbol)` lists the orders open on a pair, whoever placed them (ccxt's live, the simulator's book in backtest and paper trading). `fetchMyTrades` leaves out, with one warning, a ccxt trade without an amount and a price above 0 (`isExecutedTrade`): read as 0, an unknown price entered the mean price of its order.
- The credentials are optional in the exchange schemas, an import reading the public client alone: binance's `apiKey` and `secret`, hyperliquid's `privateKey` (it signs the orders) and `walletAddress` (the account ccxt reads, and trades for). On hyperliquid, `privateKey` without `walletAddress` is refused, and in realtime the configuration requires `walletAddress` with a TradingAdvisor or a Trader and `privateKey` with a Trader (checked once the sections have no issue); binance's keys are not checked by plugin. A number at either hyperliquid key (an unquoted `0x…`, hexadecimal to YAML and JSON5) is refused with a message saying to quote it.
- The schema ties the exchange to the mode: backtest takes `dummy-cex` only, importer takes `binance` or `hyperliquid`, realtime takes `binance`, `hyperliquid` or `paper-binance`.
- The simulator's clock is the close of the last candle. It keeps one order book per pair. Limit orders fill in full once a candle's low/high reaches their price, market orders fill at the last close, and there are no partial fills or slippage. Fees and order limits come from `exchange.marketData`, which must hold exactly one entry per watched pair. Its `precision` is given as a number of decimals (`8`) that the schema converts to a step (`1e-8`), because `MarketData.precision` holds steps everywhere else, as ccxt reports them; an optional `precision.priceSignificantDigits` (Hyperliquid's 5) is handed on as it is. Before it checks the limits, the simulator puts an order on the steps of the market as `CCXTExchange` sends it (`roundToMarketPrecision`, `dummyCentralizedExchange.helper.ts`, on `roundToStep` and `getPriceTick`): the amount truncated to the amount step, the price rounded half up to the tick at that price. An amount truncated to 0, or whose cost falls under `cost.min`, is refused, the cost worked out in decimal (`multiplyPrecise`) by `assertOrderWithinLimits`, as both exchanges check it, so that an order costing exactly `cost.min` passes. An amount or a price rounded to nothing is refused as the order asked for it, with the step (`Order 'amount' with value 0.0000099 rounds to 0 on the amount step 0.00001 of the market. …`). An order fills, and is reported, for the amount truncated. The simulator charges the fee in the currency, on top of a BUY and out of a SELL's proceeds, names that currency in the executions `fetchMyTrades` lists (`fee.currency`, beside the rate), works out the currency of each order in decimal (amount × price × (1 ± fee), `multiplyPrecise`) and rounds it to 8 decimals (`COST_DECIMALS`), a half up, as Binance keeps its balances, and books every balance in decimal (`addPrecise`). Its refusal for want of funds names both figures with every decimal (`Insufficient asset balance (portfolio: 0.0000005, amount: 1)`). Its state sits behind an `AsyncMutex` (`packages/shared/src/helpers/async/asyncMutex.ts`), FIFO and not reentrant: a free lock runs the section at once, in the caller's tick, and an exchange call made by an `onSettled` callback runs once the bucket is processed. `MarketData.market`, when present (Binance `MARKET_LOT_SIZE`, which paper trading carries from the real market and a backtest states as an optional `market` range of its `marketData` entry, either bound optional, each checked as those of the other ranges are, and the range refused at `exchange.marketData[i].marketData.market` when it shares no amount with the amount range, which would leave every MARKET order refused: `market (at most 0.0005) and amount (at least 0.001, at most 1000) have no amount in common: a MARKET order must be within both, so the simulator would refuse every one`), narrows the amount range of MARKET orders; `CCXTExchange` and the simulator refuse such an order before sending it.
- Order classes are event emitters. In backtest they settle through exchange callbacks; in realtime, paper trading included, LIMIT and STICKY orders poll `fetchOrder` every `orderSynchInterval` from their creation, while a MARKET order settles from the answer to its creation, polled so only when that answer leaves it open (`… order still open after its creation, unexpected for a market order`, a warning). A creation is sent once and never replayed. One whose outcome is unknown ends the order in error with `mayBeLive` true, never as a refusal: lost on the network (`ExchangeNetworkError`), or `OrderOutcomeUnknown` when the exchange answered without anything to follow the order by, its state could not be read back, or ccxt threw an `OperationFailed` that is not a `NetworkError` (Binance -1000, -1006, a busy exchange). So does an order whose poll, cancelation or read-back fails for good while it is open. The reads of `CCXTExchange`, unlike its creations and cancelations, go through `retry`: after a ccxt NetworkError a read is sent again up to 3 more times, 1000, 1585 and 2000 ms apart (`getRetryDelay`, attempts numbered from 0 as the fetcher numbers its requests), each failure logged at debug level only, since the caller logs what it could not read at the level it deserves.
- Trader on a real, non-sandbox exchange is refused unless the config sets `'I understand that Gekko only automates MY OWN trading strategies': true` at its top level (the exchange section refuses the key as unknown). `config/realtime-trader.yml`, quick-start.md and modes.md write the key quoted, as the refusal message does: js-yaml also reads a flow sequence (`[I understand …]: true`) as the sentence, but other YAML parsers read a list, which the schema refuses as an unknown key.
- Storage is `SQLiteStorage` on `bun:sqlite`, the only Bun-specific API of the packages. It keeps one table of 1-minute candles per pair (`CANDLES_<ASSET>_<CURRENCY>`, upper-cased and always quoted in SQL, so tickers such as `1INCH` work), and `storage.database` is a path relative to the working directory. The `storage` section is required in backtest mode and whenever a `CandleWriter` plugin is configured, and ignored otherwise; `insertThreshold` is an integer number of minutes between 1 and 1440 (default 1 in realtime, 1000 otherwise) and `watch.batchSize` is bounded to 31 days of minutes. What replaces a stored minute depends on the mode and on the candle: an import replaces whatever is stored for the minutes the exchange returns, a minute without trades included, and its own made-up candle for a minute the exchange lacks only replaces a stored candle that is made up too (flat, volume 0); the other modes replace a stored candle only when it is made up, and only with a candle that traded, so a made-up candle never replaces one that traded. `open()` sets a 5 s busy timeout and reads `sqlite_master` before anything else, so that a file that is not a database, or one cut within its header, fails there with its path (`PRAGMA schema_version` passes a file cut within its 100-byte header). `close()` inserts the buffered candles, then closes the connection whatever that insert did, and only its first call does anything, a failed one included (main() closes the storage again after CandleWriter). A failed insert throws `[STORAGE] Could not write the buffered candles into <path> (<SQLite's error>): the minutes from <start> to <end> were not written, <count> of <pair>, …. An import of that range writes them.`, caused by SQLite's error, the count covering only the pairs it did not insert.

## Fox

Fox (`apps/fox`, `@gekko/fox`, compiled to `dist/fox`) backtests the variants of a template configuration side by side, each in a Bun Worker of its own, and the template's PerformanceReporter writes the results, one CSV row per variant. It runs from the root, where the template's relative paths (its database, its CSV) lead: `bun run dev:fox --template-path <template> --strategy.period 10..30:5` from source, `dist/fox …` compiled (`apps/fox` has no `dev` script of its own: run there, Fox would find neither path and read no `.env`); `documentation/fox.md` is its guide.

- `src/fox.ts`, the entry, parses the command line (`src/cli/cli.helper.ts`: commander with `exitOverride`, every refusal a `GekkoError` tagged `fox`, anything commander throws that is no `CommanderError` passed on as it is, for its stack to be reported): `-t, --template-path <path>` (else `FOX_TEMPLATE_PATH`), required (`[FOX] No template: give its path with --template-path <path> or FOX_TEMPLATE_PATH`); `-w, --max-workers <count>` (else `FOX_MAX_WORKERS`), a whole number of at least 1, `os.availableParallelism()` by default, an empty variable counting as unset; and `--help`, after which Fox exits 0. The rest of the command line are overrides (`parseOverrides`), `--<key> <values>` or `--<key>=<values>`, the key a path of the template written with dots: a single value sets it in every variant, and a list (`12,24`), a range (`12..24`, both bounds included, its step a unit of the bounds' last decimal as written, trailing zeros left out; `12..24:4` with a step, the end always tried: `12..24:5` is 12, 17, 22 and 24, counted and worked out on BigInts, its bounds and its step scaled to their decimals) or a list holding ranges (`10,20..30:5`) makes a variant of each value. Each item is typed: `true` and `false` are booleans, `-?\d+(\.\d+)?` a number, anything else a text; an item is a range only when it starts like a number (`/^-?\d/`) and holds `..` without a `/` or a `\`, so that `run..2`, `..` and a path (`../db/x.sql`, `2024..old/x.sql`) are texts, while `12..` is refused as a range; `12..12` is 12 alone. The values of an option are deduplicated (lodash-es' `uniq`, the first place kept): `1..10:3,10..30:10` tries 10 once, where it made two variants of one backtest, labelled alike. A stray argument (a second value, `--strategy.period 12 24`), a missing value, an empty list item, a key given twice or held in another (`--strategy.thresholds` and `--strategy.thresholds.up`), `__proto__`, `constructor` or `prototype`, and a malformed range (`12..`, `24..12`, `12..24:0`) are refused before anything runs. So are a number that no double holds as written, which Fox would otherwise have tried in place of the one written (a number keeps some 15 significant digits; checked by `toNumber`, the double's decimal `String` writes back compared on BigInts): a single value or a list item (`Invalid value "9007199254740993" of --x: it holds more digits than a number keeps, which reads it as 9007199254740992: write it with fewer digits`), a bound of a range (`its end, 9007199254740993, holds more digits than a number keeps, …`), or a value its step makes (bounds of 17 significant digits, whose default step is 1e-17, `0.30000000000000004..0.5`; a step below what its values can change by; whole numbers beyond `2 ** 53`: `its step of 1 makes 9007199254740993, more digits than a number keeps, which reads it as 9007199254740992: write the bounds with fewer digits, or give a larger step`), the first step checked before the count and every value as it is made; and a range of more than `MAX_VARIANTS` values (`fox.const.ts`, 10 000), counted exactly before any is made (`it holds 100000 values, more than the 10000 variants Fox makes at most`). A bare `--` is skipped wherever it stands among the overrides (commander drops the first when no override comes before it, and leaves it among them otherwise); commander reads `-t`, `-w` and `-h` wherever they are, so a value that starts like one takes the `=` form (`--strategy.src=-tma`), as the help says, or follows a `--`. The options of Fox's own repository that named a checkout or an executable (`--gekko-folder`, `--gekko-exec`, `--worker-path`, their `FOX_*` variables) are gone: the workers run Gekko's pipeline in Fox's process. It imports `variants.helper` and `worker.helper` inside its `try`, as `main()` imports the registry: both load the registries of the strategies and of the plugins, a private strategy of `custom/` included, whose import can throw before the process handlers exist, so do not import them statically.
- `loadTemplate` (`src/configuration/variants.helper.ts`) reads the template with `loadConfigurationFile`, whose refusals pass through as they are, a file it cannot read included (`[CONFIGURATION] Cannot read the configuration file …`), and refuses itself one that holds no mapping of sections (`[FOX] Invalid template …`). `generateVariants` makes the variants, the cartesian product of the lists and ranges, numbered from 1, the first option's values changing last, each merged with lodash-es' `merge` over a deep copy of the template and labelled with its options of several values (`--strategy.period 14 --strategy.thresholds.up 2`), a number with every decimal (`formatEveryDecimal`: `0.0000001`, which `parseOverrides` reads back as that number, where `String` wrote `1e-7`, read back as a text). It refuses, before making any variant, an option whose path enters a list of the template by a key that is not an index as JavaScript writes one (`checkListKeys`, `/^(0|[1-9]\d*)$/`: not a symbol, an asset, a plugin's name, `01`, `-1` or `length`, which lodash's `merge` kept on the array as a property no configuration reads, every variant running the template's value under the label of the value asked for), naming the list and its indexes (`[FOX] --exchange.marketData.BTC/USDT.marketData.fee.maker: exchange.marketData is a list, name its item by its index (0 or 1)`; an index one past the last item adds one), then options whose values would make more than `MAX_VARIANTS` variants, naming the values of each (`The overrides make 10100 variants (100 values of --strategy.period × 101 values of --strategy.thresholds.up), more than the 10000 Fox makes at most: give them fewer values`), and gives a labelled variant's PerformanceReporter entries its label as their `label` option, after the entry's own when it has one (in the template, or set by `--plugins.3.label …`: `baseline --strategy.period 14`; a label that is not a non-empty text is left for the reporter's schema to refuse), so that the rows of variants whose strategy blocks are the same (a sweep of a fee) name their variant. The options take JavaScript's key order: grouped by key, and under a key its integer keys first, ascending (`--plugins.2.x a,b --plugins.1.y c,d` takes `plugins.1.y` first). `validateVariants` checks every one before any worker starts: `configurationSchema.safeParse` (an analyzer's `benchmarkAsset` among the watched assets included), `watch.mode` backtest (a realtime variant would trade until stopped, an importer one write candles), the strategy block by its strategy's static schema (not for a `strategyPath`, which the worker's StrategyManager checks), an unknown strategy name, each plugin entry by its plugin's schema, and the refusals the pipeline would make in every worker, built with the pipeline's own error classes (`pipeline.error.ts`), their `untaggedMessage` quoted at `plugins[i].name`, so that Fox and Gekko say the same: an unknown plugin name (`UnknownPluginError`: `No plugin is named "trader" (did you mean "Trader"?): the plugins are …`), a plugin whose static `modes` lack backtest (`PluginModeNotSupportedError`: `Plugin CandleWriter does not support backtest mode, only realtime and importer`) and an entry whose plugin emits an event a plugin of an earlier entry emits (`PluginsEmitSameEventError`, the earlier entry's index added to its name: `Plugins PortfolioAnalyzer (plugins[2]) and RoundTripAnalyzer are broadcasting the same event: performanceReport. This behavior is unsupported.`, at the later entry's name). The first invalid variant fails the run with one message listing every issue at its path from the root (`[FOX] Variant 2 (--strategy.period 1) is invalid:` and `z.prettifyError`'s lines, `→ at strategy.period`); each worker's `createRunContext` parses its configuration again. `warnOfUnreportedVariants`, which `main()` calls once they are checked, warns of the variants whose figures no CSV row will record, once for each cause, hidden at the default level, rather than refuse them, as Gekko runs such a configuration: without a PerformanceReporter (`The template has no PerformanceReporter: no CSV row will record the figures of its variants`; an analyzer logs its report at info level in each worker's output), or with one but no plugin whose static `eventsEmitted` holds `performanceReport`, the report the reporter writes its rows from (`The template has no plugin that sends its PerformanceReporter the performance report, as PortfolioAnalyzer and RoundTripAnalyzer do: …`), each as the template's when every variant has it, else naming the variants (`Variants 1 and 4 have …`).
- `runWorkers` (`src/worker/worker.helper.ts`) keeps `--max-workers` workers running, the next variant starting as one ends, and settles with the results in the order of the variants. A worker (`src/worker/gekko.worker.ts`) gets `{ variant, configuration, writeLock }` by `postMessage` (`VariantRequest`, `src/fox.types.ts`), builds ``createRunContext(configuration, `variant ${variant}`)``, runs `gekkoPipeline({ context, plugins })` with the registry of `@gekko/plugins/index`, closes the storage in `finally` (`context.services.closeStorage()`), posts `{ variant, status: 'done' | 'failed', error?, stack?, durationMs }` (`error` as `describeError` writes the failure, `stack` what the bot's `main()` would log of a failure whose message does not say where it was thrown, which the main thread logs at debug level under the variant's `… failed after …` line, `durationMs` the backtest's own) and exits. `stack` is `describeFailure` of `@gekko/core/logger/failure.helper`: the stack of an Error that is not a `GekkoError` and the causes of any Error, down to the root, the errors of an AggregateError included, so that a strategy's exception in `end()`, which the pipeline wraps in `[STREAM] TradingAdvisor failed to finalize: …`, is posted as that line then `Caused by: TypeError: … at end (…)`; it is left out for a `GekkoError` without a cause and for a value that is no Error, whose message says it all. The main thread terminates each worker once its result is in, a worker left running keeping Fox alive, and fails a variant whose worker emits `error` (its message without Bun's code frame) or closes without a result. The worker's `onmessage` stays a sync function that floats its promise. Under Bun 1.3.14 an async handler whose promise rejects aborted the whole process (SIGABRT) only when the main thread had no `error` listener on the worker, where 1.4.4 drops the rejection silently; with one, as `runWorker` has, the rejection is the worker's `error` event under both, from source and compiled. A rejection a worker leaves unhandled, or a throw in one of its timers, ends its variant at once, as the worker's `error` event, with no row written, where the bot logs an unhandled rejection and finishes its backtest.

Resolved from the worker helper's own URL, which compiled is the entry's too, the worker was looked for at `/$bunfs/root/gekko.worker.ts`, so a branch on Bun's virtual root picked the path, and a build made on Windows, which roots its modules elsewhere, would have failed every variant; the entry-relative URL should name the worker there too, but no Windows build is tested. `fox.test.ts` holds the path to the file and the build: the module `main()` hands the workers is `src/worker/gekko.worker.ts` and exists, and `build:exec` names `src/fox.ts` and `path.join('src', WORKER_MODULE)`.
- A worker logs to its own stdout through `@gekko/core`'s logger, at the `GEKKO_LOG_LEVEL` it inherits (`error` by default), without relay or prefix, under the lock of stdout Fox's main thread shares: `runWorker` posts it with the variant (the request's `writeLock`), from `shareWriteLock()`, under which the main thread writes from its first call on, and the worker takes it before its backtest (`useWriteLock`). Each line of Fox's threads is written whole under that lock, an Atomics lock over a SharedArrayBuffer (its holder renewing its lease at each wait for the pipe, a lease left unrenewed for `WRITE_LOCK_STALE_MS`, 1 s, taken over: a worker terminated while it wrote), before the call that logs it returns, so that no line over 4096 bytes, which a pipe takes in several writes (a TRADING REPORT of 17 pairs or more), is spliced with another thread's, and neither the worker's `process.exit()` after its `postMessage`, nor `terminate()`, nor Fox's final `process.exit()` drops a line, whatever reads Fox's output; a reader that stalls stalls the workers, and Fox with them. Fox's threads keep no queue once they write under the lock (the main thread writes what it queued before as it shares it), unlike the bot: a backtest leaves no turn to the timer of a queue, and `terminate()` cuts short a worker's `'exit'` listener. Fox logs from the main thread under the tag `fox`: the version line, `Backtesting <n> variants of <template>, <k> at a time`, `Variant 3 of 12 (--strategy.period 14) started`, then `… done in <duration>` at info or `… failed after <duration>: <reason>` at error (`formatDurationUTC`, `less than a second` below one), and the summary, `4 variants, 0 failed` at info or `4 variants, 2 failed: variants 2 and 4` at error. A refusal and an uncaught exception are reported as the bot reports them, by `logFailure('fox', …)` of `@gekko/core/logger/failure.helper` (`src/fox.helper.ts` holds `logSummary`). Fox exits 1 when a variant failed or anything threw, 0 otherwise and after `--help`; SIGINT and SIGTERM keep Bun's default, Fox and every worker stopping at once.
