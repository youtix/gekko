# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Gekko is a modular crypto trading bot framework written in TypeScript and run with Bun. It covers candle import, backtesting, screening/alerting, paper trading and live trading through CCXT (Binance, Hyperliquid). There is one entry point, `src/gekko.ts`; what it does is decided entirely by a config file.

## Commands

Bun is the package manager and the runtime. Scripts, git hooks and CI all go through `bun` and `bun.lock`; there is no `package-lock.json`. Node (22.13 or later, not 23, as `engines` says) must be on the PATH too: vitest runs the unit tests under it (see Testing).

```bash
bun install
bun run dev              # run the bot from source (src/gekko.ts)
bun run build:exec       # compile a standalone binary to dist/gekko
bun run type:check       # tsc --noEmit, incremental (node_modules/.cache/tsc): src/, test/, scripts/, vitest.config.ts
bun run lint:check       # eslint . (all but dist/, db/, coverage/, documentation/dev/; bun run lint autofixes)
bun run format:check     # prettier --check . (all but what .gitignore and .prettierignore list; bun run format writes)
bun run test             # unit tests: vitest over src/**/*.test.ts and scripts/**/*.test.ts
bun run test src/helpers/collection/ringBuffer.test.ts                       # one file
bun run test src/helpers/collection/ringBuffer.test.ts -t "argument itself"  # one test, by name
bun run test:coverage    # what CI and the pre-push hook run; fails below 95% lines/functions/branches/statements
bun run test:e2e         # test/e2e on Bun's test runner, --isolate (a fresh global per file, or the module mocks leak)
bun run bench            # vitest benchmarks (src/**/*.bench.ts)
```

`bun test` without `run` is Bun's test runner, not vitest. Only `test/e2e` is written for it, and `bun run test` finds none of its files; CI runs `test:e2e` in its `build` job, after `test:coverage`, and no git hook does. Its realtime flows run real minutes under Bun's fake timers (see Testing).

vitest pre-bundles date-fns, lodash-es and ccxt (`test.deps.optimizer.ssr` in `vitest.config.ts`): each test file runs in a process of its own, which loaded them module by module, so the suite takes less than half the time. The bundles sit in `node_modules/.vite/<key>/`, the key a hash of `bun.lock`'s content and of the checkout's path, so that a dependency bump starts a new directory (Vite reads no `bun.lock`: in one directory, the suites would go on running against the bundle of the old version) and a copy of the repository whose `node_modules` is a link does not share one (Vite deletes the bundles of another checkout to rebuild them, under a run that reads them). The directories of earlier lockfiles and of deleted copies stay behind, about 42 MB each: `rm -rf node_modules/.vite` reclaims them, and the next run rebuilds its own. ccxt must stay in the list: left out, the suites that load it fail on `Cannot access 'bydfiRest' before initialization`.

### Running the bot

There are no CLI flags, only two environment variables:

- `GEKKO_CONFIG_FILE_PATH`: the config file to load (`.yml`, `.yaml`, `.json` or `.json5`). Its `watch.mode` (`importer`, `backtest` or `realtime`) selects what runs.
- `GEKKO_LOG_LEVEL`: winston level (`error`, `warn`, `info`, `http`, `verbose`, `debug`, `silly`; case-insensitive, `warning` means `warn`). It defaults to `error`, so set `info` or `debug` to see anything. An unknown value falls back to `error` and says so once.

Bun loads `.env` and then `.env.local` (gitignored, takes precedence) automatically, so a bare `bun run dev` runs whatever config those files point at. The compiled executable (`dist/gekko`) loads them the same way, from the directory it runs in, not from beside the binary. A variable set on the command line or exported in the shell wins over both files, so there is nothing to `source`:

```bash
GEKKO_CONFIG_FILE_PATH=./config/backtest.yml GEKKO_LOG_LEVEL=info bun run dev
```

A backtest replays 1-minute candles from SQLite and aborts if any minute of `watch.daterange` is missing, so the range has to be imported first (importer mode, e.g. `config/importer.yml`, writing to the gitignored `db/`). The importer only stores closed minutes: a `daterange.end` at or after the minute in progress is clamped to the last closed minute, with a warning. It fills a gap of a pair of up to 7 days (`MAX_GAP_FILL_MINUTES`) with flat candles and refuses a longer one, naming the pair, before any of it is written; a pair whose history starts after the range does (listed on the exchange after `daterange.start`) or ends before it does, or whose last minutes of the range the exchange skips although it has later candles, keeps those minutes missing, with a warning, so that a backtest of them is refused rather than run on made-up candles. Writers (importer, realtime) create the database directory; a backtest opens the database read-only, refuses a missing file or a pair without a table (the connection it opened closed at once: it held the database until the garbage collector closed it), and writes nothing to it (SQLite's read-only connection to a database in WAL leaves an empty `-wal` and a 32 KB `-shm` beside it, which only a connection that writes removes, the next import as it closes). Every mode refuses, as the storage opens, a `storage.database` that is not an SQLite file or is a truncated copy: `Cannot open the database <path> (file is not a database).` (`database disk image is malformed` for a truncated copy). An import overwrites the stored candles of its range with the candles it reads from the exchange, so re-importing a range repairs the synthetic candles a realtime run's gap filler wrote there; a made-up candle never replaces a stored candle that traded, and a realtime run only replaces a stored candle that is itself made up.

Exit codes: 0 when a run ends normally or is stopped by `ApplicationStopError`, 1 after any other failure, 130 on SIGINT and 143 on SIGTERM (the storage buffer is flushed and closed, the plugins are not finalised). A run that ends normally still exits 1 if a promise rejection went unhandled along the way, if a plugin failed to finalise, or if the storage failed to close. A failed finalisation rejects the run with `[STREAM] <plugin> failed to finalize: <what it threw>` (several joined by `; `), caused by that failure (an `AggregateError` of them when several failed): an import whose last insert fails (another connection holding the write lock past the 5 s busy timeout, a full disk) so exits 1, naming the minutes it did not write. main() closes the storage once more on its way out, after CandleWriter's own close (the first close when no CandleWriter was finalised: a backtest, a start-up that failed before CandleWriter was initialised); a failed close is logged at error level as `Could not close the storage: …`, as on SIGINT and SIGTERM and after an uncaught exception, and a run that had ended normally then exits 1 through `process.exitCode`, ending by itself. A run that failed or was stopped keeps its code, 0 for an `ApplicationStopError`, a failed finalisation logged at error level beside its own error.

## Git workflow

- Commit messages must follow Conventional Commits. commitlint enforces it in the `commit-msg` hook (`bun x commitlint --edit`), on pull requests (their own commits, `base.sha..head.sha`) and on pushes to `main` and `development` (`before..sha`; a new branch, or a forced push whose previous tip is not in the clone, is skipped with a notice): subject not capitalised, header at most 125 characters, body and footer lines of any length. `bun run commit:check --last` (or `--from <ref>`, or a message on stdin) checks messages by hand.
- `pre-commit` type-checks what is committed, not the working tree: git keeps a copy of the tree being committed in `node_modules/.cache/index-check`, with an index of its own, updated in place, which incremental tsc checks (its errors name the copy's paths); then it runs lint-staged (`eslint --fix` and `prettier --write` on the staged `.ts`, `.tsx`, `.js`, `.jsx`, `.cjs`, `.mjs`, `.cts` and `.mts` files, `prettier --write` on the `.json`, `.md`, `.yml` and `.yaml` ones). An untracked file, a private strategy of `src/strategies/custom/` included, is not checked at commit time: `bun run type:check` checks it. A commit interrupted during the copy can leave `node_modules/.cache/index-check/.index.lock` behind, which refuses the next copy until it is deleted. `pre-push` runs `test:coverage` only for a push that creates or moves a branch, not for a tag, a notes ref or a deletion.
- Work lands on `development`, and pull requests target it (CONTRIBUTING.md has contributors fork and branch from `upstream/development`). `main` only moves for releases: a push to `main` runs the checks, then a `release` job of its own, with `HUSKY=0` so that no git hook runs at its commit and pushes, runs semantic-release, which writes `CHANGELOG.md` (listed in `.prettierignore`: it keeps the generator's text), writes the version it releases into `package.json` and rebuilds `dist/gekko` from it (the prepare step of the repository's own plugin, `scripts/release/version.cjs`, which fails the release before anything is tagged if the build writes no `dist/gekko`), commits both files to `main` (`chore(release): <version> [skip ci]`) and publishes the GitHub release with `dist/gekko` attached under the stable name `gekko`. So never bump a version or edit the changelog by hand. The executable prints the `package.json` version it was built with (`Gekko version: vX.Y.Z` at info level): a release prints its own, a build of `development` the last one merged back from `main`.
- semantic-release reads the commits with the `conventionalcommits` preset, the parser commitlint validates them with. `feat` releases a minor; `fix`, `perf` and a revert (a `revert:` or `Revert "…"` header with git's `This reverts commit <sha>.` line) a patch; the other types nothing on their own. A `!` after the type or the scope (`feat!:`, `fix(trader)!:`) and a `BREAKING CHANGE:` or `BREAKING-CHANGE:` footer each release a major; a header that starts with `BREAKING CHANGE:` is refused (no type). A `Co-Authored-By:` trailer after a breaking footer ends up in the note: mark the change with `!` and keep the trailer last, or end with a paragraph holding the trailer, then a one-line `BREAKING-CHANGE:` footer.
- CI runs on pushes and pull requests to `main` and `development`, in a job whose token can only read: the commit messages, `format:check`, `lint:check`, `type:check`, `test:coverage`, `test:e2e` and `build:exec`, `format:check` and `lint:check` reading the whole checkout (`test/`, `scripts/` and the configuration files included). The `build` job stops after 30 minutes and its `test:e2e` step after 10 (`timeout-minutes`): under fake timers a flow that awaits a promise that never settles hangs past every timeout of its own (see Testing), and GitHub's default bound is six hours, the release waiting behind it. On a push to `main`, the `release` job, which needs that one, runs `bun run release` with the write scopes, so a malformed commit pushed to `main` skips that push's release. Both jobs of `.github/workflows/ci.yml` pin Bun to 1.3.14 (`bun-version`), since the e2e harness relies on that version's test runner and fake timers (see Testing) and the release compiles `dist/gekko` with it: an upgrade changes both pins, in a commit of its own that passes `test:e2e` on the new version.

## Code conventions

- `console.*` is a lint error. Log through `debug`, `info`, `warning` and `error` from `@services/logger`, each taking `(tag, message)`; `tag` is a closed union in `src/models/tag.types.ts`. `debug` returns before winston formats anything when its level is off, so a debug line on the hot path costs nothing; an info line that would be logged on every candle goes behind `isLevelEnabled('info')` (no line of `src/` is one today), never a warning or an error, which the log buffer keeps for Supervision whatever `GEKKO_LOG_LEVEL`. A line that quotes a failure writes `describeError(err)` (`src/errors/error.helper.ts`): a `GekkoError`'s `untaggedMessage`, since the line has a tag of its own; an `AggregateError`'s message followed by its errors, each so described (`; ` between them); any other Error's message; a string as it is; an object whose message `util.inspect` does not show (Bun's ResolveMessage and BuildMessage, which the import of a strategy file that cannot be found or parsed rejects with) as `<class>: <message>`, a BuildMessage followed by ` at <file>:<line>:<column>`; anything else as `util.inspect` writes it. Never `String(err)` or `${err}`: they write an object as `[object Object]`, and throw for one without a prototype from the very catch meant to report it. `toError(value)` there makes an Error of any thrown value. A refusal that names a value it refuses writes it with `showValue(value)` (`src/utils/object/object.utils.ts`): a string in double quotes (`"3"`, not the number 3), anything else as `util.inspect` writes it, two levels deep, on one line (`[ 14 ]`, `3n`, `[Object: null prototype] {}`); the RingBuffer's size refusal and the indicators' parameter checks do. A message that counts writes its noun with `pluralize(word, count)` (`src/utils/string/string.utils.ts`), the plural for 0 too, rather than `minute(s)`, and one that names several pairs, keys or options lists them with `listInWords(items)` (same file: `a and b`, `a, b and c`).
- Unused parameters must be prefixed with `_`, a lint error otherwise, a leading one too (`args: 'all'`); an unread catch binding is left out (`catch {`), since `catch (_err)` is reported. Import cycles are lint errors (`import/no-cycle` reads the `.ts` modules), and only a type-only import breaks one: `import type …`, or `import { type A, type B }` whose every name is a type; an import written as a value import counts even when it brings only types. A value cycle can throw `Cannot access … before initialization` under Bun, depending on which of its modules loads first (`movingAverages.const.ts` says how one was avoided). No lint rule finds a dead export (`import/no-unused-modules` checks nothing without options, and crashes under ESLint 10 with `unusedExports`): look for one with TypeScript's find-references. `lint:check` and `format:check` read the whole checkout, and lint-staged gives every `.cjs`, `.mjs`, `.cts` and `.mts` file ESLint and Prettier. The `.cjs` files (the release and commitlint configurations, `scripts/release/version.cjs`) are linted as CommonJS with Node's globals; the other `.js` files are ES modules, linted with Node's globals without CommonJS's (`globals.nodeBuiltin`), so a `require` or a `__dirname` there is `no-undef`. `version.cjs` is type-checked through its `// @ts-check` (`allowJs`, and its own entry in tsconfig's `include`: under the default include, its `version.d.cts` outranks it and tsc drops it).
- Prettier: 140 columns, single quotes, trailing commas, no parentheses around a lone arrow parameter. ESLint has no formatting rule: its stylistic rules, deprecated since 8.53, refused the double quotes Prettier writes around a text holding an apostrophe.
- The path aliases (`@constants`, `@models`, `@errors`, `@utils`, `@services`, `@indicators`, `@strategies`, `@plugins`, `@helpers`) are declared in `tsconfig.json` alone: Bun, tsc and ESLint read them there, and `vitest.config.ts` builds its own from its `paths` (each `@x/*` entry is the `@x` prefix). tsconfig.json stays plain JSON, without comments or trailing commas, which the bundler that loads vitest.config.ts refuses. Its `include` is `**/*.ts` and `scripts/release/version.cjs` (a `**/*.cts` pattern would drop version.cjs again; `scripts/tooling/typeCheck.test.ts` checks that tsc reads it and vitest.config.ts), and its `lib` is `ESNext` alone: Bun has no DOM, so a stray `document` or `length` does not type-check, and `EpochTimeStamp`, which lib.dom declared, is declared in `src/modules/global.d.ts`. vitest.config.ts is typed (`defineConfig`): a misspelt option fails `type:check`.
- Files are named `<name>.<role>.ts` (`.types`, `.schema`, `.const`, `.error`, `.utils`, `.helper`, `.strategy`, `.indicator`, `.stream`, `.service`, `.storage`, `.mock`, `.bench`), and a module without a role after what it holds, a class most often (`trader.ts`, `pipeline.ts`, `ringBuffer.ts`). A test takes the name of the file it tests, `.test.ts` for `.ts` (`fillCandleGap.stream.test.ts`), and `test/e2e` names its flows `<name>.flow.test.ts` and its helpers `<name>.helper.ts`. Coverage counts `src/**/*.ts` and `scripts/**/*.cjs`, and skips `.schema`, `.mock`, `.types`, `.error`, `.const`, `.bench` and `index.ts` files, and everything under `src/strategies/custom/` and `src/strategies/debug/`. `src/utils` and `src/helpers` have no barrel files; import `@utils/<dir>/<file>` or `@helpers/<dir>/<file>`.
- Code splitting between `src/utils/`, `src/helpers/`, colocated files and class files follows strict rules:
  - `src/utils/` (`@utils/*`) holds only generic, domain-agnostic utilities (`*.utils.ts`) with no dependency on Gekko's domain models (`@models/*`), `GekkoError`, `@services/logger` or trading rules (`math.utils.ts`, `round.utils.ts`, `string.utils.ts`, `date.utils.ts`, `array.utils.ts`, `object.utils.ts`, `fetch.utils.ts`, `process.utils.ts`). The `.utils.ts` suffix is used exclusively inside `src/utils/`.
  - `src/helpers/` (`@helpers/*`) holds the helpers (`*.helper.ts`) shared across several modules that work with Gekko's domain models or its trading rules, throw `GekkoError` or log (`candle.helper.ts`, `event.helper.ts`, `market.helper.ts`, `precision.helper.ts`, `portfolio.helper.ts`, `order/sizing.helper.ts`, `stream.helper.ts`, `strategy.helper.ts`), and, whatever their number of users, the helper classes (`AsyncMutex`, `RingBuffer`, `SequentialEventEmitter`, `PositionTracker`, `PositionBook`) and `finance/stats.helper.ts`, the figures of a performance report: `SequentialEventEmitter` serves `Plugin` alone, `AsyncMutex` the simulator alone (generic, it imports nothing of Gekko's, but the modules of `src/utils/` are `*.utils.ts` files of functions), `PositionTracker` the book and the custom strategies, `stats.helper.ts` the analyzers. Nothing under `src/helpers` imports `@plugins` (`import/no-restricted-paths` refuses it): a helper that a plugin and another module share lives here, as the sizing of an order (`src/helpers/order/sizing.helper.ts`), which the Trader and the PositionBook import. Helper functions only used by a single module or directory stay colocated beside it and always use the `.helper.ts` suffix.
  - A file that declares a class (`<name>.ts`, `<name>.strategy.ts`, `<name>.indicator.ts`, `<name>.stream.ts`, `<name>.storage.ts`, `<name>.error.ts`) must contain only its imports and the class itself (apart from the `config` and `inject` singleton exports in `configuration.ts` and `injecter.ts`, and the internal `UTCDate` subclass in `date.utils.ts`). Never leave helper functions, types/interfaces or constants outside the class in that file: extract them into sibling `<domain>.helper.ts`, `<domain>.types.ts` and `<domain>.const.ts` files at the same directory level, reusing the directory's existing `.helper.ts`, `.types.ts` or `.const.ts` file whenever one already exists.
- `lodash-es` (never `lodash`), `date-fns` and zod v4 are used throughout. Timestamps are epoch milliseconds, and a duration in milliseconds is written with `ONE_SECOND` and `ONE_MINUTE` (`@constants/time.const`). A minute is floored with `startOfMinuteUTC` (`src/utils/date/date.utils.ts`) and moved with `± ONE_MINUTE`, the clocks set on every bucket included (`start + ONE_MINUTE` in the Trader, the StrategyManager, the simulator and the analyzers: date-fns' `addMinutes` built a Date each time), a second is floored with `Math.floor(t / ONE_SECOND) * ONE_SECOND`, and a duration shown to the user is written with `formatDurationUTC(start, end)` (same file), on the UTC calendar. date-fns' `startOf…`, its `add…` and `differenceIn…` of days, weeks, months and years, and `intervalToDuration` count in the host's local time: on a host with daylight saving time, `startOfMinute` read every instant of the hour repeated when it ends an hour early, so a live stream pushed nothing for that hour, a duration across a change came out an hour off, and `intervalToDuration(…, { in: tz('UTC') })` of `@date-fns/tz` still moved a date whose UTC time the host's zone skips at its spring change ("1 day -1 hours"): no code imports `@date-fns/tz`.
- There is no decimal library: `round` (`src/utils/math/round.utils.ts`) rounds a number exactly as it is written, and `addPrecise` and `multiplyPrecise` (`src/utils/math/math.utils.ts`) add and multiply two numbers as they are written (0.3 − 0.1 is 0.2, 100.01 × 0.0004 is 0.040004), exactly up to 15 significant digits and as `a + b` or `a × b` from 17, for the amounts, prices, costs and fees that must come out as decimals. At 16 digits `addPrecise` gives the double nearest to the sum, which `String` can write a unit of its last decimal off, so that the next call adds to that neighbour and a change below an ulp can be lost (an 8-decimal balance from 67.1 M to 90 M units), and `multiplyPrecise` the binary product rounded to the decimals of the two, which can land a unit off the exact product, farther than `a × b` (a cost of 100,000 to a million, from an 8-decimal amount at a 2-decimal price). A quotient, which neither works out exactly (a mean, a fee rate, a percentage), goes through `toSignificantDigits` there: the double rounded to the 15 significant digits it keeps, a tie away from zero (0.06999999999999999 is 0.07); a reported return or drawdown works its change out with `addPrecise` first, and a figure made from a return is worked out from the equities and rounded once (`calculateAnnualizedReturnPct(currentEquity, startEquity, elapsedYears)`): from the 15-digit total return, a gain of 40 on 300,000 over a day annualized to 4.87999999999999 %, written 4.87 %. They read the number's decimal string, a cost a per-candle loop should not pay: the candle batcher sums volumes with a scaled integer instead, and the analyzers' valuation (`calculatePairEquity`, `calculatePortfolioTotalValue` in `src/helpers/portfolio/portfolio.helper.ts`) pays it once per timeframe candle, a few µs for each asset held, because the analyzers compare equities exactly. The simulator books the cost of an order to 8 decimals, as Binance keeps its balances (`BOOKED_CURRENCY_UNIT`, 10^-`COST_DECIMALS`, `src/constants/order.const.ts`), while an equity values a holding at amount × price, up to 5e-9 apart: the analyzers take two equities less than that unit apart for one amount, a round trip that ends so close to its entry equity (or within a billionth of it) breaking even, and the PortfolioAnalyzer's drawdowns and returns ignoring such a gap.
- Indicator results and other computed numbers are guarded with `isFiniteNumber` (lodash's `isNumber` accepts NaN), and two values equal in exact arithmetic but computed apart, such as a flat market's close and its SMA, are compared with `compareWithTolerance` (relative 1e-9), both in `src/utils/math/math.utils.ts`. TMA, SMACrossover and EMARibbon compare so, and CCI, Stochastic (StochasticRSI through it) and Bollinger Bands (OBV through them) decide a flat window so. `isFinitePositive` there is the one check of a finite number above 0: an order's price, amount and cost, a market's bound or step (`toBound` in `src/helpers/market/market.helper.ts` reads a limit or a step so). Steps and ticks are applied by `roundToStep` and `getPriceTick` (`src/helpers/market/precision.helper.ts`), which the simulator, GridBot and the PositionTracker share: an amount truncated to its step, whatever the step, a price rounded half up to the tick at that price. An amount is valued as the exchanges check it by `getSentCost(amount, price, marketData)` (`src/helpers/market/market.helper.ts`): truncated to the amount step, the amount sent, then multiplied by the price in decimal, its cost, the two figures that the Trader's minimum warnings (`warnOfMarketMinimums`), the PositionBook's skip (`getBuyRefusal`) and the PositionTracker's `isSellable` compare with `amount.min` and `cost.min`. A message that quotes a value beside a bound writes it with `formatEveryDecimal` (`src/utils/string/string.utils.ts`): every decimal `String` gives it, without an exponent, where `formatAmount` (for a person, thousands grouped) and `toPlainNumber` (for a CSV cell) round to 8 decimals. A percentage shown to the user is written with `formatPercent(value, rounding)` (same file), the rounding taken from `PERCENT_ROUNDING` (`src/plugins/analyzers/analyzer.const.ts`), one entry per figure, so that the CSV, the console tables and Telegram write a figure alike.
- `ORDER_SIDES` and `ORDER_TYPES` (`src/constants/order.const.ts`) are the one list of order sides and types: `OrderSide` and `OrderType` derive from them, and a new type does not compile until the Trader's `ORDER_FACTORY` has a class for it.
- `TIMEFRAME_TO_MINUTES` (`src/constants/timeframe.const.ts`) is the one list of timeframes: `TIMEFRAMES` (`src/services/configuration/configuration.const.ts`) and `CandleSize` (`src/services/core/batcher/candleBatcher/candleBatcher.types.ts`) derive from it. Its months and years are nominal (30 days a month), while those candles span whole UTC months: a timeframe in any unit but minutes, hours, days or weeks does not compile until `MONTHS_PER_CANDLE` (same file) gives its months, a divisor of 12, and any other size until it has a case in the exhaustive switch of `getCandleTimeOffset` (`src/helpers/candle/candle.helper.ts`). `getCandleStart` and the batcher's `isTimeframeCandleClose` (`src/services/core/batcher/candleBatcher/candleBatcher.helper.ts`: the offset of the next minute is 0) read that one calendar, so the warmup and backtest windows and the timeframe candles share their boundaries.
- `INPUT_SOURCES` (`src/indicators/indicator.const.ts`) is the one list of price sources: `InputSources`, `checkInputSource` and the strategies' `src` parameter (`inputSourceSchema`, `src/models/schema/inputSource.schema.ts`) derive from it, so a source added there is typed, checked and offered by RSI, TMA, SMACrossover and EMARibbon at once. A new strategy with a `src` takes `inputSourceSchema.default('close')`.

## Architecture

### Boot and pipeline

`src/gekko.ts` calls `gekkoPipeline()` (`src/services/core/pipeline/pipeline.ts`), which threads the configured plugin list through a fixed sequence of steps: the backtest's check that the database holds every minute of `watch.daterange`, read each plugin class's static configuration, mode compatibility, per-plugin zod parse, dependency and duplicate-emitter checks, a warning when a plugin creates orders that no plugin executes (a TradingAdvisor without a Trader), `exchange.loadMarkets()`, instantiate, wire events, inject services, then launch the stream pipeline for the mode. `gekkoPipeline({ signal })` is the one way to end a run from code, and the only end of a realtime run but a failure or the circuit breaker's stop: aborting the signal destroys every stream of the run, lets the bucket in progress finish, finalises the plugins with the `AbortError` as their failure (the analyzers report its message, `The operation was aborted.` under Bun, as their `interruption`), then rejects the run with that `AbortError` (its `cause` is the reason of the abort), unless a bucket failed meanwhile, whose error stays the run's. `main()` passes no signal, so SIGINT and SIGTERM keep their behaviour; the e2e harness ends its realtime runs with one.

Two module-level singletons sit under everything:

- `config` (`src/services/configuration/configuration.ts`) reads the config file and validates it with zod at import time, and throws if `GEKKO_CONFIG_FILE_PATH` is unset. `configuration.schema.ts` is the source of truth for the config shape. Every section is a `z.strictObject` except the `strategy` block and the `plugins[]` entries, which the plugin's own strict schema parses, so an unknown key anywhere (a misspelt `sandbox`, say) refuses the file. A YAML file is loaded with js-yaml's core schema, so an unquoted timestamp stays text, like a quoted one, for the schema to check (merge keys `<<` and js-yaml's `!!timestamp`, `!!set`… tags are not supported). A `watch.daterange` bound is a day (`2024-01-01`, its midnight UTC) or a day and a time with `Z` or an offset (`2024-01-01T00:00:00Z`, `2024-01-01T02:00:00+02:00`), checked against the calendar: `2023-02-29`, `24:00` or a `+25:00` offset is refused rather than rolled over to another day. The range must end in the minute of its start or later, in every mode; both minutes are read, so equal bounds are one minute. Assets, the currency and symbols are written in upper case: Latin capitals, digits or the letters of a script without case, a symbol being two of them around one slash (`pairConfig.schema.ts`). A list read into a Map by a key (`simulationBalance` by `assetName`, `marketData` and `initialTicker` by `symbol`) refuses a repeated key (`refuseRepeatedKeys`, `exchange.schema.ts`), and every `simulationBalance` asset must be a watched asset or the currency. An invalid file is a `GekkoError` naming the file, followed by every issue with its path (`z.prettifyError`, one per line); an invalid plugin entry is reported the same way, with the plugin's name and index. A file that does not parse is refused in one line, naming its format and the file, with the parser's reason and the line and column of the fault (`[CONFIGURATION] Invalid YAML in configuration file ./config/live.yml: bad indentation of a mapping entry at line 9, column 18`), without quoting the file and without a cause: js-yaml's own message quotes the lines around the fault, credentials included, and the fatal error report prints a cause in full.
- `inject` (`src/services/injecter/injecter.ts`) lazily creates and memoises the `exchange()` and `storage()` instances that streams, orders and plugins share. `closeStorage()` closes the storage only if one was created.

`src/gekko.ts` imports the configuration, the injecter and the pipeline dynamically inside the `try` of `main()`, so that a configuration error is reported like any other failure; a static import that loads `config` would throw before the handlers exist, so do not add one. It is also the only place that reports a fatal error and decides the exit code. Its `catch` and its process-level handlers share one formatter: a `GekkoError` is logged as its one-line message (stack at debug level), anything else with its name, message and stack, and causes are appended. A wrapper passes the failure it wraps as `{ cause }` (`GekkoError(tag, message, options?)` takes `ErrorOptions`, and keeps `tag` and `untaggedMessage` beside its tagged `message`), and the report appends each cause in full (`Caused by: <its stack>`), as for the SQLite open failure or a plugin dependency that fails to load. An `uncaughtException` is logged and exits 1 at once, without finalising the plugins, once the storage is closed (a failure of that close is logged as `Could not close the storage: …`, and the process exits whatever the logger does); `Heart` failing to tick after the machine slept is no longer one: it emits `'error'`, the realtime stream destroys itself with it and the pipeline rejects, so the plugins are finalised. An `unhandledRejection` is logged and sets the exit code to 1 but does not stop the bot, because timer-driven tasks float promises that reject on a network blip.

### Candle streams

Data moves as 1-minute `CandleBucket`s (`Map<TradingPair, Candle>`, one candle for every watched pair) through Node object-mode streams assembled in `src/services/core/pipeline/pipeline.helper.ts`:

| Mode     | Chain                                                                                                                                                                                                     |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| realtime | warmup history, then live per-pair streams synchronised by timestamp → RejectFutureCandle → RejectDuplicateCandle → FillCandleGap (drops the leading buckets that miss a pair never seen) → PluginsStream |
| backtest | SQLite reader → PluginsStream                                                                                                                                                                             |
| importer | exchange OHLCV history → RejectFutureCandle → FillCandleGap (leaves out a pair whose history has ended) → PluginsStream                                                                                   |

A history range (`HistoricalCandleStream`) is inclusive on both ends, so equal bounds mean one minute. The realtime pipeline reads the clock once: the warmup history runs from the start of the candle `warmup.candleCount` candles before the one in progress (`getCandleStart`, on calendar boundaries for `1M`, `3M`, `6M` and `1y`) to the minute before the one in progress, and the live streams start at the minute in progress, so the two ranges neither overlap nor leave a gap. `HistoricalCandleStream` pulls one page per `_read` with `tickrate` as the minimum interval between requests. An empty page after some data ends the history with a warning naming how many minutes of the range it leaves out, the last page warns likewise about the minutes the exchange skipped before the end of the range although it has later candles, and the first page warns once of the minutes before the first candle the exchange has from the start of the range on, naming them and that candle (a pair listed during the range; a first candle after the whole range gets that one warning, `starting the history of this pair after the range`, where the end-of-range warning spoke of an early end); those minutes stay missing too, the gap filler filling a pair only from its last candle, and the warning comes in realtime as well, for a warmup history that starts late, beside FillCandleGap's drop warnings; a gap longer than `MAX_GAP_FILL_MINUTES` between two candles of the range fails the stream at once, so that an import never stores a week of flat candles before the refusal. A live stream ticks on each minute boundary plus `REALTIME_GRACE_PERIOD` (`src/constants/realtime.const.ts`), asks for every closed minute since the last one it pushed, oldest first (a failed fetch is retried on the next tick, never pushed as a made-up candle, and a late tick catches up instead of skipping a minute), ignores the minute in progress, and destroys itself with a `GekkoError` after `REALTIME_MAX_TICKS_WITHOUT_CANDLE` minutes without a candle, so a pair that stops delivering stops the bot instead of freezing it; until then the buckets wait for it, so that no pair's minutes reach the plugins between that pair's last candle and the stop. `FillCandleGap` fills a missing minute with a flat candle marked `synthetic`, but never a pair more than `MAX_GAP_FILL_MINUTES` (7 days) after its last candle, missing alone or with every pair: the bucket that would is refused with a `GekkoError` naming the gap (and the pair, but for a gap of every pair longer than that) before anything of it is pushed, and the writes still queued are ignored. In the importer it leaves out a pair whose stream has ended (`hasEndedBefore`, which `MultiAssetStream` answers from `synchronizeStreams`' `onPairEnd` by comparing the start of the pair's last candle with the bucket's minute), so a pair whose history ends early keeps its remaining minutes missing; in realtime it fills such a pair until its live stream takes over. A partial gap still open when the stream ends is summed up in a warning. In realtime it also drops the leading buckets that lack a pair it has never seen a candle for (one warning per such pair at the first drop, one summary at the first minute pushed), so the plugins only ever get complete buckets; the importer lets such buckets through. `pipeline.helper.ts` makes the three pipelines reject with the error of the failed bucket rather than with an upstream one. In every mode the per-pair streams are merged by `synchronizeStreams` (`src/helpers/stream/stream.helper.ts`), each bucket holding the pairs in the order of `watch.assets`: a pair's stream that ends lets the others go on and is reported to `onPairEnd` with the start of its last candle, one that fails fails the pipeline with its error, and one that closes without ending, or delivers a candle whose start is not a finite number, fails it with a `GekkoError` naming the pair (its position among the streams when it closes before its first candle), rather than leave the pair out of the buckets (in realtime, filled with flat candles forever) or stall them.

Aggregation to `watch.timeframe` is not a stream stage. It happens inside the TradingAdvisor plugin (`CandleBucketBatcher`), which throws a `GekkoError` if a bucket misses a watched pair, mixes minutes or does not follow the previous bucket by one minute, and which skips the minutes before the first timeframe boundary (with one warning for the bucket, whatever the number of pairs) rather than emitting a partial first candle; the per-pair `FastCandleBatcher` skips them without a word (Supervision batches an exchange's minutes with one).

For every bucket, `PluginsStream` (`src/services/core/stream/plugins.stream.ts`) does three things in order: the simulated exchange, if one is configured, consumes the bucket and fills orders; every plugin's `processOneMinuteBucket` runs concurrently; then the deferred events are flushed plugin by plugin, in config order, a plugin with nothing queued skipped (`hasDeferredEvents()`; in backtest the Trader counts its reports in flight as queued). In realtime, from the second bucket on, the same pass also runs between the first two: once the simulated exchange (paper-binance) has consumed the bucket, what the plugins queued since the previous flush is delivered before their `processOneMinuteBucket`, such as the end of an order whose report floated between two buckets (`deliversQueuedFirst`, the mode read from `config.getWatch()` as the stream is built). Not in a backtest, whose Trader awaits its reports before its flush: there, a delivery before the hooks would bring the fills the simulator settles as it consumes a bucket before that bucket's candle, and, before the simulator, an order hook's orders (GridBot's grid) would trade on the bucket a candle early. Nor before the first bucket, whose prices the analyzers need to value the Trader's start-up read.

### Plugins (`src/plugins`)

A plugin extends `Plugin`, implements `processInit`, `processOneMinuteBucket` and `processFinalize`, and exposes a static `getStaticConfiguration()` returning `{ name, schema, modes, dependencies, inject, eventsHandlers, eventsEmitted }`. `tradingAdvisor/tradingAdvisor.ts` is a good reference.

- Registry: the exports of `plugins/index.ts`. `plugins[].name` in the config must equal the exported class name exactly; an unknown name is refused with the list of valid names. The entry is parsed by the plugin's zod `schema` (a `z.strictObject`: a misspelt or retired option is an error, not a silent default) and the result is the constructor argument.
- Wiring is by name: an emitted event `orderCompleted` is bound to the `onOrderCompleted` method of every plugin that has one. Handlers are discovered on the prototype, so they must be methods, not arrow-function properties. Event names live in `src/constants/event.const.ts`, payload types in `src/models/event.types.ts`.
- An event can have only one emitting plugin. `PortfolioAnalyzer` and `RoundTripAnalyzer` both emit `performanceReport`, so they cannot be configured together. The RoundTripAnalyzer also refuses, at construction, a run that watches several pairs, with a `GekkoError` (`[ROUNDTRIP ANALYZER] RoundTripAnalyzer can only be used with a single pair: 2 assets are watched (BTC and ETH); watch one asset, or report through the PortfolioAnalyzer, which values every pair`): a signal strategy trading several pairs reports through the PortfolioAnalyzer.
- `processFinalize(failure?)` receives the error that stops a run before its end (a crash, `MissingCandlesError`, the circuit breaker, an aborted `signal`): the analyzers then set `interruption` on their `performanceReport`, `PerformanceReporter` writes it in the `status` column of its CSV rows (`interrupted: <message>`, `completed` otherwise), and with `enableConsoleTable` the analyzers print it on a line above their table, at any log level (`Run interrupted, the report below covers a partial period. Reason: <message>`). A `processFinalize` that throws fails a run that ended normally (exit 1, see Exit codes); after a failed run it is logged at error level, naming the plugin. `Supervision`'s `candle_check` subscription also alerts on Telegram when no 1-minute bucket came for `candleStaleThreshold`.
- Delivery is deferred: plugins queue events with `addDeferredEmit(name, payload)` and handlers receive an array of payloads when the queue is flushed after the bucket (in realtime, what was queued between two buckets also before the next one's hooks), each handler its own copy, so that one writing to it changes nothing for the others. The payload is copied when queued, by `copyPayload` (`src/helpers/event/event.helper.ts`), which copies plain data by hand and anything else with `structuredClone`, and refuses what `structuredClone` refuses, a function or a symbol (a `DataCloneError`). The payload of an event nobody listens to is queued uncopied: a listener added before its delivery would get a copy made then, which never happens in a run, the pipeline wiring every listener before the stream starts. A listener added during an emit or a delivery is called from the next one on. Nothing is flushed after `processFinalize`, so events sent from there use `emit` directly and carry a single payload, the same object for every listener, not a copy. The analyzers await that emit: a listener that fails is logged at error level (`A listener failed on the performance report: …`) and the run ends as it would have. The one exception is a strategy's error line: `tools.log('error', …)` fails the bucket, whose deferred events are then dropped, so the TradingAdvisor emits that `strategyInfo` at once, as an array of one.
- Config order matters. Each delivery is one pass over the plugins in config order, so an event queued on a plugin whose turn is over waits for the next pass: in a backtest the flush of the next bucket, one minute later; in realtime the flush after the hooks when it was queued in the delivery before them (an order an order hook places on the end of an order that floated), else the delivery before the hooks of the next bucket, one minute later. Keep `TradingAdvisor`, then `Trader`, then analyzers and reporters. Only the plugins that emit in answer to another's events need that order (the Trader after the TradingAdvisor, the analyzers after the Trader): with the Trader first, a backtest's fills reach the strategy a bucket late and the last minute's fill never reaches the analyzers. Those that emit nothing (PerformanceReporter, EventSubscriber, Supervision, CandleWriter) can go anywhere.
- Order reports are asynchronous (the order classes settle through callbacks or polls). In backtest the Trader waits for its pending reports before its queue is flushed and again in `processFinalize`, so a fill reaches the strategy and the analyzers in the bucket it happened in, the last one included. In realtime they float: a report queues the end of its order between two buckets, and PluginsStream delivers it as the next bucket arrives, before the plugins process it. In paper trading a MARKET order's end comes as the next bucket arrives, and a LIMIT order's fill is read by its next poll (every `orderSynchInterval`, 20 s by default), its end heard as the bucket after that poll arrives. So the strategy, its position book and the analyzers know of every order the exchange ended before a bucket when they process it, as in a backtest. The exception is a report still waiting for the exchange as the bucket arrives (its summary's trades, or its synchronization's balance or tickers): it is heard after the hooks or with the next bucket, while the Trader may already size from the balance it read. The order hooks run before the candle hooks: a line an order hook logs is dated with the close of the candle the strategy processed last, the one before, and the orders it places go out after the hooks, with those of the bucket. The EventSubscriber's `Current price` of an errored or canceled order is that close too. The RoundTripAnalyzer reads a round trip's adverse excursion by the fill dates, from the one-minute candles that close after its BUY fills and by the time its SELL fills (`countCandle`, `roundTripAnalyzer.helper.ts`): a report that floats changes none, up to `LATE_FILL_CANDLES` (an hour) late. It prices the part a canceled order filled at the `fillPrice` the Trader relays, else at a LIMIT order's own price, else at the last close (`priceCanceledFill`, `roundTripAnalyzer.helper.ts`): the `price` of a MARKET or STICKY order is only the one the strategy sized it from.
- Services named in `inject` (`exchange`, `storage`) are set after construction: use `getExchange()`/`getStorage()` from `processInit` onwards, not in the constructor.
- Modes: TradingAdvisor, Trader, PortfolioAnalyzer and RoundTripAnalyzer run in realtime and backtest; PerformanceReporter in backtest only; CandleWriter in realtime and importer; EventSubscriber and Supervision (both Telegram) in realtime only. Both take an optional `chatId` (`0` is refused); without it the bot warns at start-up, drops what was queued while Gekko was down, binds itself to the first chat that sends it a command from then on (logged at info with whose chat it is) and never rebinds, and anything sent before that is dropped. Each bot needs its own token (two pollers on one token get 409s). Both start subscribed to nothing and keep their subscriptions in memory: nothing is sent (for Supervision, no check runs) until the chat sends `/subscribe_all` or a `/sub_…`, and again after every restart. With `chatId` set, the commands the chat sent while Gekko was down (Telegram keeps them 24 hours) are handled at the first poll. The EventSubscriber answers `/portfolio` at once, subscribed or not, from the events alone (`inject: []`, no exchange call): the balances of the last read of the Trader's portfolio the events brought, with their age: the `exchange.portfolio` of any order event (`orderInitiated` included), whatever its balances, dated with its `exchange.portfolioReadAt` (`Balances read by the Trader at <read> (<age> ago)`; an event without one carries no read, the empty portfolio the Trader starts with), or a `portfolioChange`, which says nothing of its read, dated with its reception (`Balances read by the Trader, received at <reception> (<age> ago)`). The last one received is the newest read, the Trader queuing its events in the order of its reads: no read time is compared, which would hold every newer read out after a clock set back. `No balance received from the Trader yet …` without a Trader or before its first read arrives; each pair's last 1-minute close; the total value in the currency.

The trading loop for one bucket: TradingAdvisor builds the timeframe candle and calls the strategy → `strategyCreateOrder` → Trader creates a `MARKET`, `LIMIT` or `STICKY` order (`src/services/core/order`) → `orderInitiated`, later one of `orderCompleted` / `orderCanceled` / `orderErrored`, plus `portfolioChange` → back into the strategy's order hooks and into the analyzers → `roundtripCompleted`, `performanceReport`. Strategies track their pending orders through those three terminal events, so every order has to end in one of them. Only the Trader emits them: with a TradingAdvisor and no Trader (a screener), no order ever ends, and a strategy that waits for its order to end before it advises again, as the built-in ones do, advises once per run on each pair. The pipeline warns about it at start-up (one `warn` line, hidden at the default `error` level) rather than refuse, since a strategy that never creates orders needs no Trader; a screener runs the Trader on `paper-binance`. `orderErrored` carries `filled` and `mayBeLive`, whether the order may still be live on the exchange, where Gekko follows it no more; `orderCanceled` carries the cumulative fill and what was left of Gekko's own amount (not of the amount the exchange took, truncated to its step), both undefined when the exchange reported no fill (unknown, not 0), and `fillPrice`, the mean price of the fills reported for a LIMIT or STICKY order, left out without a priced fill and for a MARKET order, whose reported price can be the bound of its slippage. The `exchange` part of every order event carries `portfolioReadAt`, when the Trader read the balances of its `portfolio` (`Date.now()` once the exchange answered, the wall clock in a backtest too), undefined for the empty portfolio it starts with; `portfolioChange` stays a bare Portfolio, queued as the Trader reads it. `strategyCancelOrder` carries an `AdviceCancelOrder` (`src/models/advice.types.ts`): the `id`, and the `symbol` when the StrategyManager knows the order (created in this run by `createOrder`, the trailing stops' SELLs included, whose end it has not heard of yet, among the 10 000 most recent of those: `MAX_PENDING_ORDERS` in `strategyManager.const.ts`, beyond which the oldest is forgotten with the stop it asked for, a bound only orders that do not end reach, as without a Trader; forgotten before the order hook runs), left out otherwise; a `RoundTrip` names its `symbol`, the RoundTripAnalyzer's one pair.

`ApplicationStopError` is the graceful stop (the circuit breaker): plugins are finalised, the reason is logged at error level and the process exits with code 0, so that a restart-on-failure supervisor leaves it stopped. `ApplicationStopError(tag, message)` takes its thrower's tag, as every `GekkoError` does: the breaker's stop reads `[STRATEGY] Max consecutive order errors reached (5)`. Any other exception thrown by a plugin or a handler finalises the plugins and ends the process with exit code 1. `PluginsStream` destroys itself with the error it caught, which is how `main` tells the two apart, and it also finalises the plugins that were initialised when a stream upstream fails. When several plugins fail on the same bucket, an `ApplicationStopError` is the failure reported, otherwise the first in config order, and the others are logged after the close reason. SIGINT and SIGTERM flush and close the storage, then exit with 130 or 143 without running `processFinalize`.

### Strategies (`src/strategies`)

A strategy is a plain class, constructed without arguments, that implements any of the optional hooks of `Strategy<Params>` (`strategy.types.ts`, whose JSDoc gives the contract of every hook and tool). `StrategyManager` drives it. Model a new one on an existing strategy such as `dema/`, or on the Complete Example of `documentation/custom-strategies.md`, whose TypeScript examples type-check again.

- `init` runs once, on the first one-minute bucket, before any timeframe candle: in realtime the first minute of the warmup history, in a backtest the first minute of `watch.daterange`. Its `candle` holds that minute's candle of every watched pair, in the order of `watch.assets`. It is the only place `addIndicator(name, symbol, params)` is available: called once `init` has returned, it throws a `GekkoError`. It throws one too for an unknown indicator, an unwatched pair, a parameter the indicator refuses (a required one left out included) or a third argument that is not a plain object (left out or null, an untyped strategy's parameters are `{}`, the defaults), so such a mistake stops the bot at start-up. Then on each timeframe candle: indicators update, `onEachTimeframeCandle`, then once warmup is over `log` and `onTimeframeCandleAfterWarmup`.
- `init` also gets `openOrders`, the orders open on each watched pair at start-up, which the TradingAdvisor's `processInit` reads with one `fetchOpenOrders` per pair (a failed read fails the start-up). The map is empty in backtest and paper trading, whose simulator starts empty, and the run does not follow those orders: the Trader follows only the orders of this run.
- Hooks get `candle` as a `Map` holding every watched pair, followed by one `{ results, symbol }` argument per indicator in `addIndicator` order. Results are typed `unknown`: `null` until the indicator has enough data, then complete on every candle (a number, or an object whose fields are all set), so one `=== null` check suffices. ROC and TRIX are the exception: `null` again on a candle whose base is 0. `watch.warmup.candleCount` counts timeframe candles and is unrelated to indicator periods, so always null-check.
- What a hook receives is the strategy's own copy (the candles, the indicator results, the portfolio, an order hook's event, a trailing stop's state, `openOrders`, `tools.strategyParams`, `tools.marketData`): writing to it changes nothing elsewhere.
- Realtime prefetches the warmup candles from the exchange. A backtest spends the first `candleCount` candles of its `daterange` on warmup, and the configuration refuses a backtest with a TradingAdvisor whose range holds no more whole timeframe candles than that.
- `tools.createOrder()` returns a UUID immediately; the outcome arrives later through `onOrderCompleted`, `onOrderCanceled` or `onOrderErrored`. The order is dated with the end of the minute being processed. It is sized by at most one of `amount`, in the asset, `cost`, in the currency (a BUY may spend it, the 5 % fee buffer included, sized as an all-in BUY of that currency, `getAllInBuyAmount(cost, price)`; a SELL sells `cost / price`, no buffer) and `allocation`, a percentage in (0, 100] of a balance as of the Trader's last synchronization, not of what the orders placed since leave: for a BUY, of the currency read (`FreeBalanceLeft.read`) plus what the Trader's own BUYs that read shows open hold of it (`heldByOpenBuys`, taken at each read: a BUY placed before that synchronization started and whose completion was not heard by then counts its amount at the price it was created with, its filled part included, one the strategy canceled before the read its filled part alone), then sized as a `cost`; for a SELL, of the asset read free, what an open SELL holds being that SELL's to sell. Omitting all three means all-in, which a BUY of `allocation: 100` is to the digit in its amount (with BUYs open at the read, its share is above what is left, and it is capped there with a warning). The order events carry `cost` and `allocation` as asked, beside the `amount` sized. It throws a `GekkoError`, which stops the bot, before it draws an id or relays anything: during the warmup (so always from `init`), for a key `StrategyOrder` does not declare (`ORDER_KEYS` in `strategyManager.const.ts`, checked before the pair whatever its value: the Trader ignored it, so a misspelt `price` made a LIMIT at the last price and a `quantity` an all-in order), for a pair that is not watched (a key of `tools.marketData`), a `side` or `type` outside `ORDER_SIDES`/`ORDER_TYPES` (ccxt's lower-case `'buy'` and `'market'` among them), an `amount`, `cost` or `price` given that is not a finite number above 0, an `allocation` given that is not one at most 100, more than one of `amount`, `cost` and `allocation` (`null` and `undefined` count as left out), or an invalid `trailing`.
- `trailing` applies to BUY orders only: a `percentage` in (0, 100), an optional `trigger` above 0, no other key. The stop is armed, from a copy `createOrder` took, when the BUY completes. A BUY that errors gets it for the fill the exchange reported, if any, with a warning either way, and a BUY canceled loses it, even after a partial fill. It trails each one-minute candle met as open, low, high, close, each price tested against the stop price before it raises the peak. `onTrailingStopActivated` fires when a high reaches `trigger` (at arming when there is none). When a price reaches the stop price, `StrategyManager` sends a MARKET SELL and hands its id to `onTrailingStopTriggered`: an order of the strategy's own from then on, to adopt as its pending SELL (`PositionTracker.adoptSell(orderId)`, or `PositionBook.adoptSell(orderId, state.symbol)` for the tracker of the stop's pair). Both trailing hooks get `tools` last.
- A triggered stop sells until its SELL ends. Completed for all of the stop's amount, the stop is over. Completed for less (the Trader caps every SELL to the free balance and to the market's one-order maximum, and the exchange truncates its amount to the step), errored or canceled, it is active again for the rest, from the peak and the stop price it triggered at, with a warning, also when the SELL errored while it may still be live (`mayBeLive`). It is over instead, said at info level, when that rest is too little to sell at the market's minimums (`isSellable`), whatever else the account holds and even when that SELL may still be live. It is over too when the portfolio after that SELL shows too little of the asset free to sell, while no SELL the strategy created pends on the pair (at info level after a completed SELL, with a warning after an errored or canceled one): that is how a stop ends whose SELL went through after all, or whose BUY's fee was taken in the base asset (`Strategy.onTrailingStopTriggered` has the details). A SELL the strategy created holds the stops of its pair while it pends (they trail but do not trigger), cancels them all once it completes, and releases them when it is canceled or errors.
- The Trader caps every SELL to the free balance it last read less what the SELLs it placed since take from it, with a warning, and sizes an all-in SELL from that remainder, so that neither a live fee taken in the base asset nor two SELLs of one asset between two balance reads (two stops on one minute, a stop's and the strategy's) get a SELL refused; once the SELLs placed since take the whole of the asset read, a SELL of an `amount`, a `cost` or an `allocation` is sent as asked, not capped to 0, with a warning naming that cause (`[<id>] SELL MARKET order of 1.5 BTC (50 % of 3 BTC): 1.5 BTC sent as asked, which the market refuses unless some of the asset is free by then (3 BTC free at the last synchronization, less 3 BTC for the SELLs placed since)`): it goes through should one of those SELLs be refused or canceled first; an all-in SELL is sent for 0 with its cause line, and nothing is warned of while no balance was read; a SELL by `cost` (`cost / price`, `toSignificantDigits`) or `allocation` (that share of the asset read) is an amount asked for, capped so, its warnings naming the key. It sizes an all-in BUY the same way, from the currency it last read less what the BUYs it placed since may spend (each its cost at its price plus the 5 % fee buffer, a BUY without an amount the budget it was sized from once capped at what is left, or what the market maximum costs at its price plus the buffer when that caps it; an order the strategy cancels after a partial fill (as its polls reported it) still takes what its fill took until the next read, the amount filled for a SELL, what that amount may spend at the order's price for a BUY (`getBuyBudget`), never more than it took when placed), with a warning, so that two all-in BUYs between two balance reads (two entry signals on one candle, two pairs of one currency), or a BUY then an all-in BUY, are not both sized from the whole currency: the second gets what is left, 0 once nothing is, which the market limits refuse. A BUY by `cost` or `allocation` is sized from a budget, its cost or its share of the currency read plus what the Trader's own BUYs open at that read hold, reserved or spent on their fills (so two BUYs of 50 % on one candle both go through in full, and so do two a synchronization apart while the first still rests), capped at what is left with one warning naming the key, the figure asked for and the currency left, with the all-in warning's breakdown (read, less what the BUYs placed since take) when there are some; when the market maximum caps it too, the one line is the maximum's, which keeps `above the free balance, sized from <free>` and drops the breakdown. It also caps every SELL, the trailing stop's included, and every BUY without an amount (all-in, `cost`, `allocation`) at the most the market takes in one order of its type (`amount.max`, narrowed for a MARKET order by `market.max`, Binance's MARKET_LOT_SIZE: see `getMarketOrderLimits`), with one warning naming the amount asked for and the maximum sent: the rest stays held, or unspent, for a later order, and the completed event carries the amount executed. A BUY with an amount is never capped: above the maximum, the exchange refuses it. Nor is an amount that is not a finite number, which only a price so small that the currency buys an infinite amount gives (5e-324, which createOrder lets through): it is sent as it is, for the exchange to refuse, whether the order is a SELL, an all-in BUY or a BUY by `cost` or `allocation` (`capBuyAtMaximum`, one cap for both BUY paths). An all-in order, a BUY by `cost` or `allocation` whose budget comes to nothing, or a SELL by `allocation` of no asset is warned of before the exchange refuses its amount of 0, with the cause: no balance read yet, none of the asset (or currency) free at the last synchronization, or the orders of its side placed since taking what was (an all-in BUY says that last one with its breakdown instead). An order by `cost` or `allocation`, or an all-in BUY, that the market refuses for one of its minimums is warned of before it is sent (`warnOfMarketMinimums`, through `getSentCost`): its amount truncated to the market's amount step as both exchanges send it, against `amount.min` (narrowed for a MARKET order by `getMarketOrderLimits`), then its cost at its price in decimal (95 % of a BUY's budget at most, not the budget) against `cost.min` (`toBound`), the amount first as the exchanges check them, one line at most; the exchange then refuses it, an `orderErrored` counting towards the breaker. The amount line ends `which the market refuses` (`[<id>] BUY MARKET order of 6 USDT: 0.00057 BTC at 10000 sent, below the minimum amount of 0.001 BTC of a MARKET order on BTC/USDT, which the market refuses`). The cost line ends `which the market refuses at that price`, the price it names: the Trader values the cost at the price of the order (the last close or the last synchronization's bid for a MARKET or STICKY order), while CCXTExchange checks a market order at its ticker's ask or bid and a limit order on its tick, so that in realtime the two can lie on either side of the minimum (a BUY of 5.3 USDT at a close of 62499 is sent as 0.00008 BTC, 4.99992 USDT, which passes at an ask of 62501); the simulator checks a market order at the close. When the step cuts the amount, either line says so after `… sent` (`, truncated to 0.00008 BTC on the amount step 0.00001 of the market`) and names the amount sent or its cost, the one the refusal names. The check skips an order sized to 0, which its cause warning covers, one the step cuts to 0, whose refusal names the step, an `amount` order, whose refusal names the amount the strategy chose, and an all-in SELL, which sells the asset free. An all-in BUY gets the same warnings, its line opening with `All-in BUY … sized from <currency left>` (`[<id>] All-in BUY MARKET order sized from 5 USDT: 0.0475 BTC at 100 sent, a cost of 4.75 USDT once 5 % is kept back for the fee, below the minimum cost of 10 USDT on BTC/USDT, which the market refuses at that price`), as a BUY of `allocation: 100` of the same amount does: it is the BUY of the signal strategies on one pair, and of the last pair to buy on several. Every figure of the Trader's lines is written with `formatEveryDecimal`: its sizing lines, and those of an order's summary, estimated summary, cancelation, refusal after a fill, partial fill and invalid price (an optional one through `formatFigure`, `src/plugins/trader/trader.helper.ts`, which keeps `Fee percent: undefined,` for a fee rate no trade gave). Each sizing by `cost` or `allocation` is logged at debug level (the key, its base, the budget, the amount, the price). A share is of the balance as of the last synchronization (every `exchangeSynchInterval` in realtime, every timeframe in backtest, 10 minutes at least, and after each order's end), as all-in is.

- The built-in strategies are the seven signal strategies (CCI, DEMA, EMARibbon, MACD, RSI, SMACrossover, TMA) and GridBot. The seven trade every pair of `watch.assets` (they traded the first alone, and warned of the others) through a `PositionBook` (`src/helpers/strategy/positionBook/positionBook.ts`, a `private readonly book` field): `init` calls `book.track(params)`, then makes the same `addIndicator` calls on each pair of `book.pairs`, pair by pair in that order; every hook that reads candles or indicators loops over `book.pairs`, reading the pair's candle where it reads one (skipped when missing) and its results from `indicatorsBySymbol(indicators)` (`src/helpers/strategy/strategy.helper.ts`: the hooks' indicator arguments grouped by pair, each pair's in `addIndicator` order); a strategy's signal state is kept per pair (a `Map<TradingPair, …>`, reset at `init`); and every line it logs about a pair starts with `[<pair>] `, the rest as it was (`[BTC/USDT] SMA crossed DOWN price (9950.00000 < 10000.00000) => BUY`), but for the position lines of its tracker, which start with the order's id (`[<id>] BUY order canceled: 0.9 BTC filled, enough to sell: the strategy is long`), as built-in-strategies.md says. GridBot alone trades the first pair: `init` takes it with `pickTradedPair(candle, tools)` (`src/helpers/strategy/positionTracker/positionTracker.helper.ts`), which warns once when more pairs are watched, as a custom single-pair strategy can.
- The book keeps one `PositionTracker` per pair, and the seven trade through it: they buy only when flat and sell only when long on a pair (`book.canBuy(pair)`/`book.canSell(pair)`, false for a pair it does not track), never while an order of their own is pending on that pair, place their orders through `book.buy`/`book.sell({ type, symbol: pair }, params)`, the hook's params whole, and hand it the params of their three order hooks whole, which it dispatches to the tracker of `order.symbol`. A BUY takes an equal share of the free currency among the tracked pairs not long, a pair whose BUY is pending counted, since two BUYs of one candle are sized from one balance read: its `allocation` is `round(100 / n, SHARE_DECIMALS, 'down')`, 6 decimals, so the shares of a candle never sum above 100 %, and with n = 1 (a single pair, the last entrant) the BUY goes all-in, today's order, without `allocation`; a SELL stays all-in. The Trader sizes that `allocation` from the currency read plus what its own BUYs open at that read hold of it, reserved or spent on their fills (see the Trader's sizing above), so that a share does not depend on whether a synchronization fell between two BUYs, a STICKY BUY resting across one. On several pairs only (`this.pairs.length > 1`), a BUY the market would refuse is skipped, nothing sent or pending (`buy` returns undefined): one whose estimated cost, its budget (`getAllocatedShare` of the currency in `params.portfolio`: its `free`, plus its `used`, what the exchange holds for the orders open at the read, while another tracked pair is flat with an order of its own pending, a BUY of the book's, since the Trader adds back what its own BUYs open at its read held; all of the `free` for the last entrant's all-in BUY, which the Trader sizes from what is left) × 0.95 (`BUY_COST_SHARE`, 1 − `DEFAULT_FEE_BUFFER`, both in `src/constants/order.const.ts`), is below `toBound(cost.min)` of its market, or whose amount as the Trader would send it, `getAllInBuyAmount(budget, price)` at `order.price ?? candle.get(symbol).close` truncated to the market's amount step (`getSentCost`, `src/helpers/market/market.helper.ts`; the limits of a MARKET order narrowed by `getMarketOrderLimits`), is below `amount.min` or costs less than `cost.min`, worked out by `getBuyRefusal` (`src/helpers/strategy/positionBook/positionBook.helper.ts`; the book's params carry the hook's `candle` for that price). The first skip of a pair is a warning (`[BTC/USDT] BUY skipped: 33.333333 % of the 25 USDT free, 7.9166665875 USDT once 5 % is kept back for the fee, is below the minimum cost of 10 USDT of the market: watch fewer pairs or fund the account; the next skips of this pair are logged at debug level until a BUY of it is placed`; for the amount sent, `…, 5.7 USDT once 5 % is kept back for the fee, 0.00005 BTC at 97654.32 once truncated to the amount step 0.00001 of the market, a cost of 4.882716 USDT, is below the minimum cost of 5 USDT of the market: …`, or `…, 0.00057 BTC at 10000 once truncated to the amount step 0.00001 of the market, is below the minimum amount of 0.001 BTC of the market: …`; while a part is held, the share names it as the Trader's sizing lines do (`[ETH/USDT] BUY skipped: 50 % of 30 USDT: 15.75 USDT free at the last synchronization, plus 14.25 USDT held by the BUYs open then, 14.25 USDT once 5 % is kept back for the fee, is below the minimum cost of 15 USDT of the market: …`), the line otherwise as it was; `used` equals what the Trader adds back for a BUY resting unfilled at its price on Binance, it is less once that BUY has partly filled, and more by the maker fee the simulator holds with it, by a STICKY BUY's tick and moves above its creation price, or by orders Gekko did not place), and its next skips are that line without its suffix, at debug, until a BUY of that pair is placed (no skip without a minimum cost or amount on the market, nor when the portfolio does not list the currency, and no check of the amount sent without a price above 0; every skip line writes the free currency with `formatEveryDecimal`). A BUY skipped while the portfolio shows enough of the pair's asset free to sell at the close makes the tracker long instead (`PositionTracker.adoptHolding(held, close, type, marketData)`, on `isSellable`, only while the tracker is flat with nothing pending), said at info in place of the warning, so that a holding present at start-up is sold at the next SELL signal (`[BTC/USDT] BUY skipped: 50 % of the 8 USDT free, 3.8 USDT once 5 % is kept back for the fee, is below the minimum cost of 5 USDT of the market, but 0.002 BTC is free in the portfolio, enough to sell: the strategy is long`). Otherwise the strategies treat a skip as a refused BUY without the refusal: DEMA, MACD, RSI and CCI wait for the next trend and SMACrossover for the next crossover, while TMA and EMARibbon ask again on each candle of their signal, the book logging its skip at debug. A skip leaves the book's line as its only trace: DEMA, SMACrossover and TMA log their advice line (`[BTC/USDT] Executing long advice due to detected uptrend: …`, `[BTC/USDT] SMA crossed DOWN price (…) => BUY`, at info, relayed as `strategyInfo`) only once `book.buy` has returned an id, the BUY placed, so the TradingAdvisor queues that BUY's `strategyCreateOrder` before the `strategyInfo` of its line (on Telegram, its `strat_create` notification comes before its `strat_info` line); CCI, MACD, RSI and EMARibbon log no line that says the BUY was placed. A book of one pair never skips: its all-in BUY is sent and refused as before, which is how the tracker learns of a holding present at start-up and how an unfunded account trips `maxConsecutiveErrors`. With several pairs, `track` logs one info line naming them and the rule (`Trading BTC/USDT and ETH/USDT: each BUY takes an equal share of the free currency among the pairs not invested, each SELL sells all of its asset`). A completed BUY makes the tracker long, and a completed SELL flat once it sold all it asked for; one that sold less (the Trader's caps), and every all-in or adopted SELL, is read from the portfolio after it, long when the asset left free is enough to sell, said at info level. An order of theirs that ends canceled or errored may have executed: the tracker then reads the position from what a canceled BUY filled, and otherwise from the free balance of the asset in the portfolio after the order, a SELL canceled after a fill included, since its fill tells what is left of the order, not of the holding (a SELL by `cost` or `allocation`, or capped at the market maximum, sells part of it), though never below what that SELL left unsold, which the cancelation released (a portfolio that shows less, or does not list the asset, was read before it); a SELL of an `amount` sent for all of it reads its fill alone, that amount being the position, as when it completes (`coversAmountAsked`, `positionTracker.helper.ts`). It is long when that is enough to sell at the market's minimums, and logs a change at info. They start flat on every pair, so a holding present at start-up is sold only once a BUY of theirs on its pair has ended, completed, or refused or canceled while the account held enough to sell, or has been skipped, on several pairs, while the portfolio showed enough of the asset free to sell. The original Gekko discarded a repeated same-side advice; Gekko relays every advice, so a strategy without that tracking re-advises an all-in BUY on every candle of a trend until the refusals trip the breaker.

It refuses to start while orders are open on its pair, and its lowest-buy and price-tick checks run when the grid starts and again around the price a rebalance ended at.

### Indicators (`src/indicators`)

An indicator extends `Indicator<Name>` (`indicator.ts`): it implements `onNewCandle`, which sets the inherited `result` that `getResult` returns, `null` until the output is complete, then complete on every candle, never a partial object or a placeholder (ROC and TRIX aside, `null` on a zero base). It declares its types by augmenting the global `IndicatorRegistry` interface in its `<x>.types.ts` with `{ input, output }`. The registry key, the class name and the export in `indicators/index.ts` must be identical, because the runtime lookup is `indicators[name]`.

- A constructor checks its parameters before it builds anything, with the helpers of `indicator.helper.ts` (`checkInteger`, `checkNumber`, `checkOneOf`, `checkInputSource`, `checkBelow`, `checkAtMost`), each throwing a `GekkoError` that names the indicator, the parameter and what it accepts. An indicator built on others checks its own parameters first, so that the message names the one the strategy passed. An indicator with a `src` reads its price through `getInputSource(src)` (`indicator.helper.ts`), the close by default.
- A moving average extends `MovingAverage<Name>` (`movingAverages/movingAverage.ts`): it checks its parameters, passes `src` to `super` and implements `update(value)`, which the inherited `onNewCandle` calls with the candle's price. An indicator built on another feeds it its own values through `update`, never a made-up candle.
- A moving-average kind that indicators take as a `maType` is added to `MOVING_AVERAGES` (`movingAverages/movingAverages.const.ts`) and nowhere else: `MOVING_AVERAGE_TYPES`, `MovingAverageTypes` and `MovingAverageClasses` derive from it, and its `satisfies` admits only a `MovingAverage` built from `{ period }`. No moving average may import that file, even through `indicator.const.ts`: the cycle would make the moving average loaded first throw "Cannot access … before initialization" under Bun, and leave it missing from the map under vitest.
- +DM, −DM, +DI, −DI and DX read one `DirectionalMovement` (`directionalMovement/directionalMovement.ts`), whose true range is `getTrueRange` (`volatility/trueRange/trueRange.helper.ts`), as TrueRange's is. These helpers, like `MovingAverage`, are not exported by `indicators/index.ts`, so they are not `addIndicator` names.
- `RingBuffer` (`@helpers/collection/ringBuffer`), the window of ROC, Williams %R, CCI, Stochastic and Bollinger Bands, is read in place: `first` in constant time, `max`, `min`, `sum` and `reduce` in one pass (`sum` and `reduce` oldest first), and its constructor refuses a size that is not a whole number of at least 1 with a `GekkoError` (`[CORE] RingBuffer size must be a whole number, at least 1, got 0`). A callback that needs a value of its caller goes through `reduce`'s `argument`, made once, rather than a closure made on every candle.

### Exchanges, orders and storage

- `exchange.name` picks the implementation, through a zod discriminated union and a switch in the injecter: `binance` and `hyperliquid` use `CCXTExchange` (`sandbox: true` for testnets; the hyperliquid client is created with `builderFee: false`, otherwise ccxt signs a builder-fee approval at the first order and attaches a 1 bp fee to every one); `dummy-cex` is `DummyCentralizedExchange`, the backtest simulator; `paper-binance` trades simulated orders on live Binance data. A new CCXT exchange needs its schema, a union entry, an injecter case and a `LIMITS` entry in `src/services/exchange/exchange.const.ts`, and ccxt must list every feature of `BROKER_MANDATORY_FEATURES` there in its `has`, which `checkMandatoryFeatures` checks as `CCXTExchange` is built. `fetchOpenOrders` is one of them: `fetchOpenOrders(symbol)` lists the orders open on a pair, whoever placed them (ccxt's live, the simulator's book in backtest and paper trading). `fetchMyTrades` leaves out, with one warning, a ccxt trade without an amount and a price above 0 (`isExecutedTrade`): read as 0, an unknown price entered the mean price of its order.
- The credentials are optional in the exchange schemas, an import reading the public client alone: binance's `apiKey` and `secret`, hyperliquid's `privateKey` (it signs the orders) and `walletAddress` (the account ccxt reads, and trades for). On hyperliquid, `privateKey` without `walletAddress` is refused, and in realtime the configuration requires `walletAddress` with a TradingAdvisor or a Trader and `privateKey` with a Trader (checked once the sections have no issue); binance's keys are not checked by plugin. A number at either hyperliquid key (an unquoted `0x…`, hexadecimal to YAML and JSON5) is refused with a message saying to quote it.
- The schema ties the exchange to the mode: backtest takes `dummy-cex` only, importer takes `binance` or `hyperliquid`, realtime takes `binance`, `hyperliquid` or `paper-binance`.
- The simulator's clock is the close of the last candle. It keeps one order book per pair. Limit orders fill in full once a candle's low/high reaches their price, market orders fill at the last close, and there are no partial fills or slippage. Fees and order limits come from `exchange.marketData`, which must hold exactly one entry per watched pair. Its `precision` is given as a number of decimals (`8`) that the schema converts to a step (`1e-8`), because `MarketData.precision` holds steps everywhere else, as ccxt reports them; an optional `precision.priceSignificantDigits` (Hyperliquid's 5) is handed on as it is. Before it checks the limits, the simulator puts an order on the steps of the market as `CCXTExchange` sends it (`roundToMarketPrecision`, `dummyCentralizedExchange.helper.ts`, on `roundToStep` and `getPriceTick`): the amount truncated to the amount step, the price rounded half up to the tick at that price. An amount truncated to 0, or whose cost falls under `cost.min`, is refused, the cost worked out in decimal (`multiplyPrecise`) by `assertOrderWithinLimits`, as both exchanges check it, so that an order costing exactly `cost.min` passes. An amount or a price rounded to nothing is refused as the order asked for it, with the step (`Order 'amount' with value 0.0000099 rounds to 0 on the amount step 0.00001 of the market. …`). An order fills, and is reported, for the amount truncated. The simulator charges the fee in the currency, on top of a BUY and out of a SELL's proceeds, works out the currency of each order in decimal (amount × price × (1 ± fee), `multiplyPrecise`) and rounds it to 8 decimals (`COST_DECIMALS`), a half up, as Binance keeps its balances, and books every balance in decimal (`addPrecise`). Its refusal for want of funds names both figures with every decimal (`Insufficient asset balance (portfolio: 0.0000005, amount: 1)`). Its state sits behind an `AsyncMutex` (`src/helpers/async/asyncMutex.ts`), FIFO and not reentrant: a free lock runs the section at once, in the caller's tick, and an exchange call made by an `onSettled` callback runs once the bucket is processed. `MarketData.market`, when present (Binance `MARKET_LOT_SIZE`, which paper trading carries from the real market and a backtest states as an optional `market` range of its `marketData` entry, either bound optional, each checked as those of the other ranges are), narrows the amount range of MARKET orders; `CCXTExchange` and the simulator refuse such an order before sending it.
- Order classes are event emitters. In backtest they settle through exchange callbacks; in realtime, paper trading included, LIMIT and STICKY orders poll `fetchOrder` every `orderSynchInterval` from their creation, while a MARKET order settles from the answer to its creation, polled so only when that answer leaves it open (`… order still open after its creation, unexpected for a market order`, a warning). A creation is sent once and never replayed. One whose outcome is unknown ends the order in error with `mayBeLive` true, never as a refusal: lost on the network (`ExchangeNetworkError`), or `OrderOutcomeUnknown` when the exchange answered without anything to follow the order by, its state could not be read back, or ccxt threw an `OperationFailed` that is not a `NetworkError` (Binance -1000, -1006, a busy exchange). So does an order whose poll, cancelation or read-back fails for good while it is open. The reads of `CCXTExchange`, unlike its creations and cancelations, go through `retry`: after a ccxt NetworkError a read is sent again up to 3 more times, 1000, 1585 and 2000 ms apart (`getRetryDelay`, attempts numbered from 0 as the fetcher numbers its requests), each failure logged at debug level only, since the caller logs what it could not read at the level it deserves.
- Trader on a real, non-sandbox exchange is refused unless the config sets `'I understand that Gekko only automates MY OWN trading strategies': true` at its top level (the exchange section refuses the key as unknown). `config/realtime-trader.yml`, quick-start.md and modes.md write the key quoted, as the refusal message does: js-yaml also reads a flow sequence (`[I understand …]: true`) as the sentence, but other YAML parsers read a list, which the schema refuses as an unknown key.
- Storage is `SQLiteStorage` on `bun:sqlite`, the only Bun-specific API in `src/`. It keeps one table of 1-minute candles per pair (`CANDLES_<ASSET>_<CURRENCY>`, upper-cased and always quoted in SQL, so tickers such as `1INCH` work), and `storage.database` is a path relative to the working directory. The `storage` section is required in backtest mode and whenever a `CandleWriter` plugin is configured, and ignored otherwise; `insertThreshold` is an integer number of minutes between 1 and 1440 (default 1 in realtime, 1000 otherwise) and `watch.batchSize` is bounded to 31 days of minutes. What replaces a stored minute depends on the mode and on the candle: an import replaces whatever is stored for the minutes the exchange returns, a minute without trades included, and its own made-up candle for a minute the exchange lacks only replaces a stored candle that is made up too (flat, volume 0); the other modes replace a stored candle only when it is made up, and only with a candle that traded, so a made-up candle never replaces one that traded. `open()` sets a 5 s busy timeout and reads `sqlite_master` before anything else, so that a file that is not a database, or one cut within its header, fails there with its path (`PRAGMA schema_version` passes a file cut within its 100-byte header). `close()` inserts the buffered candles, then closes the connection whatever that insert did, and only its first call does anything, a failed one included (main() closes the storage again after CandleWriter). A failed insert throws `[STORAGE] Could not write the buffered candles into <path> (<SQLite's error>): the minutes from <start> to <end> were not written, <count> of <pair>, …. An import of that range writes them.`, caused by SQLite's error, the count covering only the pairs it did not insert.

  - `live-trader/`, the one flow whose orders go through CCXTExchange to ccxt: a Trader on Binance's testnet (`sandbox: true`) on the mock's account, ordering through `DebugOrderScript`: the two clients in sandbox mode, or on Binance itself with the disclaimer; MARKET orders answered closed or filled through the polls; a LIMIT BUY put on the tick, partly filled and canceled; a LIMIT SELL that sold 0.4 of 1 BTC, canceled, and the MARKET SELL of 1 sent on that candle capped at the 0.6 left and completed; creations whose outcome is unknown (`mayBeLive` true, the order executed) or refused; and the orders open at start-up handed to GridBot's `init`.

## Stale docs and example configs

`README.md` and `documentation/*.md` were written before the multi-asset refactor. The six guides, `quick-start.md`, `modes.md`, `plugins.md`, `built-in-strategies.md`, `custom-strategies.md` and `indicators.md`, have since been brought up to date: their YAML examples validate against the schemas and their TypeScript examples type-check, which `scripts/documentation/documentation.test.ts` checks (see Testing). `README.md`, which holds no code block, has been brought up to date too: its About and Summary say what Gekko does today. Prettier does not format the root's `documentation/` (`/documentation` in `.prettierignore`, whose patterns start with a slash: a bare name matched at any depth and also skipped `scripts/documentation/`), whose tables are aligned by hand, and `documentation/dev/` is gitignored: local notes and specs, never committed. quick-start.md has the reader write each configuration as a `config/<name>.local.yml` copy, which git ignores (`config/*.local.*`), never over a tracked example of `config/`. When a doc and the code disagree, trust the zod schemas (`configuration.schema.ts`, `src/plugins/**/*.schema.ts`, `src/services/exchange/**/*.schema.ts`) and `strategy.types.ts`. The usual traps when copying from an older doc or config:

- `watch.asset` is now `watch.assets: [...]`, and `exchange.key` is `apiKey`.
- `simulationBalance` is a list of `{ assetName, balance }`, naming only the watched assets and the currency, spelt as `watch` spells them (`usdt` is refused).
- Assets, currency and symbols are upper case (`btc` is refused, not read as `BTC`), and `simulationBalance`, `marketData` and `initialTicker` list each asset or symbol once.
- A daterange bound written as a day alone is its midnight UTC: `end: 2024-12-31` reads only the first minute of December 31st. Write `2024-12-31T23:59:00Z` to end with that day (`2025-01-01` reads the first minute of the next one too). A date and a time need `Z` or an offset.
- Strategy parameters sit directly under `strategy:`, not under `params:`.
- A signal strategy trades every pair of `watch.assets`, where it traded the first alone and warned of the others: an older configuration that watches several assets to trade the first now trades them all, each BUY a share of the currency. Watch one asset to trade one pair; GridBot still trades the first, and the RoundTripAnalyzer still refuses several.
- The `PerformanceAnalyzer` plugin no longer exists; use `PortfolioAnalyzer` or `RoundTripAnalyzer`.
- `addIndicator` takes `(name, symbol, params)`, and `params` is required even when every parameter has a default: pass `{}` then, `undefined` for TrueRange.
- Gekko's shared helpers moved under `src/helpers/` (`@helpers/…`), and every `<name>.utils.ts` outside `src/utils/` was renamed `<name>.helper.ts`, with nothing left at the old paths: an older guide's `import { pickTradedPair, PositionTracker } from '@strategies/positionTracker'` is now `PositionTracker` from `@helpers/strategy/positionTracker/positionTracker` and `pickTradedPair` (and `isSellable`) from `@helpers/strategy/positionTracker/positionTracker.helper`, the suites' helpers of `@strategies/positionTracker.mock` in `@helpers/strategy/positionTracker/positionTracker.mock`; a domain module of `@utils` is `@helpers/<dir>/<name>.helper` (`@utils/market/market.utils` is `@helpers/market/market.helper`, and so for candle, event, finance/stats, market/precision, portfolio and stream), `@utils/async/asyncMutex`, `@utils/collection/ringBuffer` and `@utils/event/sequentialEventEmitter` are under `@helpers/` too, and `getBuyBudget` and `getAllInBuyAmount`, of `@plugins/trader/trader.utils`, are in `@helpers/order/sizing.helper`. A strategy of `src/strategies/custom/` that keeps an old path stops every run at start-up, whatever its mode and its strategy (`ResolveMessage: Cannot find module '@strategies/positionTracker' from '…/src/strategies/custom/…'`, logged by `main()` under the `gekko` tag: `strategies/index.ts` loads it with the built-in ones), fails `type:check` (TS2307) and `build:exec` (`Could not resolve`); custom-strategies.md's Troubleshooting lists the moves.
- Every section but `strategy` refuses unknown keys, so a retired or misspelt one (`asset`, `fillGaps`, `tickRate`, `sandBox`) is an error, not a silent default. `tickrate` and `warmup.tickrate` are integers of at least 100 ms; `storage.insertThreshold` is an integer number of minutes between 1 and 1440.
- A dummy-cex example without `exchange.marketData` is incomplete: a backtest needs one entry per watched pair (`config/backtest.yml` and `documentation/modes.md` have complete blocks).
- Keys go in a copy of the example, `config/<name>.local.yml`, which git ignores (`config/*.local.*`), never in a tracked file of `config/`: Gekko reads no environment variable inside the file (`${BINANCE_API_KEY}` is that text).
- Hyperliquid's `privateKey` and `walletAddress` are written in quotes (`'0x…'`): unquoted, YAML reads them as numbers, which the schema refuses.

In `config/`, `backtest.yml`, `importer.yml`, `importer-hyperliquid.yml`, `realtime-writer.yml` and `realtime-hyperliquid-writer.yml` validate as they are. The other `realtime-*.yml` files validate once their credentials are filled in, `realtime-trader.yml` also once its disclaimer is set to `true`, and each opens with a comment saying to fill them in a copy, `config/<name>.local.yml`, which git ignores, and that Gekko reads no environment variable in the file. The documentation test checks them so, each empty credential filled in with a stand-in. `importer-hyperliquid.yml` imports the last days only: Hyperliquid's API serves only the latest 5000 candles of an interval, about 3.5 days of 1-minute candles, so its range has to be moved before a run.
